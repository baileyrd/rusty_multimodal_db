## Methodology

- Backends: `AosStore` (`Vec<DogRecord>`), `SoaStore` (parallel `Vec<Uuid>`/`Vec<String>`/`Vec<u32>`), `CanonicalStore` (`HashMap<Uuid, DogRecord>` + a breed→UUIDs index, `scan_ages`/`same_breed` implemented as views over the map, not copies — see ADR-0001), `CanonicalCachedStore` (`CanonicalStore`'s map and breed index, plus a packed `Vec<u32>` age cache and a `HashMap<Uuid, usize>` position index, `update_age` writing through to both the map and the cache — see ADR-0003).
- Dataset sizes: 1,000 / 100,000 / 1,000,000 records.
- Breed cardinality: fixed at 50 distinct breeds across all sizes (a reuse-heavy case, representative of "~50 real dog breeds shared across however many dogs") — the case where a breed index is expected to help most. A cardinality sweep was not run this pass; see Open Questions.
- Seed: fixed (`20260824`), so this run is reproducible via `cargo bench`.
- Point-workload benchmarks (`get`, `update_age`, `same_breed`) rotate through 200 pre-sampled target UUIDs per dataset rather than hitting one fixed UUID, specifically to avoid keeping a single record's cache line artificially hot across iterations — see `STORAGE-003`'s data/state notes and `benches/workloads.rs`.
- Criterion run with reduced sampling for this pass (`--warm-up-time 1 --measurement-time 2 --sample-size 20`, vs. Criterion's defaults of 3s/5s/100) to keep total run time reasonable. Confidence intervals were still tight (typically ≤5% spread between low/high estimates; see raw output), so this reduction doesn't call the verdicts below into question, but a final/published number set should use Criterion's defaults or higher. Machine: this session's cloud Linux container — not the owner's Windows dev machine or `baileyai`; see the cache-miss section below for why that matters more for hardware counters than for wall-clock numbers.
- Full raw Criterion output is reproducible via `cargo bench` (`benches/workloads.rs`); this document reports the point estimate (the middle of Criterion's `[low median high]` triple) for each case. Two separate `cargo bench` runs (first pass: 3 backends; this revision: 4 backends) produced the AoS/SoA/Canonical numbers below — they agree with the first pass within normal run-to-run noise (a few percent), which is why they aren't reported as a fifth "before" column.

All numbers below are **median wall-clock time per call**, lower is better. Winner(s) per row in **bold**.

## `get` (full-record read by UUID)

| Size | AoS | SoA | Canonical | Canonical+cache |
|---|---:|---:|---:|---:|
| 1,000 | 496.7 ns | 478.8 ns | **60.0 ns** | **59.9 ns** |
| 100,000 | 69.47 µs | 45.93 µs | **69.4 ns** | **69.4 ns** |
| 1,000,000 | 2.467 ms | 744.7 µs | **72.7 ns** | **71.6 ns** |

**Verdict: Canonical and Canonical+cache are tied for the win, both clearly ahead of AoS/SoA, and the margin grows with scale.** `get` doesn't touch the age cache at all — it's the same `HashMap<Uuid, DogRecord>` lookup in both backends — so this is exactly the sanity check it looks like: adding the age cache cost `get` nothing. At 1M records, both are ~34,000× faster than AoS and ~10,300× faster than SoA.

## `scan_ages` (column scan / average-age aggregate)

| Size | AoS | SoA | Canonical | Canonical+cache |
|---|---:|---:|---:|---:|
| 1,000 | 501.8 ns | **119.4 ns** | 2.294 µs | **119.4 ns** |
| 100,000 | 181.1 µs | **16.27 µs** | 346.9 µs | **16.32 µs** |
| 1,000,000 | 5.887 ms | **291.6 µs** | 14.96 ms | 332.2 µs |

**Verdict: Canonical+cache closes the gap — it matches SoA at 1K/100K and is statistically indistinguishable from it at 1M once measurement noise is accounted for (see below), while beating AoS outright at every size.** This is the fix working as intended: `scan_ages` on `CanonicalCachedStore` reads the packed `age_cache: Vec<u32>` directly, the same contiguous-array access SoA gets, instead of walking `HashMap` buckets and heap-allocated `DogRecord`s. At 1M records, Canonical+cache is **~45× faster than plain Canonical** and **~17.7× faster than AoS** — completely reversing plain Canonical's loss to AoS, not just narrowing it.

**Follow-up on the ~14% residual gap to SoA at 1M — diagnosed, not a real gap.** The reported table numbers come from one `cargo bench` run; re-running `scan_ages/soa/1000000` vs. `scan_ages/canonical_cached/1000000` two more times at higher rigor (50 samples/3s, then 100 samples/5s, both up from the 20-sample/2s run behind the table above) settled the question at check 1 (noise check) before checks 2/3 were needed: the *sign* of the gap flips between runs — run 1 (table above): Canonical+cache ~14% slower (332.2 µs vs. 291.6 µs); run 2: ~12% *faster* (263.2 µs vs. 298.9 µs); run 3: ~9% faster (255.0 µs vs. 280.4 µs). A real structural cost wouldn't flip sign under more rigorous sampling — this is measurement noise from this session's shared/virtualized environment (consistent with ADR-0002's separate finding that this same environment lacks stable hardware-counter access) dominating an effect this small at this timescale (~250–330 µs total), not a real cost of `CanonicalCachedStore`'s extra fields. For completeness, the two code-level checks the noise check would have skipped were confirmed clean anyway: the age cache is built with `Vec::with_capacity(records.len())` up front (no reallocation-via-`push` growth), and `scan_ages` returns it via a plain `.clone()` (memcpy path, not a per-element `.collect()`). **No code changed as a result of this pass** — the table above is left as originally measured (rerunning it would just swap in a different single sample of the same noise), with this paragraph as the record of why the residual gap isn't chased further.

## `update_age` (random single-field update) — the cost of write-through

| Size | AoS | SoA | Canonical | Canonical+cache |
|---|---:|---:|---:|---:|
| 1,000 | 409.7 ns | 460.1 ns | **35.1 ns** | 52.8 ns |
| 100,000 | 68.81 µs | 47.07 µs | **46.0 ns** | 68.3 ns |
| 1,000,000 | 2.916 ms | 677.2 µs | **46.2 ns** | 70.4 ns |

**Verdict: Canonical+cache is still a clear, overwhelming win over AoS/SoA — the eager write-through cost is real but small relative to what it protects.** Per ADR-0003's check-in threshold (roughly an order of magnitude): the actual regression from plain Canonical to Canonical+cache is **~1.5× at every size** (52.8/35.1 ≈ 1.50 at 1K; 68.3/46.0 ≈ 1.48 at 100K; 70.4/46.2 ≈ 1.52 at 1M) — a second `HashMap` lookup (the position index) plus one array write, not a second linear scan or anything worse. That's well under the threshold that would have called for a check-in, so this proceeded straight through per the task's working-style instructions. At 1M records, Canonical+cache is still **~41,400× faster than AoS** and **~9,600× faster than SoA** — the write-through overhead is essentially invisible next to the O(n)-vs-O(1) gap that dominates this workload for both baselines.

## `same_breed` (one-hop lookup — graph-view stand-in)

| Size | AoS | SoA | Canonical | Canonical+cache |
|---|---:|---:|---:|---:|
| 1,000 | 3.927 µs | 4.209 µs | **342.9 ns** | 355.9 ns |
| 100,000 | 422.7 µs | 407.1 µs | **5.895 µs** | 6.000 µs |
| 1,000,000 | 11.19 ms | 7.953 ms | **70.09 µs** | 69.11 µs |

**Verdict: Canonical and Canonical+cache are effectively tied for the win, both far ahead of AoS/SoA.** `same_breed` doesn't touch the age cache either — same breed index, same lookup path in both backends — so the two backends track each other within noise (largest gap: 355.9 ns vs. 342.9 ns at 1K, ~4%; they're within 2% of each other at 1M). At 1M records, both are ~160× faster than AoS and ~114× faster than SoA.

## Where the hypothesis wins vs. loses — explicit call-out

- **Canonical (uncached) still loses clearly**: `scan_ages` — worse than *both* baselines, and the gap widens with `n`. This finding from the first pass is unchanged; it's exactly what motivated building the fourth backend.
- **Canonical+cache turns that loss into a win**: `scan_ages` goes from "worse than AoS, 48× worse than SoA" (plain Canonical, at 1M) to "beats AoS by ~17.7×, statistically tied with SoA" (Canonical+cache — the initially-reported ~14% residual gap didn't reproduce under repeated, higher-rigor measurement; see the `scan_ages` section's follow-up paragraph) — for the cost of one extra `Vec<u32>` and, per `update_age`'s numbers above, a ~1.5× write-time tax that's negligible against Canonical's underlying advantage there.
- **Canonical+cache wins everywhere Canonical won, at effectively no cost**: `get` and `same_breed` are identical between the two (neither touches the age cache), so Canonical+cache doesn't trade away any of Canonical's existing wins to fix `scan_ages`.
- **Net picture, updated**: with the fourth backend, there is no longer a workload where the UUID-canonical family loses outright — `CanonicalCachedStore` wins or ties the win on all four workloads benchmarked. The interesting remaining tradeoff isn't "canonical vs. row/column baselines" anymore, it's "is the ~1.5× `update_age` tax and the extra `Vec<u32>` memory worth it," which is a much easier case to make than the first pass's genuine three-way split. See Open Questions for what would still need checking (write-heavy mixed workloads, memory overhead) before calling this fully settled.

## Cache-miss measurement (real hardware counters, `baileyai`)

Obtained this pass, on `baileyai` (bare-metal Fedora Server) — the machine named in ADR-0002 specifically because it has real PMU access, unlike every prior session's container. `cargo bench --bench cache_events --features perf-events` (note: the Cargo feature is `perf-events`, not `cache-events`) ran clean for all four backends.

**PMU access needed one sysctl change.** `perf_event_paranoid` was `2` by default, which fails every hardware counter with `Could not create counter: Os { code: 13, kind: PermissionDenied, ... }`. `sudo sysctl -w kernel.perf_event_paranoid=1` was sufficient — didn't need `0` or `-1`. This is a live, non-persistent sysctl write (resets on reboot, no `/etc/sysctl.d` file added), so it's this-session-only, not a permanent host change.

**Coverage gap fixed first.** `benches/cache_events.rs` as it stood only benchmarked `get` and `same_breed` — a prior session's own comment on the file argued `scan_ages` and `update_age` weren't worth measuring, on theories about what would dominate their cost. Those theories were never actually checked against hardware counters (the environment that wrote them had no PMU access at all), and `scan_ages` specifically is the workload this run most needed to check. `benches/cache_events.rs` was extended to cover all four workloads, mirroring `benches/workloads.rs`'s existing `run_scan_ages`/`run_update_age` patterns exactly — no `src/` changes, per the task constraints.

**Unit note**: Criterion labels the measurement axis "cycles" regardless of which `Perf` counter is plugged in — for this run it's actually the selected hardware event's raw count per call (`cache-misses` or `cache-references`), not CPU cycles. Fractional values below 1 are real: Criterion's point estimate is a per-iteration average over a batch of iterations, and sub-1 averages just mean "usually zero misses this call."

**Working-set caveat**: `get`/`update_age`/`same_breed` rotate through a pool of 200 pre-sampled UUIDs (`RoundRobin`, `SAMPLE_TARGET_COUNT`) across each benchmark's full measurement window (typically tens of thousands to low millions of iterations). For the two `HashMap`-based backends this means the *same* ~200 records get re-touched constantly within one measurement window, so they stay cache-resident after the first few iterations regardless of overall dataset size — that's why `canonical`/`canonical_cached`'s `get`/`update_age` miss counts below sit near zero even at 1M records. That's a real property of this benchmark's access pattern (and it's the same pattern the wall-clock suite already uses, so the two are comparable), not evidence that a HashMap lookup into an out-of-cache 1M-entry map costs nothing in general — a genuinely cold, uniformly-random-across-all-records access pattern would show more. AoS/SoA don't get this benefit because their `get` is a linear `.find()`/`.position()` scan that touches a scan-distance-dependent amount of memory per call.

Machine: `baileyai`, AMD Ryzen AI Max+ 395 (32 threads), L1d 768 KiB/16 instances, L2 16 MiB/16 instances, L3 64 MiB across 2 instances (32 MiB per CCD) — noted because it's relevant to the `scan_ages` finding below: a 1M-record `AosStore` (~48 MB of `DogRecord`s alone, plus scattered heap-allocated breed `String`s) doesn't fit in one CCD's 32 MiB L3 share, while the 100K case (~4.8 MB) comfortably does.

### `get` — cache-misses per call

| Size | AoS | SoA | Canonical | Canonical+cache |
|---|---:|---:|---:|---:|
| 1,000 | 0.011 | 0.012 | **0.002** | **0.002** |
| 100,000 | 1,479.9 | 336.9 | **0.002** | **0.002** |
| 1,000,000 | 1,798.9 | 1,237.6 | **0.002** | 0.004 |

**Verdict: Canonical and Canonical+cache both show dramatically fewer cache misses than AoS/SoA, matching the wall-clock win.** Given the working-set caveat above, this specific gap is partly an artifact of the 200-ID rotation pool keeping the `HashMap`-based backends' small working set resident — but AoS/SoA's `.find()`/`.position()` genuinely does scan real memory (338–1,800 misses/call, scaling with the touched-region size), so the *relative* story — hash lookup beats linear scan on cache behavior, not just wall-clock — holds regardless.

### `scan_ages` — cache-misses per call

| Size | AoS | SoA | Canonical | Canonical+cache |
|---|---:|---:|---:|---:|
| 1,000 | 0.015 | **0.003** | 0.045 | **0.003** |
| 100,000 | 8,100.8 | **269.4** | 10,962.6 | 909.9 |
| 1,000,000 | 44,872.2 | 23,816.8 | 1,100,195.9 | **7,097.9** |

**Verdict, directly answering the task's core question: at 1M records — the size where wall-clock timing called Canonical+cache and SoA statistically tied — real hardware counters show Canonical+cache has a genuine structural advantage: ~3.36× fewer cache misses (7,097.9 vs. 23,816.8).** Cache-references at 1M are nearly identical between the two (Canonical+cache 250,317.8 vs. SoA 251,847.7 — both are `.clone()` of an already-packed `Vec<u32>`, so this checks out: same amount of data touched), which means the real signal is in the **miss rate**: Canonical+cache misses on 2.84% of references vs. SoA's 9.46% — over 3× more efficient per access, not just fewer total accesses. This is exactly the kind of thing wall-clock timing on a noisy/virtualized environment can't resolve but a hardware counter can: **the prior diagnostic session's conclusion that the ~14% wall-clock gap was "noise, not real" was correct about wall-clock time specifically, but cache-miss counts now show Canonical+cache is the structurally better choice at 1M, even though that didn't show up as a wall-clock win.**

One honest wrinkle: at 100K, the direction flips — SoA has fewer misses (269.4 vs. 909.9) and a lower miss rate (2.06% vs. 6.06%) than Canonical+cache, even though both backends run the identical `.clone()`-of-a-packed-`Vec<u32>` code path at every size (verified in `src/store/soa.rs`/`src/store/canonical_cached.rs` — this isn't a code-path difference). The likely explanation is that Canonical+cache also carries a `HashMap<Uuid, DogRecord>`, a breed index, and a `HashMap<Uuid, usize>` position index alongside `age_cache`, all built during `Dataset` construction just before the benchmark runs — a much larger co-resident working set than SoA's three flat arrays, which could change cache-associativity conflicts differently at 100K's specific data volume (~a few hundred KB of just `age_cache`, well inside even one CPU core's L2) than it does at 1M's (~4 MB of `age_cache` alone, past L2 territory for one core, into shared-L3 territory where the CCD's total occupancy from those other structures matters more). This is a plausible mechanism, not a verified one — flagged as an open question below rather than asserted as settled.

**Follow-up investigation (this pass): the "larger co-resident working set" mechanism above is real but doesn't cleanly explain the crossover's *direction*.** `examples/memory_footprint.rs` (new — a counting global allocator, no PMU/`perf` access needed, so this runs from any session) measured the actual live-byte footprint of each backend at construction, rather than guessing at struct-size math:

| Size | SoA total | Canonical+cache total | Canonical+cache's extra |
|---|---:|---:|---:|
| 100,000 | ~11.2 MB | ~20.9 MB | ~9.7 MB (+87%) |
| 1,000,000 | ~112.0 MB | ~287.0 MB | ~175.0 MB (+156%) |

If "more co-resident bookkeeping bytes → more cache misses" were the *whole* story, Canonical+cache's misses should be higher than SoA's at both sizes (its footprint is larger at both, and *relatively* larger still at 1M — 156% vs. 87% extra). Instead it's higher only at 100K and reverses at 1M, the opposite of what footprint size alone predicts. That rules out the simplest version of the hypothesis without replacing it with a confirmed one. One concrete, measured lead worth naming: `CanonicalStore`'s own per-record overhead (which `CanonicalCachedStore` inherits, plus its own additions) is *not* stable across sizes — 111.8 bytes/record at 1K, 56.6 at 100K, 114.5 at 1M (see `examples/memory_footprint.rs` output) — consistent with `HashMap`'s (hashbrown's) capacity landing on different sides of a power-of-two growth boundary at different `n`, rather than scaling smoothly. Whether *that* specific quantization effect is what actually drives the cache-miss crossover, versus something in how the allocator happens to place the `age_cache`/`ages` arrays themselves, isn't something byte-counting can settle — it needs to see *which cache tier* the extra misses land in. `benches/scan_ages_crossover.rs` (new) adds L1-data-cache and last-level-cache read-access/read-miss counters (via `perfcnt`'s `from_cache_event`, not the generic `CacheMisses`/`CacheReferences` events `benches/cache_events.rs` uses), scoped narrowly to `scan_ages` on SoA vs. Canonical+cache at 100K and 1M.

**Run on `baileyai` (second real-hardware pass). Result: L1 is ruled out; last-level cache isn't measurable on this hardware via this method.** L1-data read-miss rate is nearly identical between backends at both sizes — 60.25% (SoA) vs. 59.40% (Canonical+cache) at 100K, 57.93% vs. 58.29% at 1M, differences under 1.5 percentage points either way, a small fraction of the ~3× relative difference the generic (deeper-cache) counters showed. Whatever drives the crossover, it isn't happening at L1 — both backends touch the identically-sized, identically-shaped `age_cache`/`ages` array the same way at that tier. The last-level-cache half of this experiment didn't run: `CacheId::LL` via the generic `PERF_TYPE_HW_CACHE` interface returns `ENOENT` on `baileyai`'s AMD Ryzen AI Max+ 395 — AMD's PMU doesn't implement that generic descriptor the way Intel's does; getting L2/L3-specific counts on AMD needs raw, model-specific perf event codes, out of scope for this benchmark harness. **This crossover is now considered investigated to the practical limit of available tooling, not resolved** — L1 is cleared, the deeper cache tier where the effect actually lives isn't reachable from this hardware without a materially larger investment (raw AMD perf events) that isn't justified given the decision this data needs to support (`CanonicalCachedStore` wins/ties every workload regardless of this crossover's exact mechanism). Not planned as further work unless the owner wants to pursue raw AMD PMU events specifically.

## Graph traversal

**Separate from, and does not alter, the row/column verdict above.** Everything in this section tests a different question — the previously-untested third leg of the original row/column/graph hypothesis (see the charter) — using a real generated edge relationship (`littermate_of`, see `STORAGE-006` and ADR-0004) rather than `same_breed`'s shared-attribute stand-in. The `get`/`scan_ages`/`update_age`/`same_breed` verdicts above are unchanged and not re-litigated here.

### Methodology

- `littermate_avg_degree` fixed at `1.5` (mid-range of the valid `[0.0, 3.0]` band) across all sizes, independent of dataset size — same rationale as `BREED_CARDINALITY`'s fixed value: held constant so dataset *size* stays the only swept dimension. A degree sweep was not run this pass; see Open Questions.
- Same seed (`20260824`), same three dataset sizes (1K/100K/1M), same 200-target rotation pool as every other workload in this document (`RoundRobin`/`SAMPLE_TARGET_COUNT`, see `STORAGE-003`).
- `neighbors_one_hop` calls `DogStore::neighbors` directly. `neighbors_two_hop` calls `bench_support::two_hop_neighbors` — the deduplicated union of `neighbors(n)` for every `n` in `neighbors(id)`, built generically from two rounds of `neighbors` calls (not a trait method — see ADR-0004).

### Where the graph-traversal hypothesis stands

- **`neighbors` (one-hop, real edge traversal) confirms the same result `same_breed` (shared-attribute stand-in) already showed**: a `HashMap`-based adjacency index over the canonical store beats a linear scan by 4-5 orders of magnitude at scale, and costs nothing extra for `CanonicalCachedStore` to carry alongside its age cache (Canonical and Canonical+cache are within noise of each other at every size, same as `get`/`same_breed`).
- **Composing two `neighbors` calls generically (`two_hop_neighbors`, not a trait method) preserves the win** — the naive baselines don't catch up as traversal depth increases from 1 to 2 hops; if anything the relative gap widens slightly at 1M.
- **This is real graph traversal, not a repeat of `same_breed`'s result under a different name** — `same_breed` never required following an edge between two specific records; `littermate_of` does, and the adjacency-index pattern generalizes to it directly, which is itself the finding: the "views over one canonical store" hypothesis's graph leg holds for the one relationship type and hop depth tested here.

## Mixed read/write workload

**Separate from, and does not alter, the row/column or graph-traversal verdicts above.** Every other workload in this document isolates one call type per benchmark. Real usage doesn't: a store is hit with some blend of reads and writes, and `CanonicalCachedStore`'s one known cost — the eager write-through tax on `update_age` (`STORAGE-005`/ADR-0003, ~1.5× over plain `CanonicalStore` in isolation) — could in principle add up differently once writes are actually interleaved with the reads they're supposed to keep correct for. This section tests that directly with `MixedWorkloadDriver` (`src/bench_support.rs`, `STORAGE-007`): a single seeded, blended sequence of `get`/`update_age`/`scan_ages` calls, swept across write ratios of 10%/50%/90% (remainder split evenly between `get` and `scan_ages`), each call timed as it falls in the blended stream — the reported number is **median time per operation in the blended sequence**, not broken out per call type.

### Methodology

- `MixedWorkloadDriver::next_op` draws each call independently: `write_ratio` chance of `update_age`, else a coin flip between `get` and `scan_ages` — so at `write_ratio = 0.10` the long-run split is 10% write / 45% get / 45% scan; at `0.50` it's 50/25/25; at `0.90` it's 90/5/5.
- Target UUIDs for `get`/`update_age` are drawn from the same 200-ID `RoundRobin` rotation pool every other point workload in this document uses (`SAMPLE_TARGET_COUNT`) — no new ID-sampling logic was built for this driver.
- Same seed (`20260824`, XORed with a driver-specific constant for an independent op-selection RNG stream), same three dataset sizes (1K/100K/1M), same fixed breed cardinality (50) and littermate degree (1.5) as every other workload in this document.
- Criterion run with the same reduced sampling as the rest of this document (`--warm-up-time 1 --measurement-time 2 --sample-size 20`), except `write90/canonical/1000000` below, which was re-run at higher rigor (`--measurement-time 5 --sample-size 50`) after the first pass came back with an unusually wide confidence interval (±20% around the point estimate, vs. typically ≤10% elsewhere in this sweep) — flagged and re-checked per this document's established noise-diagnosis practice (see the `scan_ages` section above), not silently reported as-is. The re-run's point estimate is what's reported; it moved *further* from `CanonicalCachedStore`, not closer, so the added rigor only reinforces the verdict below. Machine: this session's cloud Linux container (same caveat as the rest of this document).
- All numbers below are **median wall-clock time per operation in the blended sequence**, lower is better. Winner(s) per row in **bold**.

### Does `CanonicalCachedStore` ever lose to `CanonicalStore` or `SoaStore`? — directly answered

**No. Across all 9 configurations tested (3 write ratios × 3 sizes), `CanonicalCachedStore` wins outright every single time — there is no write ratio in this sweep where it loses to `CanonicalStore` or to `SoaStore`.** The margin over the next-best alternative ranges from **1.8× (smallest, at 90% writes / 1,000 records) to 178.6× (largest, at 90% writes / 1,000,000 records vs. AoS)** — the closest call in the entire sweep is still a clear win, not a near-miss. ## Durability

**Separate from, and does not alter, any section above.** Every workload above is purely in-memory — nothing survives a process restart. This section asks a different question: given `CanonicalCachedStore` as the recommended backend (per every verdict above), what does it cost to make its writes actually durable, and which of several reasonable durability designs is worth keeping? Per the task that motivated this section, **only `CanonicalCachedStore` gets persistence** — `AosStore`/`SoaStore`/`CanonicalStore` remain untouched, purely in-memory baselines throughout this crate; nobody would deploy them, so building persistence for them would be pure scope creep. Eight variants were built and benchmarked (`src/durability/*.rs`, `benches/durability.rs`), split into two tiers of rigor:

- **Tier 1** (full implementation, correctness-tested, full three-size benchmarks): **(1) WAL fsync-per-write**, **(2) WAL buffered/no-fsync**, **(3) snapshot canonical-only with rebuild-on-load**, **(4) snapshot save-as-is**, **(5) hybrid periodic-snapshot-plus-WAL** with cutoff-sequence-number-based partial replay.
- **Tier 2** (lighter proof-of-concept, comparable numbers, explicitly not production-hardened — see each variant's own scope-down note): **(6) mmap-backed ages** (only the mutable `age` field lives in a memory-mapped file), **(7) LSM-tree style** (memtable + WAL + immutable flushed files, **no compaction — flagged as future work**, not silently skipped), **(8) `redb`**, an off-the-shelf embedded engine, chosen over `sled` for its ACID-transactions-from-the-start design and lack of `sled`'s long-standing crash-safety caveats.

**New dependencies, flagged explicitly (first added since this crate's inception)**: `serde` + `bincode` for snapshot/WAL (de)serialization (`bincode` chosen over `serde_json` — this is a benchmark harness, not a tool whose on-disk files need to stay human-readable, and one binary format is one fewer thing to keep consistent across 8 variants); `memmap2` for variant 6; `redb` for variant 8. Each is justified inline in `Cargo.toml`.

### Methodology

- All 8 variants implement `DogStore`, so they plug into the same generic-benchmark pattern every other workload in this document uses. `benches/durability.rs` defines two *local* traits (`DurableVariant`/`Checkpointable`, not part of this crate's public API) purely to normalize the 8 variants' differing `create`/`open`/`checkpoint`-or-`flush` signatures for iteration — see that file's module docs for why the native signatures don't already agree on one (e.g. variants 3/4's `open` takes only a path, since the persisted file is itself the canonical source of truth; `redb` has no separate checkpoint operation at all).
- Three metrics, matching the task's own framing: **per-write overhead** (`durability_per_write` — `update_age` cost, store built once outside the timed region, same convention as this document's other `update_age` numbers), **checkpoint/flush cost** (`durability_checkpoint` — cost of one explicit checkpoint/flush call after 1,000 pre-applied writes), **load/replay/startup cost** (`durability_load` — cost of `open`ing a store whose on-disk path already reflects 1,000 prior writes, built and finalized once outside the timed region; `b.iter_batched`/`BatchSize::PerIteration` keeps the per-iteration `records`/`edges` clone — `open` takes them by value — out of the timed measurement, since `open` itself is what's under test, not cloning the input dataset).
- `redb` (variant 8) is **intentionally absent from the checkpoint table** — it doesn't implement the local `Checkpointable` trait, because it has no separate checkpoint operation to benchmark: every `update_age` call is already its own independently committed transaction. This is a compile-time omission (the trait bound simply excludes it), not a runtime skip, matching the task's "if a metric doesn't map, don't force it" instruction.
- Same three dataset sizes (1K/100K/1M), same seed, same reduced Criterion sampling (`--warm-up-time 1 --measurement-time 2 --sample-size 20`), same machine caveat (this session's cloud Linux container) as every other section in this document.
- All numbers below are **median wall-clock time**, lower is better.

### Per-write overhead (`update_age`)

| Size | Baseline (non-durable) | wal_fsync | wal_buffered | snapshot_rebuild | snapshot_full | hybrid | mmap | lsm | redb |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 52.8 ns | 197.55 µs | 850.15 ns | 47.19 ns | 47.77 ns | 903.19 ns | **31.83 ns** | 926.47 ns | 233.00 µs |
| 100,000 | 68.3 ns | 213.57 µs | 901.73 ns | 59.89 ns | 61.60 ns | 865.99 ns | **43.03 ns** | 912.92 ns | 244.52 µs |
| 1,000,000 | 70.4 ns | 191.37 µs | 1.1429 µs | 62.60 ns | 62.45 ns | 1.2253 µs | **43.10 ns** | 1.2725 µs | 293.29 µs |

("Baseline" is `CanonicalCachedStore::update_age`'s own non-durable number, from the `## update_age` table above — included for scale, not a ninth durability variant.)

**Verdict: the eight variants split into four clean cost tiers, each explained by exactly how much I/O `update_age` actually performs.** In-memory-only variants (3, 4) cost the same as the non-durable baseline, within noise — expected, since they share `CanonicalCachedState::update_age` verbatim and touch disk only on an explicit checkpoint. WAL-append variants with no fsync (2, 5, 7) cost roughly 15–20× the baseline — one length-prefixed write to the OS page cache, no syscall-level synchronization. WAL-fsync and `redb` (1, 8) cost roughly 2,700–4,000× the baseline — both pay for a real, synchronous durability guarantee on every single call (an explicit `fsync`, or `redb`'s own ACID commit), and land in the same order of magnitude as each other despite very different implementations. **The standout result: mmap (6) is not just cheap, it's cheaper than the non-durable baseline itself** (31.8–43.1 ns vs. 52.8–70.4 ns) — because `MmapAgeStore::update_age` performs *one* indexed array write (into the mapped `age` region, via the position index), while the baseline's `update_age` performs *two* (the `records: HashMap<Uuid, DogRecord>` entry's `age` field, then the separate `age_cache: Vec<u32>` entry) — mmap's ages-only scope-down isn't just cheaper because it skips fsync, it's cheaper because it does structurally less work per write than the very backend it's benchmarked against. **This finding is about `update_age` only** — this benchmark never measured `MmapAgeStore`'s `get`/`scan_ages`/`same_breed`/`neighbors`. A later pass (`## Production recommendation`'s "Diagnosis and fix" subsection) benchmarked those for the first time, as part of diagnosing `ProductionStore`'s concurrency throughput, and found `scan_ages` specifically was 25–32× slower than the in-memory baseline before a since-applied fix — a genuinely separate finding about a different operation, not a contradiction of this one: `update_age` is still exactly this cheap, confirmed again directly in that later pass.

### Checkpoint / flush cost (after 1,000 pre-applied writes)

| Size | wal_fsync | wal_buffered | snapshot_rebuild | snapshot_full | hybrid | mmap | lsm | redb |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 174.81 µs | 195.52 µs | 176.84 µs | 204.89 µs | 228.07 µs | **51.97 µs** | 99.19 µs | n/a |
| 100,000 | 23.957 ms | 24.945 ms | 20.862 ms | 24.878 ms | 23.855 ms | **55.29 µs** | 140.16 µs | n/a |
| 1,000,000 | 374.36 ms | 393.49 ms | 288.86 ms | 369.73 ms | 455.92 ms | **51.63 µs** | 138.43 µs | n/a |

**Verdict: checkpoint cost splits by exactly how much of the dataset each variant's checkpoint actually rewrites — no outlier once an implementation bug found during this pass is fixed.** wal_fsync/wal_buffered/snapshot_rebuild/snapshot_full/hybrid all persist the *full current state* (all `n` records) on every checkpoint, and it shows — cost scales with `n`, from hundreds of µs at 1K to hundreds of ms at 1M, all five now within a tight band of each other at every size (they're doing structurally the same "serialize everything, write it" work).

**Correction, applied this pass**: the numbers above already reflect a fix. Hybrid's checkpoint originally measured 1.17 s at 1M — roughly 3× its closest full-state-persisting peer — traced to `HybridStore::checkpoint` calling `self.state.clone()` before serializing (to build the `HybridSnapshot` value it writes), a full extra copy of the entire dataset that none of the other full-state variants performed. Fixed by serializing directly from `&self.state` through a borrowed mirror struct (`HybridSnapshotRef`) instead of an owned one — `&T`'s `Serialize` impl delegates to `T`'s, so the on-disk bytes are unchanged and `HybridStore::open`'s deserialization path needed no changes. The fix dropped checkpoint cost by 25–61% across all three sizes (338.9 µs → 228.1 µs at 1K; 43.5 ms → 23.9 ms at 100K; 1.17 s → 455.9 ms at 1M) with **zero change to correctness**: all 4 existing hybrid unit tests, including the cutoff-boundary snapshot-plus-partial-replay test, pass unchanged. Hybrid is now the *most* expensive of the five full-state variants at 1M (455.9 ms vs. 369.7–393.5 ms for its next-closest peers, ~16–24% higher) — a real but modest gap, plausibly the extra `Option<u64>` cutoff tag and `HybridSnapshot`/`HybridSnapshotRef` wrapper overhead, not the 3× structural problem the clone caused. Not investigated further — a ~20% gap on top of an already-small checkpoint cost isn't worth chasing the way the original 3× regression was. `benches/durability.rs`'s per-write benchmark for hybrid was also re-run to confirm the fix didn't touch `update_age` (it doesn't — the diff is scoped entirely to `checkpoint`, confirmed directly against the commit): the re-run's numbers move by ordinary run-to-run noise (754–915 ns vs. the original 866 ns–1.23 µs, no consistent direction across the three sizes), not a real effect, and the per-write table above is left as originally measured.

mmap and LSM's flush costs look dramatically cheaper and roughly flat across dataset sizes — **with an honest caveat, not a free structural win**: both only ever persist what was actually *touched* (mmap syncs only dirty pages; LSM's memtable only ever holds the distinct keys written since the last flush), and this benchmark's target-UUID rotation pool (`SAMPLE_TARGET_COUNT = 200`) means the 1,000 pre-applied writes land on at most 200 distinct keys at every dataset size, so the *touched* fraction of the dataset never actually grows with `n` here. The flat numbers above are real, but they measure "cost to persist ~200 dirty keys," not "cost to persist a checkpoint at this dataset size" — a workload that dirtied a size-proportional fraction of records would show these two variants' costs growing too, just from a lower starting point than the full-state variants (they'd never need to rewrite records nobody touched).

|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1,000 | 346.4 µs | 331.6 µs | 391.7 µs | 335.4 µs | 385.2 µs | 279.3 µs | **262.5 µs** | 874.5 µs |

| 1,000,000 | 1.465 s | 1.306 s | 845.7 ms | 1.338 s | 1.394 s | 606.8 ms | 571.4 ms | **552.4 ms** |

**Numbers above reflect a size-gated fix, applied this pass — see the bullet immediately below the mechanism explanation for what changed and why.**

**Correction, applied this pass: the previous verdict here — "every variant's `open` pays the same dominant cost, rebuilding the breed/adjacency/position indexes" — was wrong, and the numbers above (and the fix behind them) are the reason why.** A profiling pass (`src/durability/mod.rs`'s temporary `profile_reopen_1m` diagnostic, run under this crate's own `[profile.bench]` after correcting for cold-start measurement bias — see below) traced the *actual* code path each variant's benchmarked `open` takes, rather than assuming from "they land in a similar ballpark" alone:

- **`snapshot_full` — the specific question this pass set out to answer: no bug.** `SnapshotFullStore::open` deserializes the *entire* persisted `CanonicalCachedState` — including the breed/adjacency/position indexes — directly via `bincode::deserialize`; there is no rebuild step in the code at all, so there was nothing to "skip" incorrectly. The reason it doesn't look cheaper than a genuine rebuild: deserializing a `HashMap`-heavy structure via `serde`/`bincode` does the *same* per-entry hash-and-insert work a manual rebuild loop does (there's no bulk-load shortcut for `HashMap`, unlike a flat `Vec`) — measured at 1M, `bincode::deserialize` alone (1.275 s) and a from-scratch rebuild via `CanonicalCachedState::new` (1.274 s) are, after correcting for warm-up bias, **statistically indistinguishable**. "Save-as-is" genuinely uses what it persists; it just doesn't save the cost it was expected to.
- **The bigger finding: `benches/durability.rs`'s own `run_load` calls `finalize()` (→ `checkpoint()`) before timing `open`, so most variants aren't measuring "rebuild" at all.** For `wal_fsync`/`wal_buffered`/`hybrid`, that pre-load `checkpoint()` writes a full base/snapshot file — so their benchmarked `open` takes the *deserialize an existing snapshot* branch (identical in kind to `snapshot_full`'s), not the *build `CanonicalCachedState::new` from records/edges* branch their own module docs describe for a true first-ever start. Verified directly (not assumed): the diagnostic confirmed `base.bin` exists before `WalBufferedStore::open` runs in this exact benchmark sequence. Only two shapes of "genuine rebuild from records/edges" are actually exercised by `durability_load` as it's currently written: **`snapshot_rebuild`** (its on-disk format is canonical-only by design, so `open` always calls `CanonicalCachedState::new` after deserializing a small `{records, edges}` blob) and **`mmap`/`lsm`/`redb`** (all three persist only `age`, so their `open` always rebuilds the breed/adjacency/position indexes from the externally-supplied `records`/`edges`, via each variant's own `build_indexes`). The original "every variant pays the same rebuild cost" conclusion was really "four variants happen to all be measuring the same deserialize operation, and the other four happen to cost about the same as that deserialize operation" — true in effect, wrong in mechanism.
- **The fix, applied to the four variants that do genuinely rebuild:** `CanonicalCachedState::new` (`src/durability/mod.rs`) and the three Tier 2 `build_indexes` functions (`mmap_store.rs`/`lsm_store.rs`/`embedded_store.rs`) each split into two provably independent phases — everything keyed by `records` (breed/position index, age cache, the records map) touches only `records`; the adjacency index touches only `edges` — with no merge step needed to combine them. Parallelized via `std::thread::scope` (stdlib, no new dependency; `rayon` would be overkill for a plain two-way split with nothing left to subdivide). No variant's `create`/`open` call signature changed — this is entirely internal to four already-tested functions, verified by the full existing test suite passing unchanged (108/108, run 3× to rule out a scoped-thread race).
- **Result: exactly the four variants the diagnosis predicted would move, moved — and by a lot, at scale.** At 1M, `snapshot_rebuild`/`mmap`/`lsm`/`redb` dropped 25–47% (1.622 s → 1.034 s; 1.305 s → 778.9 ms; 971.5 ms → 730.8 ms; 987.8 ms → 676.0 ms); at 100K the same four dropped 40–48%. The other four (`wal_fsync`/`wal_buffered`/`snapshot_full`/`hybrid`) moved by single-digit percentages in no consistent direction — noise, not a code effect, exactly as expected since their measured `open` never touches the parallelized functions. `hybrid`'s 1M number needed the same noise check `scan_ages` established earlier in this document: the first re-run showed a *statistically significant* +14% change (1.370 s → 1.564 s, p < 0.05) despite `HybridStore::open`'s code being completely untouched by this fix; two more runs came back at 1.399 s and 1.431 s (the third labeled "within noise threshold" by Criterion itself) — the sign flipped between runs, confirming noise, not a regression. The table above reports the median of those three runs.
- **Follow-up fix, applied this pass: the 1,000-record regression above is gone — a measured, size-gated threshold, not an engineered-around guess.** The prior pass reported it plainly rather than hiding it (`snapshot_rebuild` +19%, `mmap` +18%, `lsm` +26% slower at 1K, since spawning an OS thread costs tens of microseconds — more than the entire serial workload at that size takes to run) and flagged a size threshold as the natural fix without building one. This pass measured where the real crossover sits rather than picking a round number: two independent, warm-up-corrected 9-sample comparisons of sequential vs. parallel construction at 500/800/1,000/1,200/1,500/1,800/2,000/3,000/5,000 records agreed that ≤800 records reliably favors sequential and ≥1,500 reliably favors parallel, with 1,000–1,200 landing as a genuine coin-flip between the two runs — not a clean number, as expected going in. `PARALLEL_CONSTRUCTION_THRESHOLD = 1,500` (`src/durability/mod.rs`, one constant, shared by all four sites) sits at the confidently-parallel edge of that range, erring toward the known-safe sequential path through the ambiguous band. Below it, `CanonicalCachedState::new` and the three Tier 2 `build_indexes` functions now fall back to `*_sequential` — the original, pre-parallelization code, kept verbatim, not rewritten. **Result: the 1,000-record regression is gone.** `snapshot_rebuild`/`mmap`/`lsm`/`redb` at 1K now land at 391.7 µs / 279.3 µs / 262.5 µs / 874.5 µs — at or below their original pre-parallelization numbers (360.9 µs / 281.0 µs / 264.5 µs / 1.060 ms), not the regressed ones. Verified via the full existing test suite (108/108, unchanged — the test fixtures' 3-record datasets already exercise the new sequential path, since they're far below the threshold) before rebenchmarking.
- **A confound worth naming honestly, not folded into the fix's credit: this rebenchmark run landed on a machine state that was broadly faster than the prior one, independent of any code change.** At 100K/1M, all *eight* variants moved down 15–30% from the prior pass's numbers — including `wal_fsync`/`wal_buffered`/`snapshot_full`/`hybrid`, whose exercised `open` code path is completely untouched by this threshold (records.len() there is 100,000/1,000,000, both far above 1,500, so the gate is a no-op — the exact same parallel code runs before and after this fix at those sizes). A uniform shift across variants whose code didn't change is session/environment drift (shared cloud host, not this crate's logic) — the same category of effect this document's `scan_ages` and `hybrid` noise diagnoses already established for this exact environment. The **relative** story — `snapshot_rebuild`/`mmap`/`lsm`/`redb` sharply faster than `wal_fsync`/`wal_buffered`/`snapshot_full`/`hybrid` at 100K/1M, all four still far below their original pre-parallelization numbers — is unaffected and still the real, attributable result of the parallelization fix itself.
- **Practical consequence for the recommendation**: `redb`'s reopen cost at 1M (552.4 ms) is now clearly the fastest of any variant, `snapshot_rebuild` (845.7 ms) is now meaningfully faster to reopen than `snapshot_full` (1.338 s) rather than statistically tied — a new, additional reason (beyond the corruption-self-correction argument already made) to prefer `snapshot_rebuild` if a WAL-less design is chosen. `mmap`/`lsm` (606.8 ms / 571.4 ms) also pull further ahead of `wal_fsync`/`wal_buffered`/`hybrid`/`snapshot_full`'s ~1.3–1.5 s band. None of this changes which variant tier wins for a given loss-window requirement (see the Recommendation below) — it sharpens the load-time margins within tiers that were already established, it doesn't reverse them.

Not a benchmark — a comparison built from the per-write and checkpoint numbers above (100K-record dataset, representative middle size; the relative story holds at 1K/1M too, per those tables). "Guaranteed recoverable" means: on disk, provably surviving *this process* dying at any point after the batch finishes.

**This is the durability-vs-cost tradeoff the whole exercise exists to make concrete.** WAL-fsync and `redb` pay continuously and expensively (~200–250 ms to durably absorb 1,000 writes) but have *zero* loss window, ever. The buffered-WAL family (wal_buffered, hybrid, lsm) pay three orders of magnitude less (sub-millisecond) for a loss window bounded by the OS's own write-back cadence rather than this crate's own choices — a real, if usually small and non-app-controlled, gap. Snapshot-alone (rebuild, full) is cheapest per write by a further order of magnitude — but that's a deferral, not a saving: the entire batch, plus everything since the prior checkpoint, sits fully at risk until an explicit, dataset-sized-cost checkpoint closes the window. mmap is the one variant that gets *both*: near-free writes (cheaper even than the non-durable baseline, per the per-write table above) and, when durability is actually forced, the cheapest explicit step of any variant in this document by two to three orders of magnitude — because it only ever has to sync the one field that changed.

### Recommendation

**No single variant is "the" answer — the recommendation depends on which loss window is acceptable, matching the pattern the rest of this document has already established (a verdict per workload, not one overall winner).**

- **If the requirement is zero data loss with the simplest possible correctness story**: **`redb` (variant 8) over hand-rolled WAL-fsync (variant 1).** Both deliver the same guarantee (every write durable before it returns) at effectively the same measured cost (~230–295 µs vs. ~190–215 µs per write — same order of magnitude), but `redb` gets there with no hand-written WAL format, torn-write handling, or checkpoint logic at all — the task's own "should be the least code of any variant" framing for this variant holds up in the numbers, not just in line count.
- **If a small, OS-bounded loss window is acceptable in exchange for ~1,000× cheaper writes**: **WAL buffered (variant 2) over Hybrid (variant 5), for this crate's specific shape — though the margin is narrower than it first looked.** Hybrid's checkpoint-cost regression reported earlier in this section was a real implementation bug (an avoidable `state.clone()`), now fixed; with it fixed, Hybrid's checkpoint (455.9 ms at 1M) is no longer a 3× outlier, just the priciest of five full-state variants clustered within ~20% of each other. Even so, the recommendation doesn't flip: Hybrid's whole premise — bounding *replay* cost via periodic snapshots — still doesn't pay for itself here, because in this benchmark's specific write pattern (1,000 writes, one checkpoint) both variants' `open` ends up deserializing a full pre-built snapshot either way (see the corrected load section above — `WalBufferedStore::open` and `HybridStore::open` both take the deserialize branch once a checkpoint exists, not a rebuild-from-records branch), so Hybrid's bounded-replay design isn't even exercised here, let alone paying for its complexity. Hybrid remains architecturally sound and correctly tested (the cutoff-boundary replay test is real and passes); a workload with a much larger WAL between checkpoints — where the bounded-replay design would actually have something to bound — is the more informative case to revisit this recommendation on (see Open Questions).
- **If the mutation pattern genuinely matches "one small field changes, everything else is static" (which this crate's `age` field does)**: **mmap (variant 6) is the standout result of this whole pass** — cheaper per write than the non-durable in-memory baseline, the cheapest explicit durability step of any variant by two to three orders of magnitude, and (after the reopen-parallelization fix, now size-gated — see the load section above) among the fastest to reopen too (606.8 ms at 1M, down from 1.305 s pre-fix). This is not a general-purpose recommendation — it works specifically because only `age` needed to be mapped, per its own scope-down — but for exactly the shape this crate has, it's hard to beat.
- **Between the two snapshot-alone variants**, if a design without any WAL is chosen at all: **rebuild (variant 3) over full (variant 4) — and the case is stronger after this pass's reopen fix than it was originally.** Rebuild's checkpoint is marginally cheaper (20.9 ms vs. 24.9 ms at 100K); it self-corrects a future index-corruption bug on every load, where full would faithfully persist and reload the same corruption forever (see `snapshot_full.rs`'s own module docs); and — new finding — rebuild is now meaningfully *faster to reopen* too (845.7 ms vs. 1.338 s at 1M, after parallelizing `CanonicalCachedState::new`'s two independent construction phases, now size-gated so small datasets don't pay a regression for it), where before this pass the two were statistically tied on load time. Full's only advantage (skipping a rebuild step that turned out to cost about the same as its own deserialization anyway — see the load section above) isn't worth giving up rebuild's safety net and now-faster reopen for.
- **LSM (variant 7) is not recommended beyond this pass's proof-of-concept scope.** Its numbers look competitive here specifically because this benchmark's write volume and target-UUID rotation never exercise the one thing it's missing: compaction. Every flush adds one more file every future `get`/`scan_ages` must check, and a repeatedly-updated key leaves every old value on disk forever — a real, unbounded cost this benchmark's fixed 1,000-write, single-flush-per-checkpoint pattern doesn't surface. See Open Questions.

## Concurrency

**Separate from, and does not alter, any section above, including `## Durability`.** Every workload above this point assumes exactly one thread ever touches the store at a time. This section asks a different question: given `CanonicalCachedStore` as the recommended backend, what happens when real reader/writer threads share one instance, and which of several reasonable concurrency strategies is worth keeping? Per the task that motivated this section, **concurrency is built over the plain, non-durable `CanonicalCachedStore` shape only** — none of the four variants below persist anything to disk, and none is paired with a specific `## Durability` variant. Combining a concurrency strategy with a durability design (e.g. "a sharded, WAL-backed store") is a real, natural follow-up, but a second round: the two axes multiply into a much larger design space than either alone, and this pass establishes the concurrency numbers on their own footing first. Four variants were built (`src/concurrency/*.rs`, `benches/concurrency.rs`), split into two tiers of rigor matching `## Durability`'s pattern:

- **Tier 1** (full implementation, correctness-stress-tested, full benchmark sweep): **(1) global `RwLock`** — the whole `CanonicalCachedStore` wrapped in one `std::sync::RwLock`; **(2) sharded locking** — records partitioned across 64 independently-`RwLock`-guarded shards by UUID hash, `age` inline on each shard's own `DogRecord`; **(3) `dashmap`** — the canonical map swapped for `dashmap::DashMap`, an off-the-shelf internally-sharded concurrent map.
- **Tier 2** (lighter proof-of-concept, comparable numbers): **(4) actor / single-writer-thread** — one dedicated thread owns a plain, unsynchronized `CanonicalCachedStore` outright; every other thread sends `get`/`update_age`/`scan_ages` requests over an `std::sync::mpsc` channel and blocks on a per-call reply channel.

**New dependency, flagged explicitly**: `dashmap = "6"`, for variant 3 — the de facto standard sharded concurrent map in the Rust ecosystem, justified inline in `Cargo.toml`. No other new dependency: variant 1 uses `std::sync::RwLock` (not `parking_lot`, to avoid a dependency for what's meant to be the simplest baseline — see `global_rwlock.rs`'s module docs for the tradeoff); variant 4 uses `std::sync::mpsc` (not `crossbeam-channel` — a single fixed-destination request/response shape needs no `select!`).

**Scope boundary, shared by all four variants**: only `get`/`update_age`/`scan_ages` are exposed via a new `ConcurrentStore` trait (`&self` throughout, unlike `DogStore::update_age`'s `&mut self` — see `src/concurrency/mod.rs`'s module docs for why a new trait was needed at all). `same_breed`/`neighbors` aren't part of it — sharding those cleanly would require sharding the breed/adjacency indexes too, each shard boundary chosen so a query doesn't sometimes have to lock every shard, a genuinely bigger design problem this pass's scope doesn't call for (see `sharded.rs`'s module docs). Every workload this section benchmarks only ever exercises `get`/`update_age`/`scan_ages`, so this boundary costs nothing the benchmark needed anyway.

### Correctness: linearizability-style stress test (highest priority — same weight the original stale-cache test carried)

Each of the four variants is run against a flagship stress test (`run_concurrency_stress_test`, `src/concurrency/mod.rs`) before any throughput number is trusted: **16 threads**, each issuing **2,000** randomly interleaved `get`/`update_age` calls (50/50 split) against **one shared store instance**, all targeting a small, deliberately contended pool of **20 ids** drawn from a 500-record dataset — small enough relative to 16×2,000 operations that the same id is hit by many different threads many times over, not just occasionally. Every successful write is appended, immediately after it returns `Ok`, to an external, mutex-guarded log — a witness of the real order writes actually completed in. Once every thread joins, that exact recorded order is replayed *sequentially* against a fresh, single-threaded reference `CanonicalCachedStore` built from the same initial data, and the concurrent store's final value for every contended id must match the reference store's exactly (no lost update). A second, independent check — every value any thread ever *attempted* to write is also recorded, and each contended id's final value must be either the untouched initial value or something some thread genuinely attempted to write (no torn/corrupted read). This is a **linearizability smoke test, not a formal checker** (e.g. Jepsen/Knossos) — appropriate for a benchmark harness's own correctness gate, not offered as a formal proof; see `run_concurrency_stress_test`'s own doc comment for the one named residual imprecision (the log append happens just after, not atomically with, write completion — immaterial for same-id ordering, which is the only case that determines the final value, since every variant under test serializes access to a given id somewhere real around the store call itself).

**Result: all four variants pass outright — no lost updates, no torn reads, at 16 threads × 2,000 iterations each (32,000 operations per variant) against a 20-id contended pool.** `ActorStore`'s pass is structurally less interesting than the three lock-based variants' (a single owning thread can't race with itself — the property under test there is really "does the channel plumbing ever drop, duplicate, or misroute a request/reply," and it doesn't), but it's still exercised identically for consistency. Full crate test suite: 121/121 passing, including these 4 stress tests, 9 other concurrency unit tests (construction/read/write/scan sanity checks per variant, plus a sharding-specific "every shard is reachable" test), and every pre-existing test unchanged.

### Throughput methodology

Criterion's `b.iter` model times repeated calls to one closure on one thread — it has no built-in notion of "spawn N threads, run them concurrently, sum their throughput," which is the actual question this section asks. Rather than force that shape through Criterion, `benches/concurrency.rs` is a small custom (non-Criterion, still a `[[bench]] harness = false` target) harness: reuses `MixedWorkloadDriver` (`src/bench_support.rs`, the same blended `get`/`update_age`/`scan_ages` generator every workload in this document's mixed-workload sections already relies on — no new workload generator was built) via a new, additive `run_one_concurrent` method that drives a `ConcurrentStore` (`&S`, shared) instead of a `DogStore` (`&mut S`, exclusive); `run_one` itself and every benchmark using it are unchanged. Each worker thread owns its own independently-seeded driver (so each draws its own op sequence) against one shared, `Arc`-wrapped store instance; threads are synchronized to start together via a `std::sync::Barrier`, each performs a fixed 10,000 operations, and aggregate throughput is `total_ops / slowest_joined_thread_elapsed` — the *maximum*, not the average, across threads, since that's the real bound on when the whole batch is actually done.

- **Dataset sizes: 1,000 and 100,000, not 1,000,000.** Thread count is a new, second swept axis on top of size and write ratio; at this document's usual three sizes the full size×ratio×thread-count×variant matrix would be 3×3×4×4 = 144 cases. 1M is dropped specifically because it's the size where every other benchmark's story is already well-established at this document's scale, and repeating it a third time under an already-large second sweep axis wasn't judged worth roughly 50% more total runtime this pass. 1K and 100K still span two orders of magnitude — enough to see whether the qualitative thread-scaling story holds across scale (it mostly doesn't, in an informative way — see below).
- **Machine core count, reported since these numbers are meaningless without it: `std::thread::available_parallelism()` reports 4 cores** (confirmed independently via `nproc`/`/proc/cpuinfo`) on this session's cloud Linux container. **Thread counts 1/4/8/16 are swept exactly as specified, not scaled down to 4** — the 8- and 16-thread rows deliberately measure honest *oversubscription* (more runnable threads than hardware can run at once simultaneously), which is itself an informative data point about how gracefully each variant degrades under contention it can't actually parallelize away, not a mistake to correct for.
- Write ratios: the same 10%/50%/90% sweep `## Mixed read/write workload` established — and the same op-mix quirk applies here: at `write_ratio`, the remainder splits evenly between `get` and `scan_ages`, so 10% writes means **45% of every thread's operations are a full `scan_ages` call** (O(n) in record count), a fact that dominates the absolute numbers at 100,000 records far more than either the locking scheme or thread count does (see below).
- All numbers below are **aggregate operations/second across all worker threads**, higher is better. Winner(s) per row in **bold**.

### Cross-cutting observations

- **`dashmap` never wins a single configuration in this entire sweep** — it trails both global_rwlock and sharded at every size, write ratio, and thread count tested (by 4–9× at 1K, by up to ~70× at 100K vs. global_rwlock). It does scale with thread count the way sharded does (it's internally sharded too), just from a lower starting point — consistent with an off-the-grid, general-purpose concurrent map carrying more per-operation overhead (guard/reference-counting machinery) than either a raw `std::sync::RwLock<HashMap>` or the hand-rolled shard array, not investigated further at the individual-instruction level.
- **`actor` is bounded by its single worker thread's own serial processing rate, and that ceiling doesn't move with more client threads past about 4.** At 1K it plateaus around 95,000–104,000 ops/sec from 4 threads onward regardless of write ratio; at 100K it plateaus around 64,000–96,000 ops/sec (higher at higher write ratios, since scan_ages is rarer). Going from 1 to 4 threads gains roughly 2–2.7× at both sizes — enough concurrent requesters to keep the actor's channel pipeline full, closing the gap between "wait a full round-trip per call" (the 1-thread case) and "the actor is never idle between requests." Adding threads beyond that buys nothing: the ceiling is the one thread's own throughput, not the number of clients waiting on it.
- **8→16 threads is flat or noisy for every variant at both sizes** — the expected signature of oversubscription on a 4-core machine: once thread count exceeds real cores by 2×, adding more contending threads doesn't create more real parallelism, just more context-switching overhead competing for the same 4 cores.

### Recommendation

**No single variant is "the" answer — situational, matching the pattern `## Durability` already established (a verdict per configuration, not one overall winner). The bullets below are the container-run recommendation; the real multi-core follow-up above sharpens two of them — see the callout after this list.**

- **Default choice for most shapes tested here: global `RwLock`.** It's the fastest or clearly-fastest option in 5 of the 6 (size × write-ratio) configurations swept, at every thread count within each — including every 100K configuration, where its single lock's overhead turns out to matter far less than `CanonicalCachedStore`'s already-efficient packed data structures. Its one real weakness — aggregate throughput actively degrading, not just plateauing, as thread count rises — is worst specifically under sustained high-thread-count, write-heavy contention on a small dataset.
- **Sharded locking, specifically for that one weak spot**: a small dataset (this pass's 1,000-record case) under a write-heavy load (90%) with genuine multi-thread contention (≥4 threads) is the one tested configuration where sharding's thesis pays off, 2.4–2.7× ahead of global_rwlock. It is not a general win — at every other tested configuration, including every 100K case, it loses to global_rwlock, because sharding a `scan_ages`-heavy workload trades lock contention (which it fixes) for scan efficiency (which it loses, by giving up the packed-vector layout).
- **`dashmap`, as a "least code" tradeoff, not a throughput one**: it never wins a benchmark configuration in this sweep, so it isn't recommended when raw aggregate throughput is the deciding factor — but it is the only Tier 1 variant that required writing essentially no synchronization logic at all (see `dashmap_store.rs`), a real engineering-cost argument `## Durability`'s `redb` recommendation made in a similar spirit, just not a performance one here.
- **Actor / single-writer-thread**: recommended only when the access pattern genuinely fits one serial owner (e.g. a design that wants ordering guarantees, or an existing single-threaded store that can't be made internally thread-safe) and target aggregate throughput is comfortably under this pass's measured serial ceiling (roughly 65,000–105,000 ops/sec, depending on write ratio and dataset size). It does not scale by adding more actor threads — that would mean sharding the *actors* themselves, which converges back toward the sharded-locking design above.
- **Concurrency + durability, combined, remains the natural next round** — every variant above is purely in-memory; how these numbers change once each is paired with a real durability design (e.g. a sharded store where each shard also owns its own WAL) is unmeasured and out of scope for this pass, by design (see the scope note at the top of this section).

**What the real multi-core follow-up changes about this recommendation.** "Global `RwLock` by default, sharded only at 1K/90%-writes/high-thread-count" was the container's honest read of its own data, but it's a 4-core read. On real cores: sharded is competitive or ahead at 1K across *all three* write ratios once thread count reaches the machine's real core count, not just at 90%, and global_rwlock's 100K lead — while it never actually loses a tested cell — shrinks to as little as 1.2× at high write ratios and high real thread counts, not the comfortable 3.6–8.9× the container's oversubscribed rows suggested. **The practical recommendation for a small (~1K-record), high-thread-count, write-heavy deployment on genuinely many-core hardware should lean toward sharded locking, not global `RwLock`** — the opposite of the container-only default above for that specific shape. For 100K-record, read-or-mixed workloads, global `RwLock` remains the recommended default — it still wins every tested cell — but the margin is thin enough at high real core counts that this is worth re-measuring on hardware with meaningfully more cores than either environment tested here (32+) before treating it as settled at larger core counts.

**Superseded, in part, by the `baileyai` re-run above (32 real cores, the actual machine the task above asked to re-measure on).** The blanket "many-core hardware → lean sharded" call above turns out to be too broad — it was one real machine's data extrapolated to "more cores" in general, and a second real machine doesn't confirm it uniformly:

- **The 1K/90%-writes recommendation for sharded holds** — it's the one configuration every real machine tested agrees on — but the margin on `baileyai` (7.3–7.9×) is *narrower* than the Windows machine's (9.5–10.1×), so "the more cores, the wider sharded's win" specifically is not supported; the two real, non-container machines actually disagree on direction here.
- **The 1K/10%-writes part of "sharded across all three ratios once thread count reaches real core count" does not hold on `baileyai`** — global_rwlock wins that configuration at 32 and 64 threads, reversing the Windows machine's own 24/48-thread crossover. Recommending sharded at 1K/10%-writes on many-core hardware, based on the Windows-only pass, would have been wrong for `baileyai`.
- **The 100K/90%-writes margin did keep shrinking as the Windows-only pass predicted** — down to 1.03–1.05× on `baileyai`, the closest yet to a flip — so that specific prediction (not the general "more cores → wider sharded win" one) held up.
- **Revised guidance**: recommend sharded locking specifically for **1K-record, write-heavy (≥50% writes), multi-thread** deployments — that's the shape confirmed across all three real machines tested, container included, even though the exact margin varies by machine. Do not extend "many-core hardware favors sharded" to read-heavy (10%-writes) workloads at any dataset size tested — `baileyai`'s data contradicts that generalization directly. For 100K, global `RwLock` remains the default at every write ratio and every thread count tested on any of the three machines; treat the 90%-writes/high-thread-count cell as genuinely close to a coin flip on sufficiently many-core real hardware, worth re-measuring again if a fourth, still-larger real machine becomes available, rather than as settled in either direction.

## Production recommendation

**Six rounds of empirical work above all point at one combination: `CanonicalCachedStore`'s architecture, made durable via mmap (variant 6, `## Durability`), made safe for concurrent access via one global `RwLock` (variant 1, `## Concurrency`).** This section wires that combination into one new type, `ProductionStore` (`src/production.rs` — `RwLock<MmapAgeStore>`, reusing both closed pieces directly), verifies it as a composed stack for the first time, and reports its own numbers. See `docs/decisions/ADR-0008-production-default.md` for which round justified each layer and why it's `RwLock<MmapAgeStore>` rather than three literally nested types. This section doesn't repeat the durability or concurrency sections' own numbers — see `## Durability` and `## Concurrency` above for those.

**Revision note (this section only)**: the first pass of this section found a large, thread-count-invariant throughput tax at 100K records (6–32× slower than the plain in-memory recommendation) and reported it as an open question — a plausible but unverified "structural mmap read cost." ### Flagship integration test: mmap durability and `RwLock` concurrency, run together for the first time

Every number in `## Durability` and `## Concurrency` was measured with the *other* axis held at its simplest case: durability variants are single-threaded, concurrency variants are purely in-memory. Nothing had tested both together before this pass. `tests/production_integration.rs::concurrent_writers_survive_a_drop_and_reopen_with_no_lost_updates` closes that gap: two phases of 16 threads × 2,000 iterations each of interleaved `get`/`update_age` calls against a shared `ProductionStore` (500-record dataset, 20 contended ids — same shape as `run_concurrency_stress_test`), separated by a genuine `drop` + `ProductionStore::open` reopen from disk (not just an in-process flush). **Result: passes outright.** The full two-phase write log (64,000 attempted operations across both phases), replayed sequentially against a fresh reference `CanonicalCachedStore`, matches the reopened store's final state exactly for every contended id (no lost updates, no torn reads) — and a *third*, fresh open, made only after the second phase's store handle was fully dropped, sees every write from both phases, confirming the data genuinely reached disk rather than surviving only in that process's page cache. Full crate test suite: 128/128 passing (up from 121/121), including this test and 6 new `src/production.rs` unit tests (create/open/flush round-trip, `DogStore`/`ConcurrentStore` behavior, both `From` impls, and `run_concurrency_stress_test::<ProductionStore>()` reused verbatim).

### Diagnosis and fix: the 100K concurrency tax was `scan_ages`'s read loop, not durability

The first pass of this section found `ProductionStore` 6–32× slower than the plain in-memory `GlobalRwLockStore` at 100K, flat across thread counts, and called it a "per-operation cost floor" without pinning down which operation or why. This follow-up pass diagnosed it directly rather than leaving it as a guess.

**Leading hypothesis, tested first: does `ProductionStore` call `msync`/flush synchronously on every write?** No. Read directly: `DogStore::update_age`/`ConcurrentStore::update_age` on `ProductionStore` call straight through to `MmapAgeStore::update_age`, which does one indexed byte-slice write and returns — `flush()` is a separate method, never invoked automatically from either write path. Confirmed with numbers, not just code reading: an isolated, same-machine, same-process, single-threaded comparison (`MmapAgeStore` vs. `CanonicalCachedStore`, no `RwLock`, no mixed workload) found mmap's `update_age` **cheaper** than `CanonicalCachedStore`'s at both 1K and 100K (11.2 ns vs. 18.9 ns; 13.0 ns vs. 24.2 ns) — consistent with, not contradicting, `## Durability`'s original "mmap writes are free" finding. The write path was never the problem.

**The isolated comparison also measured `get` and `scan_ages` directly, and found the real cause**: `scan_ages` was **24.8× slower at 1K and 32.3× slower at 100K** (`get` was a modest 1.45–1.57× slower, not investigated further). Plugging these three isolated per-op costs into the write-ratio mix that `benches/concurrency.rs` actually runs (e.g. 100K/50% writes: 25% `get` + 25% `scan_ages` + 50% `update_age`) predicts ~24,375 ns/op — the concurrency benchmark's own pre-fix number was 24,360 ns/op, a near-exact match. `scan_ages` alone accounted for essentially all of the measured tax. This also resolves cleanly, not as a contradiction: the original durability round never benchmarked mmap's `get`/`scan_ages` at all (its own benchmark measured per-write/checkpoint/load only), so there was no prior "mmap is fast at reads" claim this pass's numbers overturn — just an untested path that turned out to be slow.

**Mechanism**: `MmapAgeStore::read_age`/`scan_ages` (`src/durability/mmap_store.rs`) read one 4-byte mapped position at a time via four individually-indexed (individually bounds-checked) byte reads, then `.collect()`s the results one element at a time — instead of a single bulk `chunks_exact(4)` pass over the mapped region. A prototype bulk read of the identical bytes measured 18–26× faster than the original loop, closing `scan_ages`'s gap to `CanonicalCachedStore` from ~25–32× down to ~1.2–1.3×.

**Fixed**: `read_age` and `scan_ages` rewritten to use `chunks_exact(4)`/slice conversion instead of per-byte indexing — one bounds check per element (`read_age`) or one pass with no per-element loop overhead (`scan_ages`), rather than four bounds checks plus a function-call frame per element. Safe code throughout, no `unsafe`, no new dependency. `update_age`/`flush`/the durability guarantee itself are untouched — this is a read-path-only change. All 128 tests pass unchanged, including `MmapAgeStore`'s own 3 unit tests and the flagship integration test above.

**Real-world effect, measured**: `scan_ages` dropped from 801.2 ns/71.35 µs/711.1 µs (1K/100K/1M) to **56.16 ns/4.129 µs/58.35 µs — 12–17× faster at every size**. Every table below reflects the numbers *after* this fix.

### Recommendation

**Use `ProductionStore` as the default, without the reservation the pre-fix numbers would have called for.** It is the composed form of the recommendation every one of the six prior rounds pointed toward, verified as a working stack (not just three separately-correct pieces) by the flagship integration test above, and — after the `scan_ages` fix diagnosed and applied this pass — its throughput is within a normal margin of the plain in-memory baseline at every tested size, write ratio, and thread count, often ahead of it.

- **There is no longer a scale- or read-ratio-dependent corner where `ProductionStore`'s durability tax is large.** The 100K/read-heavy tax this section originally reported and flagged as a real deployment risk was a specific, now-fixed inefficiency in `MmapAgeStore::scan_ages` — not an inherent cost of the durability guarantee itself. Nothing in this pass's data calls for avoiding `ProductionStore` on read-heavy or large-dataset grounds anymore.
- **The narrow corners named in `## Concurrency`'s own recommendation** (sharded locking for small, write-heavy, high-thread-count deployments) **still apply** if that specific shape doesn't need durability — `ProductionStore` is the default for "storage + durability + concurrency, all three, together," not a blanket replacement for every situational pick this document has made along the way.
- **Every other backend, durability variant, and concurrency strategy remains in the tree** — the evidence this recommendation is built on, not dead code. `src/lib.rs`, `README.md`, and `docs/architecture/SYSTEM-ARCHITECTURE.md` now lead with `ProductionStore` and frame the rest as benchmarked alternatives (see ADR-0008 for why a physical `src/comparisons/` reorganization was considered and deferred in favor of this docs-only lead).

### `MmapAgeStore` identity-keying fix

A real, latent correctness bug was found and fixed after the `## External database comparison` section above was written, motivated by the owner asking how `ProductionStore`'s own `.mmap` file compares to SQLite's/DuckDB's genuinely portable database files. It doesn't: `MmapAgeStore::open` rebuilt its `Uuid -> array position` index fresh from whatever order the caller-supplied `records`/`edges` happened to arrive in on that specific call, and trusted that array position N in the file still held position N's age from `create` time. Nothing in the file recorded which record an age actually belonged to. No caller anywhere in this crate's own test/bench suite ever triggers this (every one of them supplies the identical generator output, in the identical order, at both `create` and every later `open`), but nothing about `ProductionStore`'s public contract ever required that — a real caller supplying `records` in a different order between a `create` and a later `open` would have silently misattributed ages between records, no error, no panic. See `src/durability/mmap_store.rs`'s own module doc comment for the full account, and its `reopening_with_reordered_records_reads_the_correct_age_per_id` test for the direct regression coverage.

**First attempt: a straight port of `crate::generic::mmap_store::GenericMmapStore`'s already-proven fix** (the identical bug, found and fixed there earlier this session — see `## Generic schema library` below) — a versioned header plus one interleaved `[id: 16 bytes][age: 4 bytes][commit marker: 1 byte]` slot per record, reconciled by id on `open` instead of by position. Correct, but it broke `scan_ages`'s existing `chunks_exact(4)` bulk read (the fix behind this same section's own "Diagnosis and fix" above, 12-17× faster than a naive per-position loop) — that optimization depends on the mapped region being *exactly* a flat, homogeneous `[u32]` array, and an interleaved slot isn't one. Measured directly, not assumed:

| Size | Before | Row-oriented (interleaved) | Slowdown |
|---|---:|---:|---:|
| 1,000 | 147.7 ns | 322.3 ns | 2.2× |
| 100,000 | 13.94 µs | 74.24 µs | 5.3× |
| 1,000,000 | 299.5 µs | 1.838 ms | **6.1×** |

This directly reversed this document's own just-published headline external-database finding: with `scan_ages` at 1.838 ms, `ProductionStore` became *slower* than DuckDB's unchanged 1.156 ms at 1M records — "DuckDB closes to within 3.3×" became "DuckDB wins," the opposite of what `## External database comparison` reported. Every other workload (`get`, `update_age`, `same_breed`, `neighbors_one_hop`/`neighbors_two_hop`) stayed flat, within normal run-to-run noise — the regression was isolated entirely to `scan_ages` and the mixed-workload benchmarks that include it.

**Second attempt, accepted: a columnar layout instead of row-oriented.** Rather than accept that regression (unacceptable for this crate's own flagship read-side workload) or abandon the correctness fix, the on-disk format was redesigned around the actual constraint: `scan_ages` needs ages contiguous, and identity-keying needs ids recorded somewhere. Resolution: three separate, contiguous regions after the header — every id, then every age, then every commit marker, each its own flat array in the same record order — so `scan_ages`'s fast path goes back to a pure `chunks_exact(4)` over *only* the ages region. The real cost moved elsewhere: a columnar layout can't append one new record cheaply in place (it would need inserting bytes into three separate, non-adjacent regions), so a record with no persisted entry now triggers a full, crash-safe rewrite (write-to-temp-then-atomic-rename, never in-place truncation) instead of a cheap `O_APPEND` — a path nothing in this crate's own benchmark suite or test-suite-adjacent call sites ever exercises in the common case (every one of them supplies the same record set at every `open` as at `create`), so it costs nothing in any number below. See `src/durability/mmap_store.rs`'s own module doc comment for the full design and the crash-safety reasoning.

| Size | Before | Columnar | vs. before |
|---|---:|---:|---:|
| 1,000 | 147.7 ns | 207.1 ns | 1.4× |
| 100,000 | 13.94 µs | 18.24 µs | 1.3× |
| 1,000,000 | 299.5 µs | 338.6 µs | **1.1×** |

Mixed-workload numbers (which blend `scan_ages` calls with `get`/`update_age`) track the same pattern — close to flat at 90%-writes (where `scan_ages` is a small fraction of calls), a real but modest 1.1-1.7× at 10%/50%-writes (where it dominates), a world apart from the row-oriented attempt's up to 6.9× there.

**Verdict against the external-database comparison, re-measured (same 4 systems, only `ProductionStore`'s own numbers changed — SQLite/Postgres/DuckDB untouched by this fix, not re-run):**

| | `scan_ages` @ 1M |
|---|---:|
| `ProductionStore` (before this fix) | 347.4 µs |
| `ProductionStore` (row-oriented, rejected) | 1.691 ms |
| `ProductionStore` (columnar, accepted) | 308.7 µs |
| DuckDB (unchanged) | 1.156 ms |

**The columnar fix doesn't just close the gap the row-oriented attempt opened — it restores the original headline finding almost exactly, DuckDB now 3.7× behind `ProductionStore` at 1M (was 3.3× before this fix), 43× behind at 100K (was 41.8×).** `## External database comparison`'s own tables above are left as originally measured, per this document's own established practice of not rewriting a prior pass's numbers in place — this paragraph is the record of what changed and why the verdict there still holds. **Recommendation unchanged**: use `ProductionStore` as the default; the identity-keying fix is a real, accepted correctness improvement with a real but small (1.1-1.4×) `scan_ages` cost, not a reason to reconsider it.

## Generic schema library

**This section is genuinely separate from everything above it**: it doesn't compare AoS/SoA/Canonical/Canonical+cache, and it isn't `Dog`-specific. Four validation spikes (Dog-overhead measurement, associated-type-ambiguity diagnosis, macro-generated forwarding, directed-relation-generalization measurement — none of them touched `RESULTS.md`, by design, since spike code was explicitly kept isolated from this document until the design was promoted) resolved every risk `docs/design/GENERIC-SCHEMA-DESIGN.md` §4 named. This pass promotes that validated design into `src/generic/` — a real, public generic record/schema/query library, generic over any `Record`-implementing type instead of hardcoded to `Dog` — and builds the piece the spikes never had: [`crate::generic::production::GenericProductionStore`], the generic equivalent of `ProductionStore`, wired to the same mmap durability and global `RwLock` concurrency. See ADR-0009 (now Accepted) and `docs/specifications/storage/STORAGE-012-generic-schema-library.md`.

### Reference implementation: `Order`/`Customer`

Promoted from spike/prototype status to this library's real reference implementation (`src/generic/order_customer.rs`) — three `ScannableField`s (`Amount`, `CreatedAt`, `DiscountCents`), one `IndexedField` (`Status`), and a directed `ChildOf` relation to `Customer`. `crate::generic_spike::dog_impl` (`Dog`'s own generic trait impls) stays historical reference, not promoted further — `Dog` is a benchmark fixture, not a target domain for this arc.

### `GenericProductionStore<S>`: the generic equivalent of `ProductionStore`

[`GenericMmapStore<R, IndexMarker, ScanMarker>`] (`src/generic/mmap_store.rs`) is the generic, hand-fused analogue of `MmapAgeStore` — one equality index, one mmap-backed scannable field, the same one-durable-field scope `ADR-0009`'s §4.2 already flagged as the boundary of what mmap durability can do without a real redesign. [`GenericProductionStore<S>`] (`src/generic/production.rs`) wraps whatever composed generic stack `S` is (`GenericMmapStore` plus zero or more `Reversed`/`Symmetric`/`Indexed`/`Scanned` layers) in one `RwLock`, exposing `&self` inherent methods generic over whatever capability trait `S` implements — the same recipe `ProductionStore` uses, generalized. For `Order`/`Customer`: `Amount` is the one durable field (mirroring `Dog`'s `age`); `CreatedAt`/`DiscountCents` stay in-memory-only `Scanned` layers on top, reusing the `forward_scannable_pairs!`-generated forwarding impls unmodified (they're generic over whatever inner store type they wrap, so they don't care that the innermost layer is now mmap-backed instead of a plain `BaseStore`).

### Record-identity-keying fix: real, measured costs to `scan`/`open` — the table above is now stale

A later diagnosis pass found `GenericMmapStore`'s real fragility: each persisted slot held only a scannable value's raw bytes, addressed by `position * BYTE_WIDTH`, where `position` was whatever index a record happened to occupy in the caller-supplied `records: Vec<R>` at that specific `create`/`open` call — nothing in the file itself recorded which record a value belonged to. Reopening with `records` in a different order than at `create` time silently attributed position N's persisted value to whatever record now sat at position N: wrong data, no error, no panic. A follow-up fix pass closed it at the root: each slot now carries `(id, value)` — `R::Id` extended into `MmapFieldValue` (covering `Uuid`, the id type every domain in `crate::generic` uses) — and `open` reconciles every persisted `(id, value)` pair against the caller's `records` **by id**, not position, before trusting any of them. See `src/generic/mmap_store.rs`'s own module docs for the full account, including the explicit, deliberate behavior for a persisted id with no current record (dropped, file only ever grows) and a current record with no persisted entry (seeded from its own `scannable_value()` and appended, exactly like `create` would).

**This is not a free fix — measured directly, git-checkout-isolated before/after on the same machine, same session, same `--warm-up-time 1 --measurement-time 2 --sample-size 20` convention as the table above:**

| Operation | 1K | 100K | 1M | vs. the table above |
|---|---:|---:|---:|---|
| `get` | 80.4 ns | 93.9 ns | 98.1 ns | +5–8%, +3–7%, no significant change |
| `filter_eq` | 95.9 ns | 7.43 µs | 221.6 µs | unaffected (never touches mmap) |
| `children` | 49.3 ns | 60.5 ns | 66.9 ns | unaffected (never touches mmap) |
| `parent` | 68.9 ns | 107.4 ns | 81.5–98.1 ns | **+15–18%, +14–16%, +9–12%** |
| `update` | 38.3 ns | 49.5 ns | 51.2–53.4 ns | +6%, +4%, no significant change |
| `create` | 536.8 µs | 26.6 ms | 630.7 ms | no sig. change, **+13–15%**, no sig. change |
| **`scan`** | 339.6 ns | 104.0 µs | 1.256 ms | **~2.3× slower, ~3.6–4.4× slower, ~1.6–1.9× slower** |

**`filter_eq`/`children` are the sanity check on this methodology, not just an aside**: their code paths never touch `GenericMmapStore`'s slot layout at all (`filter_eq` reads the in-memory `index` map built from `records`; `children` reads `Reversed`'s own in-memory adjacency index) — and they show no real change, exactly as the fix's own scope predicts. That both real regressions below trace to code that *does* touch the new slot layout, and both unaffected operations that don't show nothing, is the strongest evidence these numbers are measuring the fix, not noise.

**`scan` (real, substantial — 1.6–4.4× depending on size)**: each slot is now id+value interleaved — a 16-byte `Uuid` prefix plus the 8-byte `i64` value, 24 bytes total, vs. the old 8-byte value-only layout. `scan`'s bulk `chunks_exact` fast path (kept for the common gapless case — see `GenericMmapStore::is_gapless`) still runs, but now strides through 3× the memory to extract the same values: a direct, structural consequence of co-locating identity with value in one slot, not a missed optimization. The two independent measurement passes that produced this table disagreed on the exact multiplier at 100K (3.6× vs. 4.4×) and 1M (1.6× vs. 1.9×) by a wider margin than this document's usual run-to-run noise — reported as a range rather than false precision, but both passes agree it's a real, substantial, multi-x regression at every size, not a rounding difference.

**`open` (real, substantial — 1.4–1.9×)**: exactly the cost the fix's own design predicts — `open` now reads every persisted slot into a `HashMap<Id, (position, Value)>` and reconciles it against the caller's `records` before trusting any position, replacing the old "map the file, trust array order" approach. This is the correctness guarantee's actual price, not an accident of implementation.

**`parent` (real, modest — 9–18%)**: goes through `GetById::get` → `read_value`, one extra offset computation (`position * slot_width + id_width` instead of `position * width`) per call — real and consistent across sizes, but an order of magnitude smaller than `scan`'s cost, since `parent` reads one slot, not every slot.

**`get`/`update`/`create` (negligible-to-modest, 0–15%, inconsistent significance across sizes)**: `get` pays the same per-call offset computation `parent` does; `update` is symmetric; `create` writes 3× the bytes per record (id+value instead of value-only) but at a size where disk/page-cache write throughput dominates more than compute, so the relative cost increase is smaller than `scan`'s read-side hit.

**Net verdict, stated plainly**: this section's original "no regression from spike to real implementation" claim no longer holds. `filter_eq`/`children` are genuinely unaffected; `get`/`update`/`create` carry a small, arguably-acceptable cost; `parent` carries a real but modest one; `scan`/`open` carry a real, substantial one (1.4–4.4× depending on operation and size) — this is the accepted, now-quantified cost of closing a silent-data-corruption bug, the same "report the real number, don't assume a correctness fix is free" discipline this document has applied to every prior fix (`## Generic schema library`'s own write-through fix below, at 43–88%; `Scanned::get`'s cost). Whether this cost is acceptable for `GenericMmapStore`'s intended use is a product decision this document doesn't make — see `tests/mmap_record_identity_keying.rs` for the correctness evidence and `src/generic/mmap_store.rs`'s own module docs for the full design account.

### A finding from wiring durability: write-through consistency needed a new trait method — and, in a follow-up pass, a second fix for the in-memory path too

Building `GenericMmapStore::get` surfaced something none of the four spikes exercised: it has to return a record whose scannable field reflects the *latest* `UpdateField::update` write — the same write-through consistency `CanonicalCachedStore::update_age` already has (it mutates both its canonical record and its cache). The original design's `ScannableField` trait had no way to write a new value back into a record generically. Fixed by adding `ScannableField::set_scannable_value` (`src/generic/traits.rs`) and using it in `GenericMmapStore::get` to merge the live mmap value before returning.

**This exposed a pre-existing gap in the purely in-memory composition, not introduced by this pass**: `GetById::get` on a store built purely from `BaseStore`/`Indexed`/`Scanned` (i.e. `DogGenericStore`/`OrderGenericStore`) did *not* write through — `Scanned::update` only mutated its own cache, never `BaseStore`'s records map, so `get` could return a stale value for a field `update` just wrote. None of the four spikes' tests happened to check `get` after an `update` call, so this went unnoticed until the durable path's own correctness requirements forced a closer look.

**Fixed in a follow-up pass, after diagnosing that the root cause is structurally different from the durable core's own gap.** `GenericMmapStore` is one hand-fused struct that merges two views it directly owns; `Scanned` is a separate struct layered on top of whatever actually owns the record (`BaseStore`, potentially several layers down) and has no way to reach down and mutate that owner's storage. The fix instead patches on the way *up*: `Scanned`'s `GetById` forwarding impl now takes the record `inner.get(id)` returns and overwrites its own field with the live cached value (reusing `set_scannable_value`) before returning it. When multiple `Scanned` layers stack (`Order`'s `Amount`/`CreatedAt`/`DiscountCents`), each layer patches only its own field as `get` unwinds, so the record is fully consistent by the time it reaches the caller — no change needed anywhere else (`Indexed`/`Symmetric`/`Reversed` own no `ScannableField` data to patch).

**A real, measured cost — checked, not assumed.** This adds one `HashMap` lookup per `Scanned` layer to every `get` call. Measured directly, same-session and back-to-back (stash-the-fix / no-fix / re-apply-the-fix, immediately re-run, to isolate the change from this shared environment's usual session-to-session drift): `benches/generic_spike.rs`'s `generic_get` on `Dog`'s single-`Scanned`-layer stack went from 35.8/54.3/55.4 ns to 67.5/77.7/80.9 ns at 1K/100K/1M — **roughly 43–88% slower**. `generic_scan_ages`, measured the same way, is unaffected (77.1→81.5 ns at 1K, 9.56→9.51 µs at 100K, 320→278 µs at 1M — all within ordinary run-to-run noise, not a real change, since `scan`'s own code path is untouched). This is the accepted cost of the correctness guarantee on a purely in-memory, no-mutable-field-durability path — not optimized away, since doing so would mean either caching the merged result (reintroducing a staleness question) or a bigger restructuring outside this fix's minimal-diff scope.

A regression test now guards against this recurring silently: `order_customer.rs`'s `get_reflects_a_prior_update_through_every_layer_of_the_in_memory_stack` writes through the innermost (`Amount`) and outermost (`DiscountCents`) `Scanned` layers and checks `GetById::get` reflects each write immediately, while confirming untouched fields on the same record are unaffected.

### Methodology

- Same dataset, same seed, same sizes as every other table in this document: `bench_support::build_dataset` (1,000 / 100,000 / 1,000,000 records, seed `20260824`, 50 breeds, `littermate_of` average degree 1.5), the same 200-UUID `RoundRobin` sample pool for point workloads.
- Schema creation and bulk data load happen once per (engine, size), outside the timed portion — same standard every in-repo backend's own construction already gets. SQLite/DuckDB load into a real on-disk file (not `:memory:`); Postgres loads via `COPY ... FROM STDIN`.
- Every query is prepared once per (engine, size) and reused across iterations — no per-call SQL parse/plan cost, matching how a `HashMap` lookup never re-parses anything either.
- `get`: `SELECT breed, age FROM dogs WHERE id = ?` against an indexed primary key. `scan_ages`: `SELECT AVG(age) FROM dogs` (Postgres needs an explicit `::float8` cast — `AVG()` over an integer column returns `numeric`, not `float8`, by default). Graph traversal: a `WITH RECURSIVE` query over `littermates(dog_id, littermate_id)` (loaded with both edge directions, indexed on `dog_id`), originally depth-bounded to 1 hop via `WHERE hop.depth < 1` in the recursive term (one-hop only, matching `neighbors_one_hop` above, not `neighbors_two_hop`) — extended to 2 hops (`WHERE hop.depth < 2` in the recursive term, `WHERE depth = 2` in the final `SELECT`) in a later addition, see `### Graph traversal, two-hop` below.
- Criterion run with the same reduced sampling this document's own first pass established for a container run (`--warm-up-time 1 --measurement-time 2 --sample-size 20`, vs. Criterion's defaults of 3s/5s/100) — kept explicit here rather than silently assumed equivalent to a full-rigor run. Machine: this session's cloud Linux container, same as most of this document's other passes.
- All numbers below are **median wall-clock time per call**, lower is better. Winner in **bold**.

**A real methodology bug was found and fixed during this pass, not glossed over.** The first `neighbors_one_hop` run showed Postgres jumping from 109.6 µs at 1,000 records to 152.9 ms at 100,000 — a ~1,400× cliff with no equivalent jump in `get`'s or `scan_ages`'s Postgres numbers, and not something any real structural cost of the query shape would produce. Investigated directly (not assumed to be noise): `EXPLAIN ANALYZE` against the same table state the benchmark had just built showed `pg_class.reltuples = -1` (COPY doesn't update planner statistics itself) driving a wildly wrong cost estimate for the recursive CTE (~93,000 estimated vs. ~260 real cost on the 100K-row table) — high enough to cross Postgres's default `jit_above_cost` threshold and trigger LLVM JIT compilation on *every single execution* of the prepared statement, not just the first. A direct, reproducible before/after check confirmed it: 53.1 ms execution time on the un-ANALYZEd table, 0.196 ms after running `ANALYZE` — a ~270× difference from one statement, no code or data change. `benches/external_db.rs`'s `postgres_load` now runs `ANALYZE` on both tables immediately after the bulk load (any real Postgres deployment does the same after a bulk load — skipping it would have been an unrepresentative gap in this benchmark's own setup, not an honest measurement of Postgres). All Postgres numbers below are from the corrected, post-fix run.

### `get` (full-record read by UUID)

| Size | production | sqlite | postgres | duckdb |
|---|---:|---:|---:|---:|
| 1,000 | **79.4 ns** | 2.920 µs | 89.36 µs | 438.9 µs |
| 100,000 | **91.1 ns** | 4.322 µs | 95.16 µs | 492.9 µs |
| 1,000,000 | **117.1 ns** | 8.051 µs | 97.39 µs | 529.3 µs |

**Verdict: `ProductionStore` wins decisively and by a wide, growing margin — 69× to 5,530× faster than the nearest-to-furthest external engine, depending on size.** This is exactly the access pattern its design is built for: an in-memory `HashMap` lookup with no query parsing, no serialization, no process/network boundary to cross. Among the three external engines, the ranking is stable across every size: **SQLite** (embedded, direct B-tree lookup, no network hop) beats **Postgres** (a real client/server round trip — its ~90–100 µs is essentially flat across sizes, consistent with loopback TCP/protocol overhead dominating over the trivial index lookup itself) beats **DuckDB** (430–530 µs, the slowest of the three at every size) — DuckDB's vectorized, batch-oriented execution engine carries real fixed per-query overhead that a single-row point lookup can't amortize, the expected cost of a columnar/OLAP engine on a workload it isn't built for.

### `scan_ages` (whole-table average-age aggregate)

| Size | production | sqlite | postgres | duckdb |
|---|---:|---:|---:|---:|
| 1,000 | **156.4 ns** | 50.00 µs | 191.6 µs | 311.9 µs |
| 100,000 | **14.43 µs** | 7.796 ms | 12.62 ms | 602.4 µs |
| 1,000,000 | **347.4 µs** | 69.78 ms | 56.26 ms | **1.156 ms** |

**Verdict: `ProductionStore` still wins outright at every size, but DuckDB is a genuinely different story from `get` — this is exactly the workload the task predicted it would be strong on, and it is.** At 1M records, DuckDB is only **3.3× slower than `ProductionStore`**, versus SQLite's 201× and Postgres's 162× — DuckDB's columnar, vectorized full-column aggregate is close to the same shape of work `ProductionStore`'s own packed-`Vec<u32>` age cache does (see `## get`/`## scan_ages` at the top of this document for why that packed layout wins this same workload against this crate's own row-oriented backends). At 100K, DuckDB (602.4 µs) is already dramatically ahead of both row-oriented engines (7.8 ms SQLite, 12.6 ms Postgres — a full table scan that grows with row count, exactly as expected for a row store with no columnar shortcut). **The honest nuance**: at 1,000 records, DuckDB is actually the *worst* of the three external engines (311.9 µs, slower than SQLite's 50.0 µs or even Postgres's 191.6 µs) — its per-query vectorized-execution setup cost doesn't pay for itself until the dataset is large enough, and the crossover where DuckDB overtakes SQLite happens somewhere between 1K and 100K, not at the smallest size. Postgres and SQLite both scale their aggregate cost roughly with row count, as expected for a real sequential scan; DuckDB does not, which is precisely its columnar design paying off.

### Graph traversal (`neighbors_one_hop` — depth-1 `WITH RECURSIVE` over an adjacency table)

| Size | production | sqlite | postgres | duckdb |
|---|---:|---:|---:|---:|
| 1,000 | **63.6 ns** | 10.27 µs | 109.6 µs | 1.708 ms |
| 100,000 | **73.3 ns** | 19.06 µs | 102.0 µs | 1.716 ms |
| 1,000,000 | **76.4 ns** | 25.56 µs | 99.12 µs | 1.770 ms |

**Verdict: `ProductionStore` wins overwhelmingly and by the widest margin of any workload in this section — 162× to 26,900× faster, depending on engine and size.** `DogStore::neighbors`'s in-memory adjacency index is a single `HashMap` lookup into a pre-built `Vec<Uuid>`; nothing built around SQL's general-purpose recursive-query machinery can approach that for a fixed, one-hop shape. Among the external engines: **SQLite** is again the strongest (10.3–25.6 µs, scaling mildly with size — a straightforward indexed B-tree lookup, the recursive-CTE wrapper costs it very little). **Postgres** sits in the middle and, after the `ANALYZE` fix above, is now flat and well-behaved across every size (99–110 µs, consistent with the same network-round-trip floor `get` showed). **DuckDB is clearly the weakest engine on this workload, at every size** (1.7–1.8 ms, essentially flat regardless of `n` — a fixed cost, not one that scales with data volume the way `scan_ages` did): DuckDB's query engine is built for large, batch, columnar analytical scans, and a `WITH RECURSIVE` traversal over a handful of rows is close to the opposite of that — the one workload in this section where being "the columnar engine" is a real liability rather than an advantage.

### Graph traversal, two-hop (`neighbors_two_hop` — a later addition, `STORAGE-013` v0.2.0)

The one-hop recursive CTE above extended one hop deeper (`WHERE hop.depth < 2` in the recursive term, `WHERE depth = 2` in the final `SELECT`), against `ProductionStore`'s own `bench_support::two_hop_neighbors` — the deduplicated union of `neighbors(n)` for every `n` in `neighbors(id)`, the exact same generic, non-trait composition `benches/workloads.rs`'s in-repo `neighbors_two_hop` group already benchmarks (see ADR-0004). Same dataset, same sizes, same sampling discipline as every table above.

| Size | production | sqlite | postgres | duckdb |
|---|---:|---:|---:|---:|
| 1,000 | **814.5 ns** | 22.18 µs | 449.7 µs | 2.299 ms |
| 100,000 | **891.0 ns** | 52.07 µs | 138.1 µs | 2.270 ms |
| 1,000,000 | **1.095 µs** | 65.68 µs | 133.3 µs | 2.262 ms |

**Verdict: `ProductionStore` wins overwhelmingly again — 27× to 2,822× faster, depending on engine and size — and the per-engine ranking from one-hop holds (SQLite strongest, DuckDB weakest), but the *shape* of how each engine's cost grows from one hop to two hops differs enough to be worth reporting on its own.** `ProductionStore`'s own two-hop cost is 12.2–14.3× its one-hop cost (two `neighbors` calls plus `HashSet` dedup) — the same order of magnitude this document's `## Graph traversal` section already found for the in-repo `Canonical`/`Canonical+cache` backends ("roughly 12-14× one-hop's time"), a genuine cross-check between the two independently-run benchmark passes. **SQLite** grows more gently (2.2–2.7× its own one-hop cost: a second indexed B-tree lookup plus a `JOIN`, cheap relative to the fixed cost it's already paying at one hop) and stays the strongest external engine at every size, 27×–60× behind `ProductionStore`. **DuckDB** grows the least (1.3× its own one-hop cost) and stays the weakest external engine at every size (2.26–2.30 ms) — consistent with `neighbors_one_hop`'s own finding that DuckDB's cost here is a fixed per-query overhead, largely indifferent to how much actual traversal work a given query does.

**Postgres is the one genuinely surprising number, investigated directly rather than reported as-is**: 449.7 µs at 1,000 records, dropping to 138.1 µs at 100,000 and 133.3 µs at 1,000,000 — backwards from every other engine/workload combination in this document, where cost holds flat or grows with `n`. `EXPLAIN (ANALYZE, BUFFERS)` against a prepared statement on each size's own schema (`ANALYZE` already current at every size — this is not a repeat of the missing-statistics bug above, and no plan crosses `jit_above_cost`, confirmed by the absence of a `JIT:` section at any size) found a real, cost-based join-strategy flip: at 1,000 records, the recursive term's join between the WorkTable and `littermates` (3,018 rows after loading both edge directions) is planned as a **Hash Join over a full `Seq Scan` of `littermates`**; at 100,000 and 1,000,000 records, the planner instead picks a **Nested Loop against `idx_littermates_dog_id`** for the same join. The index-nested-loop plan is the faster of the two here, so Postgres's real two-hop cost is dominated by *which join strategy the planner picks for a WorkTable-driven recursive join*, not by `littermates`' row count — a genuine, reproducible Postgres planning behavior for this exact recursive-CTE shape, not a benchmark artifact or a repeat of the earlier JIT finding.

### Where `ProductionStore` is actually competitive — explicit call-out

Per the task's own framing: this section reports where `ProductionStore` is genuinely competitive with a real external engine on the access patterns it was designed for, not just where it wins by the widest margin.

- **`ProductionStore` never loses a single cell in this comparison** — it is the fastest of the four systems at every size, on every workload, no exceptions. That is expected (it is a purpose-built, in-memory, single-schema store with none of a general-purpose engine's parsing/planning/serialization/transaction-isolation machinery to pay for) and is not itself the interesting finding.
- **The interesting finding is which external engine gets *close*, and where.** DuckDB closes to within 3.3× of `ProductionStore` on `scan_ages` at 1M records — by far the smallest margin any external engine reaches on any workload in this section, and a direct confirmation of the task's own prediction that DuckDB would be strong specifically on the scan/aggregate shape. The next-closest is SQLite on two-hop traversal at 1K records (27.2×) — `ProductionStore`'s own two-hop cost grows faster (12–14×) than SQLite's does (2.2–2.7×) from one hop to two, narrowing the margin between them even though `ProductionStore` still wins outright. No other (engine, workload) pair gets closer than ~37× (SQLite on `get` at 1K).
- **DuckDB's strength is narrow, not general** — the same engine that gets within 3.3× on `scan_ages` is the *worst* performer of the three externals on `get` (430–530 µs, worst at every size) and both graph-traversal depths (1.7–1.8 ms one-hop, 2.26–2.30 ms two-hop, worst at every size in both, by a wide margin). Picking the right tool for the access pattern matters as much for the external engines as it does for this crate's own row/column/graph comparison at the top of this document.
- **SQLite is the most consistently competitive external engine across all four shapes** — never the fastest external engine on `scan_ages` at scale, but never the worst on anything either, and the clear best on `get` and both graph-traversal depths. Its embedded, no-network-hop, direct-B-tree-lookup design generalizes better across these fixed shapes than either DuckDB's columnar specialization or Postgres's client/server model.
- **Postgres's numbers are dominated by its client/server round trip, not its query engine — except where a real planner decision changes which plan runs.** Its `get` and (post-fix) one-hop graph-traversal numbers are both flat, ~90–110 µs regardless of dataset size, consistent with loopback TCP/protocol overhead rather than any per-row cost. Its `scan_ages` numbers, by contrast, do scale with row count (a real sequential scan has to touch every row) — the one one-hop-or-simpler workload in this section where Postgres's *query* cost, not its round-trip cost, is the visible factor. Two-hop traversal breaks the "flat" pattern in a different way: its cost is dominated by *which join strategy the planner picks* (Hash Join + `Seq Scan` at 1K vs. Nested Loop + index at 100K/1M — see `### Graph traversal, two-hop` above), not by round-trip overhead or row count directly.

## Open questions

- **Cache-miss counts on real hardware**: done this pass — see the cache-miss section above. Resolved the `scan_ages` question the prior diagnostic session left open: Canonical+cache does have a real structural cache-miss advantage over SoA at 1M (not just noise), even though it doesn't show up in wall-clock time at that size.
- **The `scan_ages` 100K cache-miss crossover**: investigated to the practical limit of available tooling, not resolved. SoA has fewer cache misses than Canonical+cache at 100K (opposite of the 1M result), despite both running the identical `.clone()`-of-packed-`Vec<u32>` code path at every size. Real memory-footprint measurements (`examples/memory_footprint.rs`) ruled out the simplest version of the "larger co-resident working set → more misses" hypothesis. A finer-grained perf-counter bench (`benches/scan_ages_crossover.rs`) then ruled out L1 specifically: L1-data-cache miss rate is nearly identical between backends at both sizes (differences under 1.5 percentage points, vs. ~3× on the generic counters) — run for real on `baileyai`. The last-level-cache half of that bench doesn't run on `baileyai`'s AMD chip (`ENOENT` — AMD doesn't implement the generic last-level-cache PMU event this crate uses; would need raw, model-specific perf events to get). Not pursuing that further — the decision this data needs to support (`CanonicalCachedStore` wins/ties every workload) doesn't depend on it.
- **Lazy/dirty-flag invalidation as a fifth backend or mode**: ADR-0003 chose eager write-through for correctness-first simplicity, on the theory that a write-heavy mixed workload was the scenario most likely to flip that calculus. **Tested this pass (see `## Mixed read/write workload` above) and it didn't flip**: even at 90% writes, `CanonicalCachedStore` still wins outright at every size — eager's per-write tax never outweighs the `scan_ages` cost it saves plain `CanonicalStore` from paying on the remaining reads. Lazy invalidation remains a documented option (e.g. for a workload that's *purely* writes, with reads rare enough that eager's per-write cost is never recouped) but this pass found no evidence it's needed.
- **Write-heavy / mixed read-write workloads**: tested this pass — see `## Mixed read/write workload` above. `CanonicalCachedStore` wins all 9 tested configurations (3 write ratios × 3 sizes); margin never drops below 1.8×. Remaining gaps: write ratios beyond 90% weren't swept (the closest call in this pass was at 90%, so >90% is the more informative direction if this is revisited), and each call's target/op-kind is drawn independently and uniformly at random rather than in bursts (e.g. "100 writes in a row, then 100 reads") — a bursty pattern could interact differently with `CanonicalCachedStore`'s per-write cache write and is unmeasured.
- **Memory overhead per backend**: measured this pass (`examples/memory_footprint.rs`, real allocator-tracked bytes, not estimated) — see the crossover entry above for the headline numbers. Full picture: `AosStore` adds ~0 bytes beyond the input `Vec<DogRecord>` (it just moves it in); `SoaStore` is actually *smaller* than the input by ~4 bytes/record at every size (three parallel-array headers pack tighter than one `DogRecord` array); `CanonicalStore`'s overhead is 56–115 bytes/record depending on `n` (not stable — see the crossover entry's note on `HashMap` capacity quantization); `CanonicalCachedStore` adds a further ~37–56 bytes/record on top of `CanonicalStore` for `age_cache` + the position index. At 1M records this puts `CanonicalCachedStore`'s total footprint at ~287 MB vs. `SoaStore`'s ~112 MB — the real number behind "given how decisively it wins every workload, memory is the most likely reason not to default to it." Still open: whether that ~2.6× memory cost is acceptable given the workload — a decision this pass can surface but not make.
- **Behavior beyond the 1M boundary**: unchanged from the first pass — margins widen with `n` for the workloads where they matter, which suggests (not verifies) they'd hold at 10M+.
- **Breed-cardinality sweep**: unchanged from the first pass — cardinality was fixed at 50 throughout; `same_breed`'s advantage under a more evenly-distributed breed cardinality is still unmeasured.
- **`CanonicalStore`/`CanonicalCachedStore`'s breed-index design**: unchanged from the first pass — a `HashMap<String, Vec<Uuid>>` vs. alternatives, not benchmarked.
- **`CanonicalCachedStore`'s position-index design**: new this pass — the `HashMap<Uuid, usize>` position index is itself a design choice (parallel to the breed-index one above) that wasn't benchmarked against alternatives (e.g. storing the position inline on the record, avoiding the second map entirely).
- **LSM compaction**: new this pass — explicitly out of scope for the durability prototype (see `## Durability` above and `lsm_store.rs`'s own module docs). This pass's fixed 1,000-write, single-flush-per-checkpoint benchmark pattern never accumulates enough flushed generations to expose the unbounded read-amplification/disk-growth cost real compaction exists to solve — a workload with many checkpoint cycles over a long-running store's lifetime would show it. Not implemented; flagged as future work, not silently skipped.
- **mmap/LSM checkpoint costs at a size-proportional write volume**: new this pass — the `## Durability` checkpoint table's flat, size-independent mmap/LSM numbers are a real artifact of this benchmark's `SAMPLE_TARGET_COUNT = 200` target-rotation pool (1,000 pre-applied writes touch at most 200 distinct keys regardless of dataset size — see that section's own caveat). A workload that dirties a size-proportional fraction of records (rather than a fixed 200-key pool) would show both variants' checkpoint costs growing with `n`, just from a lower starting point than the full-state-persisting variants — unmeasured this pass.
- **`HybridStore::checkpoint`'s extra `state.clone()`**: identified in the original durability pass as the cause of Hybrid's checkpoint cost being the outlier of the whole durability sweep (1.17 s at 1M vs. 289–393 ms for its full-state-persisting peers) — **fixed in a follow-up pass**: `checkpoint` now serializes directly from `&self.state` via a borrowed mirror struct (mirroring how `WalFsyncStore`/`SnapshotFullStore` already avoid an equivalent clone), dropping checkpoint cost 25–61% across all three sizes with no change to correctness (all 4 hybrid unit tests, including the cutoff-boundary test, pass unchanged) or to `update_age`'s cost (confirmed via the diff and a targeted re-benchmark). See `## Durability`'s checkpoint section for the corrected numbers. No longer an open question.
- **Durability write-volume/size interaction beyond 1,000 writes and 1M records**: new this pass — every durability number above uses a fixed batch of 1,000 pre-applied writes (matching the task's own recoverability-comparison framing) against datasets up to 1M records. How checkpoint/load costs trend at 10M+ records, or under batches far larger than 1,000 writes between checkpoints, is unmeasured.
- **Tier 2 variants' scope-downs as a ceiling, not just a floor**: new this pass — mmap and `redb` both only persist the `age` field (records'/edges' own durability is out of scope for both, per their module docs); LSM's memtable holds only overridden ages, not full records. Whether extending any of these to cover the full record shape (not just the mutable field) would meaningfully change their relative standing — likely erasing mmap's structural per-write advantage over the baseline, since it would then need to write more than one field per call, same as every other variant — is unmeasured and not attempted this pass.
- **Reopen-path parallelization's break-even point**: resolved this pass. Parallelizing `CanonicalCachedState::new`'s and the three Tier 2 `build_indexes` functions' two independent construction phases (via `std::thread::scope`) was a clear win at 100K/1M (25–47% faster) but a real, measured regression at 1,000 records (17–26% slower) in the pass that introduced it — OS thread-spawn overhead exceeded the work being parallelized at that size. A follow-up pass measured the actual crossover directly (two independent 9-sample runs at 500/800/1,000/1,200/1,500/1,800/2,000/3,000/5,000 records: ≤800 reliably favors sequential, ≥1,500 reliably favors parallel, 1,000–1,200 is a genuine coin-flip between runs) and gated all four sites on one shared constant, `PARALLEL_CONSTRUCTION_THRESHOLD = 1,500`, falling back to the original sequential construction below it. The 1K regression is gone (see `## Durability`'s load section for the corrected numbers); 100K/1M gains are unchanged. No longer an open question, though the exact sub-500-record shape of the curve (whether the threshold could safely be lower) wasn't explored beyond confirming both ends of the measured range.
- **`benches/durability.rs`'s `run_load` doesn't measure WAL/Hybrid's true "first-ever start" reopen path**: new this pass, discovered during the reopen-parallelization diagnosis. Because `run_load` calls `finalize()` (which triggers `checkpoint()`) before timing `open`, `wal_fsync`/`wal_buffered`/`hybrid`'s benchmarked reopen always deserializes an existing base/snapshot file — never the `CanonicalCachedState::new`-from-records-and-replay-the-full-WAL path their own module docs describe as the interesting "no checkpoint has ever run yet" case. That scenario — and how large a WAL has to get before its replay cost, not the initial rebuild, dominates — is real and currently unmeasured. A future pass could add a fourth Criterion group (or a `run_load` variant) that skips the pre-load `finalize()` call specifically for the WAL-based variants.
- **Concurrency + a specific durability variant, combined**: new this pass — every `## Concurrency` variant is purely in-memory, deliberately not paired with any `## Durability` design (see that section's scope note for why). Whether, say, a sharded store where each shard also owns its own WAL changes either section's numbers or recommendation is a real, natural follow-up round, unmeasured here.
- **Sharded locking's shard count**: new this pass — `ShardedStore` fixes `SHARD_COUNT = 64`, chosen to sit well above the largest swept thread count (16) so shard collisions are the exception rather than the rule, but never swept against alternatives (e.g. would 16 or 256 shards change where sharding's one win — 1K records, 90% writes, ≥4 threads — starts or stops paying off?). Unmeasured; see `sharded.rs`'s own module docs.
- **`std::sync::RwLock` vs. `parking_lot::RwLock` for the global-lock variant**: new this pass — `GlobalRwLockStore` uses the standard-library lock specifically to avoid a new dependency for what's meant to be the simplest baseline (see `global_rwlock.rs`'s module docs). Whether `parking_lot`'s generally lower per-acquisition overhead would narrow global_rwlock's own thread-count degradation (its one weakness in this pass's numbers) is a plausible, unmeasured follow-up.
- **Concurrency benchmark dataset sizes stop at 100,000, not 1,000,000**: new this pass — dropped specifically to keep the new four-axis (size × ratio × thread-count × variant) sweep tractable in one pass (see `benches/concurrency.rs`'s own module docs). Whether global_rwlock's structural advantage over sharded/dashmap at 100K (driven by `scan_ages`'s packed-vector-vs.-64-shards cost, not lock contention) holds, narrows, or reverses at 1M is unmeasured.
- **Actor variant scaled beyond one owning thread**: new this pass — `ActorStore`'s measured throughput ceiling (roughly 65,000–105,000 ops/sec) is the cost of routing every operation through exactly one serial owner. Whether sharding the actors themselves (N owning threads, each responsible for a disjoint id range) would recover sharded-locking-like scaling while keeping the actor pattern's structural simplicity is a natural extension, not attempted this pass.
- **Bursty/skewed access patterns for the concurrency stress test and benchmark alike**: new this pass — both the correctness stress test (20 contended ids) and the throughput benchmark (`MixedWorkloadDriver`'s uniform-random target selection over a 200-id rotation pool) spread contention evenly. A workload with a genuine hot key (one id hit far more often than the rest) could show a different, more adversarial contention story for the lock-based variants specifically — unmeasured.
- **The real multi-core follow-up ran on the owner's Windows dev machine, not `baileyai`**: resolved this pass — the sweep re-ran directly on `baileyai` (session confirmed via `hostname`/`whoami`), see `## Concurrency`'s `baileyai` follow-up subsection. The 100K/90%-writes margin did keep shrinking toward parity as predicted (down to 1.03–1.05× at 32/64 threads, from 1.2× at 48 threads on the Windows machine) — the one prediction that held cleanly. But the broader "sharded's advantage widens with real parallelism" framing did **not** hold uniformly: `baileyai`'s extra 8 real cores over the Windows machine reversed the 1K/10%-writes crossover outright (global_rwlock wins again at 32/64 threads) and *narrowed* the 1K/90%-writes sharded margin (7.3–7.9× vs. the Windows machine's 9.5–10.1×), rather than widening either. **New open question this pass raises**: whether that non-monotonicity is a genuine machine-specific effect (different microarchitecture/memory subsystem between the Windows machine's Ryzen 9 7900X3D and `baileyai`'s Ryzen AI MAX+ 395 APU, not just a different core count) or would resolve into a cleaner trend on a fourth, still-larger real machine — unmeasured, and the two real non-container data points collected so far aren't enough to distinguish the two explanations.
- **Actor's throughput collapse at real high thread counts (1K, 24/48 threads) vs. the container's flat plateau**: new this pass — plausible mechanism named (real cross-core contention on the single `mpsc` channel and its per-call reply channel, once enough client threads are genuinely running in parallel rather than time-slicing on 4 cores) but not verified further (e.g. by profiling where the actor-side thread or the channel itself becomes the bottleneck at 24+ concurrent senders). The 100K rows show the same shape far more mildly, consistent with per-op cost dominating channel overhead at that size — also not verified beyond the observed numbers.
- **`ProductionStore`'s standard-suite numbers vs. the four-backend comparison, on the same machine**: new this pass — `ProductionStore`'s `get`/`scan_ages`/etc. numbers were measured directly on `baileyai`; every AoS/SoA/`CanonicalStore`/`CanonicalCachedStore` number earlier in this document was measured on this session's cloud Linux container instead (see the Methodology section and `## Production recommendation`'s own caveat). Re-running the original four-backend suite on `baileyai` would give a genuine apples-to-apples comparison and confirm whether `ProductionStore`'s read-side numbers are structurally slower than `CanonicalCachedStore`'s (the plausible mechanism named in `## Production recommendation`) independent of the machine difference — unmeasured this pass.
- **`ProductionStore`'s 100K read-heavy concurrency tax**: resolved in a follow-up diagnosis pass — see `## Production recommendation`'s "Diagnosis and fix" subsection. Traced to `MmapAgeStore::scan_ages`'s per-position indexed-read loop (`src/durability/mmap_store.rs`, a previously-closed durability-round module), not to any durability guarantee (`update_age` was confirmed, not just assumed, to still be cheaper than the in-memory baseline). Fixed via `chunks_exact(4)` bulk reads — safe code, no new dependency, `update_age`/`flush` untouched. `scan_ages` dropped 12–17× at every size; the concurrency-throughput tax that motivated this investigation is gone (every tested cell now within 0.77–1.46× of the plain in-memory baseline, most at or ahead of parity). `get`'s modest ~1.5× cost (two `HashMap` lookups vs. `CanonicalCachedStore`'s one) was measured but not similarly optimized — small enough not to warrant it, and not the source of the 100K tax this pass investigated.
- **Concurrency + a specific durability variant, combined — now partially resolved**: `## Concurrency`'s own open question named this as unmeasured; `PRODUCTION-DEFAULT` measured exactly one instance (global `RwLock` + mmap, i.e. `ProductionStore`). Every *other* pairing (e.g. sharded locking + a WAL variant, for the small-write-heavy corner where sharding wins but durability is also needed) remains unmeasured — this pass deliberately didn't generalize beyond the one combination all six prior rounds converged on.
- **Physical `src/comparisons/` reorganization**: new this pass — explicitly considered as a way to make the other three storage backends/seven other durability variants/three other concurrency strategies read as more clearly secondary than a docs-only lead can, and explicitly declined this pass (checked in on directly) in favor of the docs-only approach, to avoid a large, purely mechanical diff across every bench/test/example import path. Remains available as a future follow-up if the docs-only lead proves insufficient in practice; see ADR-0008's Considered options and revisit triggers.
- **The in-memory `Scanned`/`BaseStore` composition's write-through gap**: discovered while wiring `GenericMmapStore` (see `## Generic schema library` above), then diagnosed and fixed in a follow-up pass — `GetById::get` on a purely in-memory composed generic stack (`DogGenericStore`/`OrderGenericStore`) now reflects a field `UpdateField::update` just wrote, same as every hand-written backend in this crate. The fix carries a real, measured cost specific to the in-memory path (`get` ~43–88% slower — an extra `HashMap` lookup per `Scanned` layer), which `GenericMmapStore`'s own equivalent fix didn't pay (it replaced work that already had to happen, rather than adding new work). No longer an open question — resolved with a regression test (`order_customer.rs`'s `get_reflects_a_prior_update_through_every_layer_of_the_in_memory_stack`) guarding against recurrence.
- **`GenericMmapStore`'s one-durable-field scope**: unchanged from ADR-0009's own §4.2 finding, now built rather than just predicted — a domain wanting more than one mutable, durable field (e.g. `Order`'s `Amount` *and* `status` both durable) needs the string-heap/fixed-layout redesign ADR-0006/ADR-0009 both declined to build; `GenericMmapStore` deliberately keeps `MmapAgeStore`'s exact one-field scope, generically, rather than attempting that redesign.
- **Generic library benchmark coverage stops at `Order`/`Customer`**: new this pass — `crate::generic` is generic over any `Record`-implementing type by construction, but only two domains (`Dog`, `Order`/`Customer`) have ever exercised it, and only `Order`/`Customer` has a real durable production-store benchmark. A third, structurally different domain (e.g. one needing `SymmetricRelation` *and* `ChildOf` together, which neither `Dog` nor `Order`/`Customer` does) would be the next real stress test, per this project's own "no abstraction before two real call sites" rule now being satisfied at the *implementation* level, not just the design level.
- **Generic dataset generation/benchmark infrastructure remains domain-specific**: unchanged from ADR-0009's §4.7 finding — `crate::generic_spike::order_bench_support`'s dataset generator is `Order`-specific, hand-written rather than a generic equivalent of `bench_support::GeneratorConfig`; a third domain would need its own dataset generator too, same as this pass's did.
- **Generic library benchmark coverage now includes a third domain — resolved**: `Employee` (`SERVER-QUERY-LAYER` v0.3.0) is exactly the domain the entry above named as the natural next stress test — `SymmetricRelation` and `ChildOf` together, which neither `Dog` nor `Order`/`Customer` has. No longer unmeasured; see `## Server / query layer` above and `docs/decisions/ADR-0009-generic-schema-design-proposal.md`'s "Acceptance and implementation" addendum for the real gap it found and fixed (`Reversed` never forwarded `Neighbors`).
- **No throughput/latency benchmark for the server layer — resolved**: `SERVER-001`'s own "Open questions" named this as a real, unscoped follow-up since the layer's initial implementation. `benches/server.rs` closes it — see `## Server / query layer` above. Headline finding: at this record-count scale, one loopback round trip's network/framing cost (~37 µs) dwarfs any per-domain in-process operation cost by two to three orders of magnitude, so all three domains' numbers land in the same band.
- **The thread-per-connection model's real connection-count ceiling — resolved, with a nuance**: re-run on real hardware (the owner's Windows dev machine, `Beast`, 24 real cores — see `## Server / query layer`'s own real-hardware subsection above), `THREAD_COUNTS` retuned to `[1, 4, 24, 48]` to match. Confirms the container's flat 4-through-16 plateau was that environment's own 4-core ceiling, not a structural property of the model: throughput genuinely keeps climbing from 4 to 24 threads on real hardware (roughly doubling again, every domain, both runs). The ceiling itself sits at or near this machine's real core count — pushing to 48 threads (2× cores) is flat-to-negative, not a continuation of the climb, the same oversubscription signature already seen elsewhere in this document. Not chased further into the "hundreds to thousands of concurrent clients" range originally scoped, since the real finding — the model scales with genuine parallelism up to core count, then oversubscription costs rather than helps — doesn't need a higher connection count to establish; that finer-grained "exactly how many connections past core count before it gets worse, not just flat" shape remains unmeasured and is a smaller, separate follow-up if it matters. One new, unexplained observation this pass surfaced instead: this real machine's peak throughput is *lower* than the 4-core container's own plateau (147K–192K vs. 160K–310K ops/sec) — plausibly Windows's loopback TCP/scheduling overhead vs. the container's Linux stack, not verified, see that subsection's own honest caveat.
- **`bincode`'s wire-format stability across crate versions remains unverified**: unchanged from `SERVER-001`'s own open questions — `benches/server.rs` measures cost, not compatibility, and doesn't touch this question.
- **Two-hop traversal against the external engines — resolved for 2 hops, deeper still open**: `## External database comparison` now has a `### Graph traversal, two-hop` subsection (`STORAGE-013` v0.2.0). `ProductionStore` still wins every cell; DuckDB's fixed per-query overhead does grow, but only mildly (~1.3× its one-hop cost, not proportionally to the extra work); Postgres's `ANALYZE`d cost estimates stay accurate (no repeat of the JIT bug), but a genuine, separate finding turned up — a cost-based join-strategy flip (`Seq Scan`+Hash Join at 1K vs. indexed Nested Loop at 100K/1M) that makes Postgres's two-hop cost non-monotonic in `n`. Three-or-more-hop traversal remains unmeasured — whether Postgres's join-strategy choice keeps flipping at other table sizes, or DuckDB's/SQLite's near-linear per-hop growth holds, is open beyond depth 2.
- **A controlled-for durability comparison across all four systems**: new this pass — SQLite/Postgres/DuckDB each ran under their own default durability behavior (WAL/checkpointing), untuned; `ProductionStore`'s own mmap durability guarantee was not matched against them under equivalent settings (e.g. `synchronous=OFF` vs. `FULL` for SQLite, `fsync` on/off for Postgres). The numbers above measure query cost under each engine's real default behavior, not a normalized "durability turned off everywhere" baseline.
- **Concurrent/multi-client access to the external engines**: new this pass — every number above is single-threaded, single-connection, the same starting point every other workload benchmark in this crate had before its own later concurrency pass (`## Concurrency` above). Whether Postgres's/SQLite's/DuckDB's relative standing changes under real concurrent load (especially SQLite, whose single-writer model is a well-known real constraint `ProductionStore`'s own `RwLock` doesn't share) is unmeasured.
- **DuckDB's `bundled` Cargo feature's CI build-time cost — resolved**: flagged in ADR-0015's Consequences as a real cost with a mitigation deliberately deferred until it became a real friction point; it did (every fresh CI run rebuilt DuckDB's C++ amalgamation from scratch, ~20 minutes, since `.github/workflows/ci.yml` had no build cache at all). Fixed by adding `Swatinem/rust-cache@v2` to the workflow, keyed on `Cargo.lock` — a standard, minimal-risk mitigation, not the more invasive alternatives (a system-DuckDB feature variant, or excluding this bench from the default `--all-features` sweep) named in the ADR.
- **`MmapAgeStore`'s identity-keying fix wasn't independently crash-tested against this specific store**: new this pass (see `## Production recommendation`'s own subsection) — the `COMMITTED`-marker torn-write safety and the rewrite-via-rename's crash-safety both reuse `GenericMmapStore`'s own already-validated reasoning by structural analogy, not a fresh fault-injection trial (`src/bin/crash_safety_harness.rs`-style `SIGKILL` testing) against `MmapAgeStore` itself. A dedicated harness remains a real, unscoped follow-up if that transfer-by-analogy is ever judged insufficient.
- **The columnar rewrite-on-append path is untested by any benchmark, deliberately** — new this pass — every existing benchmark and test-suite call site supplies the identical record set at `create` and every later `open`, so the full-file-rewrite path (triggered only when a genuinely new record appears since the last write) never runs in this crate's own measured workloads. Its cost (an O(N) rewrite, correctness-tested but not benchmarked) is real for any caller whose record set actually changes between reopens — unmeasured, and not expected to matter for this crate's own benchmark suite, which never exercises it.
- **`ProductionStore`'s `.mmap` file still isn't a portable, self-contained database file the way SQLite's/DuckDB's are** — the identity-keying fix closes the silent-misattribution risk, but the file still only persists `age`, not `id`/`breed`/edges, and still requires the caller to independently reconstruct the full record set on every `open`. Full file-portability parity with SQLite/DuckDB (persisting the whole record, not just the mutable field) would be a separate, larger design decision — not attempted this pass, see the conversation that led to this fix for the original framing of that gap.
