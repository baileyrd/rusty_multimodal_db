**Two follow-up fixes landed before merge, both found by re-checking the results rather than accepting them at face value:**
- **`HybridStore::checkpoint`'s extra `state.clone()`**: identified as the cause of Hybrid's checkpoint cost being the one 3× outlier in the whole durability sweep (1.17 s at 1M vs. 289–393 ms for its full-state-persisting peers). Fixed by serializing directly from `&self.state` through a borrowed mirror struct (`HybridSnapshotRef`) instead of an owned `HybridSnapshot` — same on-disk bytes, `open`'s deserialization path unchanged. Dropped checkpoint cost 25–61% across all three sizes with zero change to correctness (all 4 hybrid unit tests, including the cutoff-boundary replay test, pass unchanged) or to `update_age`'s cost.
- **Reopen-cost profiling found the prior round's "shared bottleneck" framing was right about the symptom, wrong about the mechanism.** Real profiling (not assumption) traced which code path each variant's benchmarked `open` actually takes: `benches/durability.rs`'s own `run_load` calls `finalize()`/`checkpoint()` before timing load, so `wal_fsync`/`wal_buffered`/`hybrid`/`snapshot_full` all measure "deserialize an existing snapshot," not "rebuild indexes from records." `snapshot_full` itself has no bug — it genuinely deserializes its persisted indexes, and deserializing a `HashMap`-heavy structure costs about the same as rebuilding one (1.275 s vs. 1.274 s at 1M, after correcting for cold-start measurement bias in this shared environment). Only `snapshot_rebuild` and the three Tier 2 variants genuinely rebuild indexes under this benchmark. Fixed by parallelizing the two independent construction phases in `CanonicalCachedState::new` and the three Tier 2 `build_indexes` functions via `std::thread::scope` (stdlib, no new dependency) — `snapshot_rebuild`/`mmap`/`lsm`/`redb` reopen 25–47% faster at 100K/1M; the other four move by noise only, exactly as predicted. Honest tradeoff reported, not hidden: at 1,000 records the "improved" four actually regress 17–26% (thread-spawn overhead exceeds the tiny workload) — not engineered around with a size threshold.

Both fixes verified via the full existing test suite (108/108, unchanged, re-run 3× after the reopen fix to rule out a scoped-thread race) — no new tests needed since these were performance fixes to already-tested code, not new behavior.
