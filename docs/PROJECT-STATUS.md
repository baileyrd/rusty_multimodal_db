- Current milestone: `MMAP-AGE-STORE-IDENTITY-FIX` — a real, latent correctness bug in `MmapAgeStore` (`ProductionStore`'s durable storage layer), found while the owner was asking how `ProductionStore`'s own file compares to SQLite's/DuckDB's portable ones, is fixed: `open` used to trust that array position N in the file still held position N's age from `create` time, with nothing on disk recording which record an age actually belonged to — a caller supplying `records` in a different order between `create` and a later `open` would have silently misattributed ages, no error, no panic (never triggered by this crate's own test/bench suite, but never ruled out by `ProductionStore`'s public contract either). Fixed by porting `crate::generic::mmap_store::GenericMmapStore`'s own already-proven identity-keying + schema-version-header design — reconciliation by id, not position. **A first, row-oriented (interleaved-slot) port regressed `scan_ages` 2.2-6.1× (299.5 µs → 1.838 ms at 1M) and reversed this session's own just-published external-database headline finding** (`ProductionStore` losing to DuckDB on `scan_ages` at 1M, not narrowly beating it) — caught via detailed before/after benchmarking before merging, not discovered after. **A second, columnar redesign (ids/ages/markers in three separate contiguous regions instead of interleaved) recovered nearly all of it**: `scan_ages` now only 1.1-1.4× slower than pre-fix (338.6 µs at 1M), and the external-database headline finding is restored almost exactly (DuckDB 3.7× behind at 1M, was 3.3×). The real cost moved to a rare, never-benchmarked path instead: a columnar layout can't append a new record cheaply in place, so that case now does a full, crash-safe rewrite (write-to-temp-then-atomic-rename) rather than the row-oriented design's cheap `O_APPEND`. **Two follow-up fixes landed before merge, both found by re-checking the results rather than accepting them at face value:**
- **`HybridStore::checkpoint`'s extra `state.clone()`**: identified as the cause of Hybrid's checkpoint cost being the one 3× outlier in the whole durability sweep (1.17 s at 1M vs. 289–393 ms for its full-state-persisting peers). - **Reopen-cost profiling found the prior round's "shared bottleneck" framing was right about the symptom, wrong about the mechanism.** Real profiling (not assumption) traced which code path each variant's benchmarked `open` actually takes: `benches/durability.rs`'s own `run_load` calls `finalize()`/`checkpoint()` before timing load, so `wal_fsync`/`wal_buffered`/`hybrid`/`snapshot_full` all measure "deserialize an existing snapshot," not "rebuild indexes from records." `snapshot_full` itself has no bug — it genuinely deserializes its persisted indexes, and deserializing a `HashMap`-heavy structure costs about the same as rebuilding one (1.275 s vs. 1.274 s at 1M, after correcting for cold-start measurement bias in this shared environment). Honest tradeoff reported, not hidden: at 1,000 records the "improved" four actually regress 17–26% (thread-spawn overhead exceeds the tiny workload) — not engineered around with a size threshold.

- `GENERIC-MMAP-APPEND-SLOT-RACE-FIX` — fixes the "next free slot" race `GENERIC-MMAP-MULTIPROCESS-DIAGNOSIS` found. - `SERVER-TRANSACTION-DESIGN` — the owner's third and last "what's next" pick, session/transaction semantics. `docs/FUTURE-GROWTH.md` names this "genuinely new," not incremental, so this got the same design-first, stop-for-review treatment `SERVER-AUTH-DESIGN`/ADR-0012 itself got — no implementation code, no new source file under `src/`, no test suite, no dependency added.

  `docs/design/SERVER-TRANSACTION-DESIGN.md` proposes the smallest real slice of `docs/FUTURE-GROWTH.md`'s broader "session/transaction semantics across multiple requests" framing: a new `Request::Transaction { updates: Vec<TransactionOp> }`, each `TransactionOp` shaped exactly like `Request::UpdateField`'s own fields — a batch of writes, all known and submitted together in one request message. Every operation's precondition (record exists, field known and updatable, value type matches) is checked before any write is applied; if every check passes, every write is applied, otherwise none are (`Response::Ok` vs. `Response::TransactionFailed { index, code, message }`). Requires `TokenClass::ReadWrite`, extending `AUTH-FR-003`'s existing rule to the new request kind rather than reopening it. One new `ErrorCode::RecordNotFound` variant, reachable only through the new response shape — a single, non-transactional `UpdateField` keeps its existing `Response::NotFound` behavior unchanged.

  Validate-then-apply (not an undo log) is the chosen atomicity mechanism, exploiting a real invariant this crate already has everywhere: no domain ever deletes a record at runtime, so a precondition checked once stays true for the rest of a batch as long as every check and every write happen under one continuously-held lock acquisition — no time-of-check-to-time-of-use race to guard against, no rollback machinery needed.

  **The one real architectural finding this proposal surfaced**: today's `ConnectionStore` trait methods (`get`/`update_field`/etc.) each independently acquire and release whatever lock the underlying store manages, per call — there is no way to hold that lock across several logical operations using only the trait's existing shape. Delivering real atomicity therefore needs a new, minimal primitive on the storage layer itself (`ProductionStore`/`GenericProductionStore`), not just an addition at the server layer — a materially bigger footprint than `SERVER-AUTH`'s purely server-layer-additive implementation, and named explicitly in ADR-0013's own Decision section rather than left for an implementation round to discover. A server-layer-only second lock was considered and rejected: it would either not achieve real isolation (unless every write, transactional or not, is rerouted through it) or duplicate the store's own lock outright — either way a real violation of ADR-0010's own "no new lock at this layer" principle.

  **Explicitly, deliberately does not propose a multi-round-trip interactive session** (`BeginTransaction`/several separate requests/`Commit`, transaction state held open across them) — the literal "session" half of `docs/FUTURE-GROWTH.md`'s framing. Rejected specifically because holding a connection's exclusive lock open across an unbounded number of client round trips is a real liveness/denial-of-service risk this project has never accepted anywhere else in the server layer (a slow, stalled, or malicious client could block every other connection indefinitely, with no timeout/forced-abort/fairness story anywhere in this project's concurrency model). Named as a real, larger future design, not ruled out forever.

  **Explicitly, deliberately does not deliver crash-atomicity across a batch** — a process crash between two of a batch's writes landing on stable storage can leave a partial batch durably applied. This proposal delivers atomicity and isolation with respect to concurrent access only; a true ACID transaction would additionally need a combined-journal or two-phase-commit-style mechanism this proposal does not build.

  ADR-0013 records the decision, following the identical structure/rigor ADR-0012 established: Context, Decision drivers, Considered options (batch shape, rollback mechanism, locking mechanism — each with a chosen option and honest rejections), Decision, Consequences (positive and negative, the storage-layer cost named as a real tradeoff), Validation and revisit triggers (true interactive sessions, crash-atomicity, a second mutating operation kind — each named as a real, separate future decision).

  **The real architectural finding**: `ConnectionStore`'s existing methods (`get`/`update_field`/etc.) are each independently self-contained — every call acquires and releases whatever lock the underlying store manages, on its own. Real atomicity needed a new, minimal storage-layer primitive, named up front in ADR-0013 rather than discovered mid-implementation: `crate::production::TransactionalStore` (a new trait, one associated type `Exclusive: DogStore`, one method `with_exclusive`, implemented only by `ProductionStore` — not every `ConcurrentStore` variant, since the other `src/concurrency/**` strategies are benchmarked historical alternatives never wrapped by the server layer in practice) and `crate::generic::production::GenericProductionStore::with_exclusive` (a plain inherent method — `OrderConnectionStore`/`EmployeeConnectionStore` are concretely typed over one specific `S`, unlike `server::dog::DogConnectionStore<S>`, so no generic caller needs a trait bound here). - `MMAP-AGE-STORE-IDENTITY-FIX` — a real, latent correctness bug in `MmapAgeStore` (`src/durability/mmap_store.rs`, the storage layer `ProductionStore` directly wraps), found while the owner was asking how `ProductionStore`'s own persisted file compares to SQLite's/DuckDB's portable, self-contained ones. `MmapAgeStore::open` rebuilt its `Uuid -> array position` index fresh from whatever order the caller-supplied `records`/`edges` happened to arrive in on that specific call, and trusted that array position N in the file still held position N's age from `create` time — nothing on disk recorded which record an age actually belonged to. A caller supplying `records` in a different order between `create` and a later `open` would have silently misattributed ages between records: no error, no panic, just wrong data under a real id. No caller anywhere in this crate's own test/bench suite ever triggers this (every one supplies the identical generator output, identically ordered, at both `create` and every later `open`), but nothing about `ProductionStore`'s public contract ever ruled it out. `GenericMmapStore` (`src/generic/mmap_store.rs`) already had this identical bug diagnosed and fixed earlier — see `GENERIC-SCHEMA-LIBRARY`'s own completed entry — but the fix was never backported to `MmapAgeStore` until now.

  **First attempt: a straight port of `GenericMmapStore`'s already-proven fix** — a versioned header (magic number + schema version) plus one interleaved `[id: 16 bytes][age: 4 bytes][commit marker: 1 byte]` slot per record, reconciled by id (not position) on `open`. Correct, but it broke `scan_ages`'s existing `chunks_exact(4)` bulk-read fast path (this same section's own earlier "Diagnosis and fix," 12-17× faster than a naive per-position loop) — that optimization needs the mapped region to be *exactly* a flat, homogeneous `[u32]` array, which an interleaved slot isn't. Measured directly before merging anything, per the owner's own explicit instruction to understand the full impact first: **`scan_ages` regressed 2.2-6.1× (299.5 µs → 1.838 ms at 1M)**, and — because `ProductionStore`'s numbers are exactly what `## External database comparison` had just measured `scan_ages` against — this **reversed that section's own just-published headline finding**: `ProductionStore` (1.691 ms) became slower than DuckDB (1.156 ms, unchanged) at 1M, not narrowly beating it. Every other workload (`get`/`update_age`/`same_breed`/`neighbors_one_hop`/`neighbors_two_hop`) stayed flat, within normal run-to-run noise.

  **Second attempt, accepted: a columnar layout instead of row-oriented.** Three separate, contiguous regions after the header — every id, then every age, then every commit marker, each its own flat array in the same record order — so `scan_ages`'s fast path returns to a pure `chunks_exact(4)` over *only* the ages region. The real cost moved to a different, rare path instead: a columnar layout can't append one new record cheaply in place (it would need inserting bytes into three separate, non-adjacent regions), so `open` reconciling a genuinely new record now triggers a full rewrite — crash-safely, via write-to-temp-then-atomic-`rename`, never in-place truncation (a *stronger* safety property than the row-oriented design's own `O_APPEND` approach, not a weaker one: a crash mid-rewrite can never leave `path` holding a partial generation). This path is never exercised by this crate's own benchmark suite or any existing call site (every one supplies the same record set at every reopen), so it costs nothing in the numbers below. Result: **`scan_ages` only 1.1-1.4× slower than the pre-fix baseline** (338.6 µs at 1M, vs. the row-oriented attempt's 6.1×), and the external-database headline finding is restored almost exactly: DuckDB 3.7× behind `ProductionStore` at 1M (was 3.3× before this fix), 43× behind at 100K (was 41.8×). `## External database comparison`'s own tables are left as originally measured, per this document's established practice — see `## Production recommendation`'s new `### MmapAgeStore identity-keying fix` subsection for the full before/after account, including the exact tables.
