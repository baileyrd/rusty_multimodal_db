# SERVER-001 — Network server/query layer: `Request`/`Response` protocol in front of `ProductionStore`/`GenericProductionStore`

- Version: 0.35.1 (patch — the `client` Cargo feature, the `SERVER-002` wire specification and its enforced conformance fixture, and the Python reference client, ADR-0043; no requirement of this specification changes; `JOIN` over a declared relation within one table — `Request::Join`/`DescribeRelations` and protocol 12, FR-045, ADR-0044; `Entity::aliases` on the wire — `ScanValue::StrList` and protocol 11, FR-044, ADR-0041; `Entity` source-verification follow-ups — whitespace-collapsing normalization and a derived `entity_id`, FR-043, ADR-0042; `Entity` aliases and case-insensitive name lookup, FR-042, ADR-0040; `Entity` v2 — multi-relation lookup and protocol 10, FR-041, ADR-0039; `Entity` domain and bounded client-side graph traversal, FR-040, ADR-0037; `Reminder` domain — the generic schema library's first front-door appearance, FR-039, ADR-0036; bounded `GROUP BY`/aggregation, FR-038, ADR-0035; bounded read-only SQL `SELECT` subset, FR-037, ADR-0034; session snapshot isolation and protocol version 7, FR-036, ADR-0033; `ServeOptions` consolidation, FR-035, ADR-0032; `Admitted` gains `classed_by_certificate`, FR-034; per-request access log, FR-033, ADR-0031; rate limiting and lockout, FR-032, ADR-0030; class from certificate, FR-031, ADR-0028; stage-time validation in sessions and protocol version 6, FR-030; authentication audit log, FR-029, ADR-0029; read-your-writes sessions and protocol version 5, FR-028, ADR-0027; journal group commit, FR-027, ADR-0026; pre-hello reconnect fallback in `SchemaDrivenClient`, FR-026; crash-atomic batches via an opt-in redo journal and protocol version 4, FR-025, ADR-0025; transaction sessions and protocol version 3, FR-024, ADR-0024; mutual TLS, FR-023, ADR-0023; `SchemaDrivenClient` transport encryption, FR-022; `SchemaDrivenClient` authentication, FR-021; protocol version + optional `Hello`, FR-020, ADR-0022; wire encoding pinned by `STORAGE-018`'s codec — see "Change history")

## Purpose and scope

`docs/decisions/ADR-0010-server-query-layer-proposal.md` (Accepted) and `docs/design/SERVER-QUERY-LAYER-DESIGN.md` (Accepted) proposed a thin network server/query layer in front of this crate's existing `ProductionStore`/`GenericProductionStore` — a `Request`/`Response` wire protocol over length-prefixed `bincode` framing, thread-per-connection, reusing whichever `RwLock` the wrapped store already manages. This spec covers the real implementation: `src/server/**`, the `server` Cargo feature, five domain adapters (`Dog`, `Order`/`Customer`, `Employee`, `Reminder` — since v0.29.0, `Entity` — since v0.30.0), a minimal server binary each for `Dog`, `Reminder`, and `Entity`, and the tests that verify it end to end over a real socket.

## Non-goals

- Not transport encryption — named as an explicit, blocking gap by ADR-0010, still open even after v0.6.0's authentication/authorization work (ADR-0012, `docs/design/SERVER-AUTH-DESIGN.md`): this spec does not authorize deploying a server built from it beyond a trusted, localhost/development network unless paired with an external TLS-terminating proxy/tunnel. **Resolved (authentication/authorization half only), v0.6.0**: see FR-016 — `AuthConfig`/`Request::Authenticate` close the "anyone who can open a TCP connection can do anything" gap; the "anyone who can observe the network can read the token and every record in transit" gap remained open until v0.9.0. **Resolved, v0.9.0**: see FR-019 — `TlsConfig`, native TLS via `rusty_tls` (this owner's own ecosystem-wide `rustls` wrapper, not a direct `rustls` dependency — see `docs/design/SERVER-TLS-DESIGN.md`'s "Ecosystem check"), closes the transport-encryption half. `TlsConfig` and `AuthConfig` are each independently opt-in; a deployment beyond a trusted network still needs both configured together, not either alone.
- Not multi-round-trip session semantics — v0.6.0's per-connection authentication state remains the only exception this spec has ever made to "no cross-request server-side state" (see `SERVER-AUTH-DESIGN.md`'s own "Non-goals"): it gates requests, it doesn't remember a cursor or a transaction. **v0.7.0's `Request::Transaction` (below) does not change this** — a transaction is one request message carrying several operations, not a `Begin`/several-requests/`Commit` session with state held open across round trips; see `SERVER-TRANSACTION-DESIGN.md`'s own "Non-goals" for why that shape was deliberately rejected (an unbounded, unaccepted-elsewhere liveness risk).
- Not transaction semantics — every request is single-shot, same as every existing store method. **Resolved (one bounded slice only), v0.7.0**: see FR-017 — `Request::Transaction` closes the "no way to apply several writes atomically" gap for a single request message; it does not add multi-round-trip sessions, isolation levels beyond full serialization by lock, or crash-atomicity across a batch — see FR-017's own entry and `SERVER-TRANSACTION-DESIGN.md`'s "Non-goals" for the exact scope.
- Not a query language beyond fixed, server-assigned integer field tags — no parser, no planner, no schema-description sub-protocol. **Resolved (one bounded slice only), v0.27.0**: see FR-037 — a read-only SQL `SELECT` subset (`*`/named columns, `WHERE` with `AND`-only equality/ordering predicates, `LIMIT`) closes the "every request names a field by tag, one at a time" gap for read access, entirely client-side (`SchemaDrivenClient::query` parses locally against the already-discovered `DomainSchema`; the server never sees SQL text, only a structured `Request::Query`). It does not add a query planner, a cost-based optimizer, joins, aggregation/`GROUP BY`, `ORDER BY`, writes via SQL, prepared statements, or a server-side SQL parser — every `Query` is an unconditional full scan, named as a real, disproportionate, still-open gap by `docs/design/SERVER-SQL-SELECT-DESIGN.md`'s own "Non-goals". **Resolved (one further bounded slice), v0.28.0**: see FR-038 — `GROUP BY` and `COUNT`/`SUM`/`AVG`/`MIN`/`MAX` close the aggregation half of that remaining gap, entirely client-side-parsed the same way (`SchemaDrivenClient::query` compiles an aggregate-shaped `SELECT` to a structured `Request::Aggregate`). A query planner/cost-based optimizer, joins, `ORDER BY`, writes via SQL, prepared statements, and a server-side SQL parser all remain open, named as disproportionate by `docs/design/SERVER-SQL-AGGREGATE-DESIGN.md`'s own "Non-goals" — `HAVING` specifically named there as the most likely next slice.
- Not an async runtime (`tokio`) — thread-per-connection was the chosen concurrency model (ADR-0010's "Considered options"); this spec doesn't revisit that choice.
- Not a change to `ProductionStore`, `GenericProductionStore`, or any existing store/durability/concurrency code — this is a new, additive translation layer. **One exception, v0.3.0**: validating the `Employee` domain adapter surfaced a real, load-bearing gap directly in `crate::generic` (`Reversed` never forwarded `Neighbors`) — see FR-012. That fix completes already-accepted `STORAGE-012` capability, not a new storage-layer decision, and is the only `src/generic/**` change this spec's implementation has ever required.
- Not a benchmark suite for v0.1.0 through v0.3.0 — those rounds' acceptance criteria were correctness (a real client/server round trip, a concurrent-client stress test), not throughput measurement, named as a real, unscoped follow-up rather than silently assumed unnecessary. **Resolved, v0.4.0**: `benches/server.rs` closes this gap — see FR-014.
- Not `CreatedAt`/`DiscountCents` field access for `Order` — `OrderProductionStack` (the durable stack this spec wraps) only carries `Status`/`Amount`; those two fields are in-memory-only in `crate::generic` and were never part of the durable production stack to begin with (see `src/server/order.rs`'s own module docs).

## Context and terminology

- **`server` Cargo feature**: off by default, distinct from `research` — this is new, real, additive capability (a network-listening binary surface), not a benchmarked-alternative or historical-spike module. Validating it against `Order`/`Customer` or `Employee` additionally needs `research` (since `order_customer` and `employee_impl` are both research-gated reference material); the `Dog` side needs `server` alone.
- **`ConnectionStore`**: the one trait `dispatch`/`serve` are generic over (`src/server/mod.rs`) — a thin per-domain adapter, implemented by `server::dog::DogConnectionStore` (wraps `ProductionStore`), `server::order::OrderConnectionStore` (wraps `GenericProductionStore<OrderProductionStack>`, behind `research`), `server::employee::EmployeeConnectionStore` (wraps `GenericProductionStore<EmployeeProductionStack>`, behind `research`), since v0.29.0 — `server::reminder::ReminderConnectionStore` (wraps `GenericProductionStore<ReminderProductionStack>`, `server` alone, not behind `research`), and — since v0.30.0 — `server::entity::EntityConnectionStore` (wraps `GenericProductionStore<EntityProductionStack>`, `server` alone, not behind `research`).
- **`FieldRef`**: a `u16` field tag, fixed per domain adapter at compile time (not runtime-negotiated) — `Dog`'s `FIELD_BREED`/`FIELD_AGE`, `Order`'s `FIELD_AMOUNT`/`FIELD_STATUS`/`FIELD_CREATED_AT`/`FIELD_DISCOUNT`, `Employee`'s `FIELD_NAME`/`FIELD_DEPARTMENT`/`FIELD_SALARY`.
- **`ScanValue`**: the wire value type. Extends the accepted design's original `U32`/`I64`/`Bool` with `Str(String)` — a necessary completion for `Dog::breed`'s `GetById` response, not a reopened decision; see `src/server/protocol.rs`'s own doc comment for the full list of implementation-time completions beyond the design's proposed shape.
- **`ParentLookup`**: a three-way enum (`Parent(id)`/`NoParent`/`ChildNotFound`) preserving the not-found/no-parent distinction this project's own PR #21 (`docs/PROJECT-STATUS.md`'s `Parent::parent` fix) restored in-process — deliberately not collapsed into a two-way `Option` at the wire boundary.

## Requirements

- `SERVER-001-FR-001`: **`ConnectionStore` trait and `dispatch`** (`src/server/mod.rs`) — one trait covering `get`/`filter_eq`/`scan_field`/`update_field`/`parent`/`children`/`neighbors`; `dispatch(store, request) -> Response` translates one `Request` into one `Response` with no I/O of its own, independently testable.
- `SERVER-001-FR-002`: **Length-prefixed `bincode` framing** (`src/server/framing.rs`) — a 4-byte little-endian length prefix, then a `bincode`-encoded payload, over any `Read`/`Write`. A length prefix exceeding `MAX_FRAME_BYTES` (16 MiB) is rejected *before* any payload buffer is allocated. Since v0.9.1 the payload is encoded and decoded by `crate::codec` (`STORAGE-018`): fixint, little-endian, no limit — the same bytes as before — and a payload with bytes left over after the message is `FrameError::Encoding`, not silently accepted.
- `SERVER-001-FR-003`: **Thread-per-connection serving** (`src/server::serve`) — accepts connections on a `TcpListener` and spawns one OS thread per connection, each holding only `&S: ConnectionStore`; all coordination is whatever locking the wrapped store already does internally (no new lock introduced at this layer). `TCP_NODELAY` is set on every accepted connection — see FR-006.
- `SERVER-001-FR-004`: **`Dog` domain adapter** (`src/server/dog.rs`) — wraps `S: DogStore + ConcurrentStore` (in practice `ProductionStore`). `get`/`scan_field`/`update_field`/`neighbors` map onto `DogStore`/`ConcurrentStore`'s existing methods; `filter_eq`/`parent`/`children` report `ErrorCode::Unsupported` (no equality-index or directed relation exists for `Dog` in-process either).
- `SERVER-001-FR-005`: **`Order`/`Customer` domain adapter** (`src/server/order.rs`, behind `research`) — wraps `GenericProductionStore<OrderProductionStack>`. `get`/`filter_eq`(`Status`)/`scan_field`+`update_field`(`Amount`)/`parent`/`children`(`BelongsToCustomer`) map onto its existing generic methods; `neighbors` reports `ErrorCode::Unsupported` (no symmetric relation exists for `Order`/`Customer`).
- `SERVER-001-FR-006`: **A real, measured Nagle/delayed-ACK fix** — a synchronous request/response protocol pays a real ~40ms-per-round-trip cost with Nagle's algorithm left at its default on either side of the connection; confirmed directly (a concurrent-client integration test went from ~36s to well under a second after disabling it). `TCP_NODELAY` is set server-side (`handle_connection`) and documented as required client-side too.
- `SERVER-001-FR-007`: **A minimal server binary** (`src/bin/dog_server.rs`, `required-features = ["server"]`) — a real, runnable `Dog`-domain server seeded from a small hand-written sample dataset (not `generator`, which is research-gated), so it builds under `server` alone.
- `SERVER-001-FR-008`: **Real end-to-end test coverage**, not just `dispatch`'s in-process logic — `tests/server_dog_integration.rs` and `tests/server_order_integration.rs` drive a real `TcpListener`/`TcpStream` pair (a background thread with a real socket, not a genuinely separate OS process — see those files' own module docs on what that does and doesn't prove) through `GetById`/`FilterEq`/`ScanField`/`UpdateField`/`Parent`/`Children`/`Neighbors`, including the domain-appropriate `Unsupported` cases.
- `SERVER-001-FR-009`: **A flagship concurrent-client stress test**, matching this crate's established rigor — `tests/server_dog_integration.rs`'s `concurrent_clients_over_the_wire_match_a_sequential_replay` runs 8 real client connections × 200 interleaved `GetById`/`UpdateField` requests each against a small contended id pool, verified via sequential-replay linearizability against a fresh in-memory reference (the same pattern `run_concurrency_stress_test`/`production_integration.rs` use), with the write-log append made atomic with the request's round trip — the same fix (and the same false-positive failure mode) `run_concurrency_stress_test`'s own doc comment already documents.
- `SERVER-001-FR-010` (v0.2.0, ADR-0011): **Schema discovery** — `Request::DescribeSchema`/`Response::Schema(DomainSchema)`; `ConnectionStore::describe(&self) -> DomainSchema` (infallible, no store access needed). Both domain adapters implement it, reporting every named field's `ValueKind` and per-operation `FieldCapabilities` (`filter_eq`/`scan`/`update`) honestly — including fields that exist but support none of the three (`Order`'s `created_at_unix_ms`/`discount_cents`) — plus `RelationCapabilities` (`parent_children`/`neighbors`). Field *tags* remain the wire addressing scheme; this adds runtime discovery of what a compile-time client already knows, not a new addressing scheme.
- `SERVER-001-FR-011` (v0.2.0, ADR-0011): **Schema discovery is genuinely usable, not just descriptive** — `tests/server_dog_integration.rs`'s `a_schema_driven_client_discovers_and_uses_the_age_field` and `tests/server_order_integration.rs`'s `a_schema_driven_client_discovers_and_uses_the_status_field` each drive a real client that starts with zero compile-time field-tag knowledge, calls `DescribeSchema`, finds a field by name, and completes a real `UpdateField`/`FilterEq` using only the discovered tag.
- `SERVER-001-FR-012` (v0.3.0): **`Employee` domain adapter** (`src/server/employee.rs`, behind `research`) — wraps `GenericProductionStore<EmployeeProductionStack>`. `get`/`filter_eq`(`Department`)/`scan_field`+`update_field`(`SalaryCents`)/`parent`/`children`(`ReportsTo`)/`neighbors`(`CollaboratesWith`) all map onto real generic methods — the first domain adapter where no relation-kind request is `Unsupported`, since `Employee` (`src/generic_spike/employee_impl.rs`) is self-referential on both a directed (`reports_to`) and a symmetric (`collaborates_with`) relation at once. Building this adapter required a real fix one layer down: `Reversed` (the `ChildOf`-forwarding wrapper) never forwarded `Neighbors`, and `GenericProductionStore` had no `neighbors` method — neither had been needed by any domain stacking only one relation kind. Both fixed directly in `src/generic/{store,production}.rs`; see `docs/decisions/ADR-0009-generic-schema-design-proposal.md`'s "Acceptance and implementation" addendum for the full account. `crate::generic`'s own trait/wrapper design is otherwise unchanged.
- `SERVER-001-FR-013` (v0.3.0): **Real end-to-end coverage of `Employee`, including the first all-relations-real case** — `tests/server_employee_integration.rs` drives a real `TcpListener`/`TcpStream` pair through `GetById`/`FilterEq`/`ScanField`/`UpdateField`/`Parent`/`Children`/`Neighbors`, all succeeding (no domain-shaped `Response::Err`), plus the empty-but-real cases (`Parent` on a record with no manager returns `Response::NoParent`, not an error; `Neighbors` on a record with no collaborators returns an empty `RecordList`, not an error) and a schema-driven test (matching FR-011's pattern) confirming `DescribeSchema` reports both `RelationCapabilities` as `true` for the first time.
- `SERVER-001-FR-014` (v0.4.0): **Throughput/latency benchmark** (`benches/server.rs`, `required-features = ["server", "research"]`) — a custom, non-Criterion harness (matching `benches/concurrency.rs`'s own shape, for the same reason: aggregate ops/sec across concurrently-running threads isn't what Criterion's `b.iter` model measures) that puts a real `TcpListener`/`TcpStream` pair in the timed path for the first time in this crate. Measures, per domain (`Dog`, `Order`/`Customer`, `Employee`): single-connection, zero-contention `GetById` round-trip latency (average of 5,000 sequential requests), and aggregate throughput under a thread-per-connection sweep (1/4/8/16 concurrent client connections, each a real socket, `Barrier`-synchronized, ops/sec from the slowest thread's elapsed time). Uses a small, fixed 20-id pool per domain (matching the flagship concurrent-client stress test's own contended-pool precedent), not this crate's usual 1K/100K/1M `SIZES` sweep — see the bench's own module docs for why. Results in `RESULTS.md`'s `## Server / query layer` section. **Extended, v0.8.0**: see FR-018 — the same latency/throughput measurement now also covers `Request::Transaction`.
- `SERVER-001-FR-015` (v0.5.0): **A real, reusable schema-driven client** (`src/server/client.rs`'s `SchemaDrivenClient`, unconditional under `server` — no domain-specific code, so no `research` gate) — promotes the one-off schema-driven logic each of `tests/server_{dog,order,employee}_integration.rs`'s own schema-driven tests had reimplemented (FR-011/FR-013) into real library API. `connect` sends `Request::DescribeSchema` first and keeps the result; every subsequent method (`get`/`filter_eq`/`scan`/`update`/`parent`/`children`/`neighbors`) is addressed by field *name*, not a compile-time `FieldRef` constant — `get` returns `(String, ScanValue)` pairs, not `(FieldRef, ScanValue)`, for the same reason. `filter_eq`/`scan`/`update`/`parent`/`children`/`neighbors` each check the relevant `FieldCapabilities`/`RelationCapabilities` from the discovered schema *before* sending anything, returning `ClientError::Unsupported` locally rather than paying a round trip for something the schema already ruled out — an optimization, not a trust boundary: `dispatch` still enforces the identical rules independently on the server side. An unrecognized field name is `ClientError::UnknownField`, checked the same way, no round trip.
- `SERVER-001-FR-016` (v0.6.0, ADR-0012): **Authentication/authorization** (`AuthConfig`/`TokenClass` in `src/server/mod.rs`, `Request::Authenticate`/`ErrorCode::Unauthenticated`/`ErrorCode::Unauthorized` in `src/server/protocol.rs`) — implements `docs/design/SERVER-AUTH-DESIGN.md`'s `AUTH-FR-001` through `AUTH-FR-007` in full. `serve` takes an `AuthConfig` (two optional tokens, `read_only`/`read_write`, each mapping to a `TokenClass`); `handle_connection` gates its own request loop on per-connection state (`Option<TokenClass>`), never touching `dispatch` or the shared store. A connection with no successful `Authenticate` yet is rejected with `ErrorCode::Unauthenticated` for every other request kind, including `DescribeSchema` (the design's own "uniform rule" resolution of its one open question). `TokenClass::ReadOnly` is further rejected from `Request::UpdateField` with `ErrorCode::Unauthorized`; every other request kind succeeds for both classes once authenticated. `AuthConfig::check` compares the presented token against every configured token via `subtle::ConstantTimeEq`, never short-circuited on the first match (a new, narrow dependency — `Cargo.toml`'s own comment explains why this is the one place this spec departs from "avoid new dependencies"). `AuthConfig::default()` (no tokens configured) leaves every connection pre-authenticated at `TokenClass::ReadWrite` — `AUTH-FR-007`'s exact backward-compatibility bar; every pre-existing call site (`tests/server_{dog,order,employee}_integration.rs`, `tests/server_schema_driven_client.rs`, `benches/server.rs`) now passes `AuthConfig::default()` explicitly and required zero other change. `src/bin/dog_server.rs` uses `AuthConfig::from_env()` instead, reading `SERVER_AUTH_READ_ONLY_TOKEN`/`SERVER_AUTH_READ_WRITE_TOKEN` from the process environment at startup (`AUTH-FR-005`) — the exact env var names are this spec's own implementation-time decision, left open by the design. `tests/server_auth_integration.rs` (`required-features = ["server"]` — Dog domain alone is sufficient, no domain-specific behavior is under test) covers every functional acceptance criterion `SERVER-AUTH-DESIGN.md` names over a real socket; `src/server/mod.rs`'s own unit tests additionally include a timing measurement comparing `AuthConfig::check`'s latency for tokens that differ at the first byte vs. the last byte, the empirical evidence `AUTH-FR-006` calls for.
- `SERVER-001-FR-017` (v0.7.0, ADR-0013): **Atomic multi-operation transactions** (`Request::Transaction`/`TransactionOp`/`Response::TransactionFailed`/`ErrorCode::RecordNotFound` in `src/server/protocol.rs`; `ConnectionStore::apply_transaction` in `src/server/mod.rs`) — implements `docs/design/SERVER-TRANSACTION-DESIGN.md`'s `TXN-FR-001` through `TXN-FR-007` essentially as designed. A `Request::Transaction { updates: Vec<TransactionOp> }` batches several `UpdateField`-shaped writes; every operation's precondition (id exists, field known and updatable, value type matches) is checked before any write is applied — `Response::Ok` on full success, `Response::TransactionFailed { index, code, message }` naming the first failing operation on any failure, with no write applied in that case. `TokenClass::ReadOnly` is rejected with `ErrorCode::Unauthorized` for the whole request, evaluated before any operation in the batch (`handle_connection`'s gating extends the same `matches!` check `UpdateField` already used to `Transaction`). The atomicity/isolation mechanism is a new storage-layer primitive, not just a server-layer addition — `crate::production::TransactionalStore` (`STORAGE-011` v0.2.0, `Dog`) and `crate::generic::production::GenericProductionStore::with_exclusive` (`STORAGE-012` v0.3.0, `Order`/`Employee`) each let a caller hold the store's existing internal lock across multiple logical operations instead of once per call; each domain adapter's `apply_transaction` validates every operation, then applies every operation, inside one such closure, exploiting this crate's own "no runtime deletion, fixed schema" invariant so no undo log is needed. `tests/server_transaction_integration.rs` (`required-features = ["server"]` — Dog domain alone is sufficient) covers every functional acceptance criterion over a real socket (full success; failure at the first, middle, and last operation, each applying nothing; a malformed value; `ReadOnly` rejection before any operation is evaluated) plus a flagship concurrent stress test proving no lost updates/corruption under real contention (sequential-replay linearizability, the same established pattern `SERVER-001-FR-009` uses) — see that test file's own module doc comment for why a per-instant "never observed half-written" check was tried and dropped as unable to distinguish a real bug from an inherent protocol limitation (no multi-field read exists to observe two fields at one consistent instant).
- `SERVER-001-FR-018` (v0.8.0): **Transaction benchmark coverage** (`benches/server.rs`) — extends FR-014's harness with a directly-comparable `{domain}-txn` row set: the same environment, `THREAD_COUNTS`, `LATENCY_ITERATIONS`, `OPS_PER_THREAD`, and 20-id pool as the existing `GetById` measurement, the only difference being each request is a two-op `Request::Transaction` (two distinct ids from the pool, both set to the same new value) instead of one `GetById`. Bounded, additive extension of FR-014's already-accepted scope — no new FR was needed for the original benchmark's own coverage, and none is needed here either beyond naming the addition; no new dependency, no new test. Results in `RESULTS.md`'s `## Server / query layer` section, `### \`Request::Transaction\` follow-up` subsection: no meaningful latency or throughput cost was found relative to plain `GetById` at this benchmark's scale, on this session's shared container — consistent with the design's own prediction that the longer-held lock is real but swamped by the network/framing cost this whole benchmark exists to isolate.
- `SERVER-001-FR-019` (v0.9.0, ADR-0014): **Native transport encryption** (`TlsConfig` in `src/server/mod.rs`; `src/server/pem.rs`, new) — implements `docs/design/SERVER-TLS-DESIGN.md`'s `TLS-FR-001` through `TLS-FR-008` as revised (depending on `rusty_tls`, not `rustls` directly — see that design's own "Ecosystem check"). `serve` gains a fourth parameter, `tls: Option<TlsConfig>`; `None` reproduces pre-v0.9.0 plaintext behavior exactly with zero other change, the same backward-compatibility bar `AuthConfig::default()` set for v0.6.0. When configured, `handle_connection` performs a TLS server handshake (`rusty_tls::TlsAcceptor::accept`) before any framed `Request`/`Response` traffic, including `Authenticate`, is ever read or written — `dispatch`/`ConnectionStore` remain completely unaware transport encryption exists, and `src/server/framing.rs` required zero changes (already generic over `Read`/`Write`, verified by reading the source, not assumed). `TlsConfig::new` takes DER-encoded certificate chain + private key directly (`rusty_tls::TlsAcceptor::new`'s own shape); `TlsConfig::from_pem_files`/`TlsConfig::from_env` (mirroring `AuthConfig::from_env`) decode the common PEM-file case via `src/server/pem.rs`, a small hand-written PEM/base64 decoder (not a new dependency — base64 decoding is a fully-specified, deterministic transform with no invisible-to-testing correctness property, unlike `AuthConfig::check`'s constant-time comparison, which *is* a dependency, `subtle`, for exactly that reason).

  **The real implementation-time finding this round surfaced**: `handle_connection`'s existing plaintext path splits a connection into independent read/write halves via `TcpStream::try_clone` (two real OS-level socket handles); `rusty_tls::TlsServerStream`'s `rustls::ServerConnection` state can't be split that way — a read and a write both need to reach through the *same* connection object. Resolved with a new `ReadHalf`/`WriteHalf` enum pair: the `Plain` variant keeps the existing `try_clone` split unchanged (zero behavior change, zero regression risk to already-benchmarked code); the `Tls` variant shares one `Rc<RefCell<TlsServerStream<TcpStream>>>` between both halves — `Rc`/`RefCell`, not `Arc`/`Mutex`, since each connection is served by exactly one OS thread (thread-per-connection, unchanged), so a single-threaded runtime borrow check is sufficient and the `Rc` itself never needs to be `Send` (it's constructed entirely inside the already-spawned connection thread, never crossing a thread boundary itself).

  `tests/server_tls_integration.rs` (`required-features = ["server"]` — Dog domain alone is sufficient) covers every functional acceptance criterion over a real socket: a real client (via `rusty_tls::TlsStream`, the same ecosystem crate's client-side half — not a hand-rolled test client) completing a full request/response round trip over TLS; `TlsConfig` composing with `AuthConfig` (`Authenticate`'s token now travels encrypted); a plain connection to a `TlsConfig`-configured server never getting a valid response; and the one piece of direct, non-assumed evidence the design's whole purpose depends on — a byte-recording `TcpStream` wrapper capturing the real bytes a TLS client puts on the wire, asserting the plaintext `Authenticate` token is not present anywhere in that capture. This suite deliberately does not re-prove TLS correctness itself (wrong hostname, expired cert, untrusted root, ...) — `rusty_tls` already carries its own hermetic rejection-path suite for that; this suite's job is proving this crate's own wiring is correct.
- `SERVER-001-FR-020`: **Protocol version and optional `Hello`** (v0.10.0, ADR-0022, `docs/design/SERVER-PROTOCOL-VERSION-DESIGN.md`, `PROTO-FR-001`–`008`). `pub const PROTOCOL_VERSION: u32 = 2` in `src/server/protocol.rs`; version 1 is retroactively the v0.9.1 shape — what a client that never says hello speaks. `Request::Hello { protocol_version: u32 }` and `Response::Hello { protocol_version: u32 }` are appended at declaration index 10 on both enums (golden bytes for either `Hello { 2 }`: `0a 00 00 00 02 00 00 00`); every v0.9.1 golden vector is unchanged. The hello is optional and, if sent, must be the first frame on the connection: `handle_connection` answers it itself before the `Authenticate` intercept and the authentication gate (`PROTO-FR-003`, the `ADR-0012` precedent) with `Response::Hello { min(client, PROTOCOL_VERSION) }`; a `Hello` with version 0, or any `Hello` that is not the connection's first frame, is `Err { Malformed }` with the connection left open (`PROTO-FR-004`); `dispatch` maps `Hello` to `Unsupported` exactly as it does `Authenticate`. A client that never sends `Hello` is served exactly as at v0.9.1 (`PROTO-FR-002`). Four compatibility rules, written into `protocol.rs`'s module docs and binding on every later version (`PROTO-FR-005`): (i) append-only — variants are never reordered, inserted, removed, or retyped; (ii) every variant records its introducing version in `protocol.rs`'s per-version table; (iii) a server sends a variant introduced at *N* only on a connection negotiated at ≥ *N*, answering with the nearest older shape otherwise; (iv) a client sends a request introduced at *N* only after negotiating ≥ *N*. At version 2 no variant is gated, so the server stores no negotiated version per connection — only whether the first frame has been read; the first version-3 variant adds the state and rule (iii)'s branch (`PROTO-FR-006`). `SchemaDrivenClient::connect` sends `Hello { PROTOCOL_VERSION }` before `DescribeSchema` and exposes `server_protocol_version()`; a server that answers anything but `Response::Hello` is `ClientError::UnexpectedResponse` (`PROTO-FR-007`). `framing.rs`, `MAX_FRAME_BYTES`, `crate::codec`, `benches/server.rs`, and every pre-existing integration suite are untouched (`PROTO-FR-008`) — they are version 1's regression test.
- `SERVER-001-FR-021`: **`SchemaDrivenClient` authentication** (v0.11.0). `SchemaDrivenClient::connect_authenticated(addr, token)` is `connect` with `Request::Authenticate { token }` sent between the `Hello` and the `DescribeSchema`, so the schema fetch runs on an authenticated connection — the token has to be a *constructor* argument because `AUTH-FR-002` gates `DescribeSchema` itself, so on an `AuthConfig`-configured server plain `connect` cannot succeed (it now fails with `ClientError::Server(Unauthenticated, ..)` rather than the previous `UnexpectedResponse("Schema")`, the one behavioral change to an existing path). `SchemaDrivenClient::authenticate(&mut self, token)` re-presents a token on an already usable connection, changing its class for every request that follows (`ReadOnly` → `ReadWrite` and back); a rejected token is `ClientError::Server(Unauthenticated, ..)` and leaves the class as it was, exactly the raw protocol's own `AUTH-FR-001` behavior. Neither learns the granted `TokenClass` — the server answers `Authenticate` with a bare `Response::Ok`. On a server with no tokens configured both are no-ops that succeed with any token (`AUTH-FR-007`). Plaintext only, as the client has always been (against a `TlsConfig`-configured server the plaintext `Hello` fails the handshake and the connection closes before any token is written). No wire change: `Authenticate` is a version-1 variant, so this is a client-library completion of FR-015 (the client) and FR-016 (authentication), not a protocol change; `PROTOCOL_VERSION` stays 2.
- `SERVER-001-FR-022`: **`SchemaDrivenClient` transport encryption** (v0.12.0). `SchemaDrivenClient::connect_with(addr, ConnectOptions)` is the general constructor — `connect` and `connect_authenticated` become `ConnectOptions::new()` and `ConnectOptions::new().token(..)` — and `ConnectOptions::tls(ClientTlsConfig)` makes the client reach a `TlsConfig`-configured server: the TCP connection is wrapped in a `rusty_tls::TlsStream` (the client-side half of the same ecosystem-wide `rustls` wrapper `TlsConfig` uses server-side, so this crate still never touches `rustls` directly — ADR-0014's seam) before the `Hello`, so the `Hello`, any token, the schema fetch, and every later request travel encrypted. `ClientTlsConfig::new(server_name, TrustPolicy)` carries the name the server's certificate must match (also sent as SNI) and the trust policy it is verified under — exactly the explicit client-side trust configuration ADR-0014's Consequences said a self-signed certificate would need; `rusty_tls::TrustPolicy` is re-exported from `server::client` so a caller can name one without depending on `rusty_tls`. `rusty_tls::TlsStream::new` performs no I/O — the handshake runs lazily under the first frame — so a server name or policy `rusty_tls` rejects outright is the new `ClientError::Tls(rusty_tls::Error)` before anything is sent, while a certificate the policy rejects, or a server that does not speak TLS, surfaces under the `Hello` as `ClientError::Frame(FrameError::Io(..))`; a plaintext `connect` against a TLS server fails the same way, before any token is written. Named, not mitigated: a TLS client against a *plaintext* server can block rather than fail (the server reads the ClientHello as a length-prefixed frame and waits for a payload that never comes) — true of any `rusty_tls` client, not specific to this one. Internally the client now holds one stream (`rusty_tls::TlsStream` cannot be split by `try_clone`, the same finding `ReadHalf`/`WriteHalf` resolved server-side at v0.9.0) and assembles each frame in memory before a single `write_all`, so the plaintext path still produces one write per request. `ClientError` gains the `Tls` variant (the one shape change to an existing type); no wire, protocol-version, server, or `Cargo.toml` change — a client-library completion of FR-015 (the client) and FR-019 (transport encryption).
- `SERVER-001-FR-023` (v0.13.0, ADR-0023): **Mutual TLS** — implements `docs/design/SERVER-MTLS-DESIGN.md`'s `MTLS-FR-001` through `MTLS-FR-008`. The client certificate is an *admission* gate, layered under FR-016's token gate, which still decides *class*: `TlsConfig::new_with_client_auth(cert_chain_der, private_key_der, client_ca_roots_der)` (on `rusty_tls::TlsAcceptor::new_with_client_auth`) makes every connection present a certificate chaining to one of the operator's own CA roots or fail the handshake — before any framed byte, `Authenticate` included, is read, on the same `TLS-FR-003` path as any other handshake failure; an admitted connection then starts exactly where `AuthConfig` says (unauthenticated with tokens configured, `ReadWrite` without — `AUTH-FR-007` behind the gate), and nothing ever reads the admitted certificate's contents. `TlsConfig::from_pem_files_with_client_ca(chain, key, client_ca)` decodes a CA file of one or more `CERTIFICATE` blocks with the existing `pem` module; `TlsConfig::from_env` honors an optional third variable, `SERVER_TLS_CLIENT_CA_PATH` — set while the chain/key pair is not, it is `Some(Err(TlsConfigError::Io(NotFound, ..)))` naming the variables, never a silent plaintext or no-mTLS server (the decision table is factored as `from_env_values` so a unit test drives it without touching the process environment); `TlsConfig::requires_client_certificate()` reports the mode, and `dog_server` prints it. An empty root set is `TlsConfigError::Tls(InvalidClientCaRoots)` at construction. Client side, `ClientTlsConfig::with_identity(cert_chain_der, private_key_der)` / `with_identity_pem_files(chain, key)` (reporting `TlsConfigError`'s `Io`/`Pem` shapes) and `has_identity()`; `SchemaDrivenClient::connect_with` selects `rusty_tls::TlsStream::new_with_client_identity` when an identity is present. `ClientTlsConfig`'s `Debug` is hand-written to print whether an identity is present, never its bytes. A client with no identity, or one the server's roots reject, fails under the `Hello` as `ClientError::Frame(FrameError::Io(..))` (the FR-022 shape); an identity `rusty_tls` rejects outright is `ClientError::Tls` before any I/O. `handle_connection`, `serve`, `AuthConfig`, `TokenClass`, `framing.rs`, the codec, and `PROTOCOL_VERSION` (still 2) are unchanged — the acceptor carries the policy — and `Cargo.toml` is untouched (`rcgen`, already a dev-dependency, issues the tests' throwaway CA and signed leaf). Still out of scope, as the design named: class derived from the certificate (the pinned `rusty_tls` exposes no peer certificate; the future revisit), revocation without a restart, issuance/distribution.
- `SERVER-001-FR-024` (v0.14.0, ADR-0024): **Transaction sessions, protocol version 3** — implements `docs/design/SERVER-TRANSACTION-SESSION-DESIGN.md` Part A's `SESS-FR-001` through `SESS-FR-009`. The multi-round-trip shape `ADR-0013` deferred, without the lock it deferred it for: `Request::Begin` (index 11) opens a per-connection buffer; while it is open every `Request::UpdateField` the gates admit is *staged* — pushed onto the buffer and answered `Response::Staged { index }` (index 11), nothing applied, no lock taken, no validation — and `Request::Commit` (12) hands the buffer to `ConnectionStore::apply_transaction` exactly as a `Request::Transaction` would (`Response::Ok`, or `Response::TransactionFailed` naming the *staged* index, nothing applied) and closes the session either way; `Request::Rollback` (13) or a disconnect discards it. The only lock a session ever takes is `apply_transaction`'s own at `Commit`, for the interval a `Transaction` of the same batch holds it (`SESS-FR-003`). Misuse is a typed error with the connection open — `ErrorCode::NoSession` (6), `SessionOpen` (7, a second `Begin` or a `Transaction` inside a session), `SessionFull` (8, the `MAX_STAGED_OPS + 1`-th write, not staged, session still open; `pub const MAX_STAGED_OPS: usize = 4096`). Gating is unchanged and per request: staging and `Commit` need `TokenClass::ReadWrite` (`Commit` joins `UpdateField`/`Transaction` in `handle_connection`'s `ReadOnly` gate), `Begin`/`Rollback` need authentication. Reads inside a session — from any connection, the session's own included — see committed state only (`SESS-FR-007`; no read-your-writes, named). These are the first *gated* variants, the moment `ADR-0022` named as its own trigger: `PROTOCOL_VERSION` is 3, the version table gains row 3, `handle_connection` keeps the negotiated version per connection at last (1 for a silent client) and answers `Begin`/`Commit`/`Rollback` on a connection below 3 with `Malformed` (compatibility rule 3 — no version-3 response shape is ever sent on an older connection, since none can arise without a `Begin`), `dispatch` maps the three to `Unsupported` as it does `Authenticate`/`Hello`, and every version-1/2 golden vector is unchanged (rules 1–2). Client side, `SchemaDrivenClient::begin()` is the library's first version-gated API (rule 4): `ClientError::Unsupported("session")` with no frame sent below 3, otherwise a `Session` borrowing the client — `Session::update(id, field_name, value)` runs the same client-side capability checks as `update` then stages and returns the index, `commit(self)` applies (`ClientError::TransactionFailed { index, code, message }`, an additive variant, on rejection), `rollback(self)` discards, and `Drop` sends a best-effort `Rollback` if neither was called. No adapter, store, `ConnectionStore`, framing, codec, or `Cargo.toml` change; `benches/server.rs` and every pre-existing suite unchanged (they are versions 1–2's regression test).
- `SERVER-001-FR-025` (v0.15.0, ADR-0025): **Crash-atomic batches via an opt-in redo journal** — implements `docs/design/SERVER-TRANSACTION-SESSION-DESIGN.md` Part B's `JRN-FR-001` through `JRN-FR-009`. A domain adapter built with `with_journal(store, journal_path)` (`DogConnectionStore`, `OrderConnectionStore`, `EmployeeConnectionStore`; `SERVER_TXN_JOURNAL_PATH` in `dog_server`) makes every batch — a `Request::Transaction` or a session `Commit`, never a single `UpdateField` (`JRN-FR-007`) — survive a crash of the server process whole: inside the same `with_exclusive` closure the batch already held, the validated batch is appended to `src/server/journal.rs`'s `BatchJournal` and `fsync`'d *before* the first slot write (`JRN-FR-002`), applied, and, once the journal has grown past `JOURNAL_CHECKPOINT_BYTES` (1 MiB), checkpointed — the store's own files flushed first (`CheckpointFlush`, a server-layer trait implemented for exactly the three exclusive store types, so no storage module changes), then the journal truncated (`JRN-FR-004`). `with_journal` replays every complete entry on open (an idempotent overwrite per operation, so redo suffices and no prior value is recorded — the "no runtime deletion, fixed schema" invariant `ADR-0013` already relied on), flushes, and truncates; a torn tail — a crash mid-append, before the `fsync` returned — is dropped and truncated away, while a complete entry that does not decode, a bad magic or version, or a batch the store cannot re-apply is a typed `JournalError` and the adapter does not start (`JRN-FR-003`). Format `TXNJRNL\0`, `u32` version 1, entries `[u32 len][crate::codec(Vec<TransactionOp>)]` — `STORAGE-018`'s encoding (`JRN-FR-006`). The guarantee (`JRN-FR-005`): after a crash at any instant, the next `with_journal` open leaves every batch answered `Ok` either fully applied or fully replayed, never partial, provided the filesystem honors `fsync`/`msync`; a batch whose `Ok` was never sent may or may not be present, as a single `UpdateField` today. Placement at the adapter because only it both sees a batch and can replay one operation; the store knows neither `TransactionOp` nor `FieldRef`. Without a journal every adapter behaves exactly as at v0.14.0 (`TXN-FR-007`'s named gap stands there, restated below). The one wire addition is `ErrorCode::Journal` (index 9) — a journal append failure is the batch's failure, `Response::TransactionFailed { index: 0, code: Journal }`, with nothing applied — and per compatibility rule 2 an appended variant bumps the version: **`PROTOCOL_VERSION` is 4**, the table gains row 4, and per rule 3 `handle_connection` rewrites `Journal` to `Unsupported` on a connection negotiated below 4 (`downgrade_for_version`, the first use of the "nearest older shape" clause). `ADR-0025` said "the next index; version-gated like any appended code" without naming the bump; rule 2 requires it, and this is recorded as the one implementation-time clarification, not a deviation. Cost: one `fsync` per batch, paid only by journaled adapters and measured by the new `dog-jrnl-txn` rows in `benches/server.rs` (see `RESULTS.md`) — *since v0.17.0 (FR-027) one `fsync` per group of concurrent batches, outside the exclusive section*. No `Cargo.toml`, store, storage-format, framing, or `ConnectionStore`-signature change.
- `SERVER-001-FR-026` (v0.16.0): **Pre-hello reconnect fallback in `SchemaDrivenClient`, default-on** — `ADR-0022`'s third revisit trigger (*a pre-hello server is found deployed against a hello-sending client — a reconnect-without-hello fallback in the client library becomes worth its heuristic*), taken at the owner's explicit call as default-on, over the design's own "not while none is deployed" stance and this document's recommendation to close it; recorded as the owner's decision, not a finding. `SchemaDrivenClient::connect_with` now treats the one shape a pre-hello server produces — the peer closing the connection under the `Hello` frame with no reply, an end-of-stream/reset/abort-class I/O error — as that server: it opens a second connection, sends no `Hello`, reports `server_protocol_version()` as 1, and every version-gated API (`begin`) refuses from there with `Unsupported`. The heuristic is bounded: it fires at most once per `connect_with`, only under the `Hello`, and only on that error class — never on a reply (a server that answers anything is a versioned server; `Malformed` keeps its meaning), never on a connect failure, and never on a second failure (a server that dies under *any* first frame fails the second attempt too, and that error is returned). `ConnectOptions::require_hello()` turns it off, restoring the pre-v0.16.0 `ClientError::Frame(FrameError::Io(..))`. The connection setup (TCP, `TCP_NODELAY`, the optional TLS wrap and identity) is factored into one `open_transport` so both attempts are identical. The one behavior change to an existing path: `connect` against a pre-hello server now succeeds where it failed. Cost, named: a server that genuinely dies under the first frame now costs one extra connect before the same error surfaces. No wire, server, `Cargo.toml`, or `PROTOCOL_VERSION` change; every server-side path unchanged.
- `SERVER-001-FR-027` (v0.17.0, ADR-0026): **Journal group commit** — implements `docs/design/SERVER-JOURNAL-GROUP-COMMIT-DESIGN.md`'s `GRP-FR-001` through `GRP-FR-008`. On a journaled adapter the batch journal's `fsync` no longer runs inside the store's exclusive section: `apply_transaction` validates with the store's ordinary per-call reads (sound by the no-runtime-deletion invariant — existence never changes and field/type validity is a pure function of the request), appends the batch under the journal's own mutex taking a sequence, waits until the journal is durable through that sequence, then applies under `with_exclusive` in sequence order, and checkpoints only when nothing later has been appended. The durability wait is a leader/follower group commit (`src/server/journal.rs`'s `CommitGroup`): the first waiter that finds no `sync_data` in flight becomes the leader, reads how far to sync as late as possible, and syncs once for every entry appended before its `sync_data` starts; the rest wait on a condvar; no timer, no delay, no thread — a lone connection is its own leader and pays exactly v0.15.0's one `fsync`. Applies go through a turn gate (`next_apply`), free because durability is monotone in sequence, so the order the journal replays after a crash is the order the store applied — two batches on one slot cannot swap winners across a crash. A checkpoint (`JRN-FR-004`) is offered to a batch only when the journal is past `JOURNAL_CHECKPOINT_BYTES` *and* it is the last one appended; the truncation is re-checked under the lock after the store flush and withheld if anything appended meanwhile. Failure semantics per batch are v0.15.0's: a write failure at append fails that batch alone; an `fsync` failure fails every batch the leader covered, each answered `TransactionFailed { index: 0, code: Journal }` with nothing applied, and the next batch syncs again — those entries may or may not be on disk and would replay on the next open, exactly `JRN-FR-005`'s "never answered `Ok`, may or may not be present". A turn guard releases the gate on unwind. The unjournaled path is untouched (validate then apply under one exclusive section); the journal format, `open`'s replay and torn-tail handling, `CheckpointFlush`, `JournalError`, `TransactionalStore`, `ConnectionStore`, the wire, and `PROTOCOL_VERSION` (4) are unchanged. Measured (`RESULTS.md`, this container): single-connection `dog-jrnl-txn` latency 304.3 µs (v0.15.0: 320.7); throughput 3,169 / 5,906 / 14,276 / 15,322 batches/s at 1 / 4 / 32 / 64 connections (v0.15.0: 3,182 / 3,843 / 3,395 / 3,337) — the `fsync` now scales with concurrency instead of serializing it, and readers and single writers no longer wait behind it.
- `SERVER-001-FR-028` (v0.18.0, ADR-0027): **Read-your-writes sessions, protocol version 5** — implements `docs/design/SERVER-SESSION-READ-YOUR-WRITES-DESIGN.md`'s `RYW-FR-001` through `RYW-FR-008`. `Request::BeginWith { flags: u32 }` is appended at index 14, introduced at protocol version 5 (`PROTOCOL_VERSION` is 5, the table gains row 5, a golden vector pins `0e 00 00 00 01 00 00 00`); `SESSION_READ_YOUR_WRITES = 1`; `flags: 0` is exactly `Begin`; any other bit is `Malformed` and opens nothing; `SessionOpen` while one is open; `Malformed` on a connection negotiated below 5 (compatibility rule 3, as `Begin` below 3); a client sends it only after negotiating ≥ 5 (rule 4). While a read-your-writes session is open, the connection's own `GetById` is served as today and then passed through `overlay_staged` before it is sent: for each field the committed record carries, the *last* staged write with that id and field replaces the value — only when the staged value's kind equals the committed one's **and the schema marks the field updatable** (the `update`-capable tags are read once from `describe()` at `BeginWith` and kept with the session). A missing id stays `NotFound`, an absent field, a kind mismatch, and a read-only field are ignored — each would fail at `Commit`, and the read never pretends otherwise. Set reads (`ScanField`, `FilterEq`, the relation reads), plain `Begin` sessions, older clients, and every other connection keep `SESS-FR-007`'s committed-state reads; a connection with no session takes no new branch; the overlay is a pure function linear in the buffer, run outside every lock on the connection's own thread. `dispatch` maps `BeginWith` to `Unsupported` as it does `Begin`. Client: `SchemaDrivenClient::begin_read_your_writes()` (`ClientError::Unsupported("read-your-writes session")` below 5, no frame sent), `Session::get(id)` on every session — a `Session` borrows the client mutably, so before this no read at all was reachable through the library while one was open; on a plain session it reads committed state — and `Session::read_your_writes()`. No new `Response` variant or `ErrorCode`, so `downgrade_for_version` is unchanged; no store, adapter, `ConnectionStore`, or `Cargo.toml` change; the unknown-index probe in `tests/server_protocol_version.rs` moves to 15. One clarification recorded against the design: the overlay also skips fields the schema marks non-updatable (the design's kind rule did not cover a read-only field of the right kind, such as `Dog::breed`), for the same reason the kind rule exists — a write `Commit` would refuse must not be shown.

## Data/state and invariants

- No new persistent state or on-disk format — the server process wraps an existing durable store; every byte on disk is written by `ProductionStore`/`GenericProductionStore` exactly as it already was, including every write a `Request::Transaction` applies (same field-write path as a single `UpdateField`, just under a longer-held lock).
- Per-connection state is limited to the TCP stream and its read/write buffers plus (since v0.6.0) `Option<TokenClass>`, (since v0.9.0) which `ReadHalf`/`WriteHalf` variant it's speaking, and (since v0.10.0) one `bool` — whether the connection's first frame has been read, which is all `Request::Hello` needs at protocol version 2; the negotiated version itself is not stored until a gated variant exists (FR-020) — no session, no per-client cursor, no cross-request server-side state. `Request::Transaction` adds none of its own: it's one request/response round trip like every other kind, just one that happens to carry more than one logical operation (`SERVER-TRANSACTION-DESIGN.md`'s own "Non-goals"). TLS handshake/session state (v0.9.0) lives inside `rusty_tls::TlsServerStream`, held for the connection's own lifetime the same way — never shared across connections, never touching the wrapped store.
- Field tags are fixed at compile time per adapter (constants in `dog.rs`/`order.rs`), not negotiated at connection time.
- `TransactionalStore::with_exclusive`/`GenericProductionStore::with_exclusive` (v0.7.0) reuse each store's existing internal lock, held for a longer, still request-bounded critical section — no new lock, no new coordination primitive, matching ADR-0010's own "no new lock at this layer" principle.
- `rusty_tls::TlsAcceptor` (v0.9.0, wrapped by `TlsConfig`) is built once at server startup and shared across every connection thread `serve` spawns, the same lifecycle `AuthConfig` already uses for its own configured tokens — no new lock at that level either. Per-connection, the TLS path's `ReadHalf`/`WriteHalf` share one `Rc<RefCell<TlsServerStream<TcpStream>>>` (not `Arc`/`Mutex`): a real, new coordination primitive, but a purely local, single-threaded one — each connection is served by exactly one OS thread (thread-per-connection, unchanged) — not a lock visible to, or contended by, any other connection.

## Errors, failure, recovery, and observability

- `dispatch` never panics on a well-formed but semantically invalid request (unknown field, unsupported operation, malformed value) — it returns `Response::Err { code, message }` with one of six `ErrorCode` variants (`UnknownField`/`Unsupported`/`Malformed`/`Unauthenticated`/`Unauthorized`/`RecordNotFound`, the last added at v0.7.0, FR-017; the two before it at v0.6.0, FR-016). A failed `Request::Transaction` returns `Response::TransactionFailed { index, code, message }` instead of `Response::Err` — same never-panics discipline, one more field naming which operation failed.
- `handle_connection` never panics on a malformed or oversized frame, or on a client disconnecting mid-request — the connection simply ends (`FrameError`, an ordinary `Result::Err`, not a panic). A rejected `UpdateField`/`Transaction` (wrong `TokenClass`) or a failed `Authenticate` (wrong/no token) does not end the connection — only that one request is rejected; the connection stays open (v0.6.0/v0.7.0).
- One bad `accept()` doesn't take down `serve`'s loop; one connection's error doesn't affect any other connection, since the only shared state is the wrapped store itself, already safe for concurrent access.
- Out of scope, named rather than silently assumed solved: structured logging/metrics, graceful shutdown/drain, a health-check RPC. Also out of scope, named by `SERVER-AUTH-DESIGN.md` rather than silently assumed solved: rate-limiting failed authentication attempts, lockout after N failures (the third item that line carried, an audit log of authentication attempts, was taken at v0.19.0 — FR-029 / `ADR-0029`). Also out of scope, named by `SERVER-TRANSACTION-DESIGN.md` rather than silently assumed solved (v0.7.0): crash-atomicity across a batch (a process crash between two of a batch's writes landing on stable storage can leave a partial batch durably applied — see "Security, privacy, and compatibility" below), and a maximum batch size beyond the existing `MAX_FRAME_BYTES` framing bound. Also out of scope, named by `SERVER-TLS-DESIGN.md` rather than silently assumed solved (v0.9.0): TLS session resumption/ticket policy, OCSP stapling, cipher-suite pinning beyond `rusty_tls`'s own safe defaults (its `finish_config` already sets a real session-ticket producer, so working TLS 1.3 resumption comes for free without this spec deciding anything about it); certificate provisioning/rotation automation; mTLS.
- A connection that fails the TLS handshake (v0.9.0) is dropped cleanly, no panic, with no special-casing needed: `rusty_tls::TlsAcceptor::accept` performs no I/O itself, so the handshake runs lazily on the very first `framing::read_message` call, and a failed handshake surfaces there as an ordinary I/O error — the same "return on the first framing error" path a malformed plaintext frame already takes.

## Security, privacy, and compatibility

Through v0.5.0, identical posture to ADR-0010's own "Security, privacy, and compatibility": no authentication, no authorization, no transport encryption. **v0.6.0 (FR-016) closes the authentication/authorization half**: a server configured with tokens (`AuthConfig::new`/`AuthConfig::from_env`) rejects every request from a connection that hasn't presented a recognized token, and further restricts `ReadOnly`-authenticated connections from `UpdateField`/`Transaction` (v0.7.0 extends this to the latter). Token comparison is constant-time (`subtle::ConstantTimeEq`, checked against every configured token, never short-circuited). `AuthConfig::default()` (no tokens configured) is unchanged from v0.5.0's posture — this spec does not force authentication onto any existing deployment. `MAX_FRAME_BYTES` bounds one specific resource-exhaustion vector (a corrupt/hostile length prefix forcing an unbounded allocation) but is not a general defense against a hostile network peer. **v0.7.0 (FR-017) delivers atomicity/isolation with respect to concurrent access for `Request::Transaction`, not crash-atomicity** — a process crash between two of a batch's writes landing on stable storage can leave a partial batch durably applied; a caller relying on this as a full ACID transaction would be relying on a guarantee this spec does not make, exactly as ADR-0013's own "Decision" section states. `Request::Transaction` introduces no new liveness risk either: every transaction is bounded by one request message, never a multi-round-trip session holding a lock open across client round trips. **v0.9.0 (FR-019) closes the transport-encryption half**: a server configured with `TlsConfig` requires every connection to complete a real TLS handshake (via `rusty_tls`) before any framed traffic, including `Authenticate`, is read or written — tokens and every record value now travel encrypted, not plaintext, over such a connection. `TlsConfig::default`-equivalent (`tls: None`) is unchanged from v0.8.0's posture — purely opt-in, forces nothing onto an existing deployment. **This spec's own "do not expose beyond a trusted, localhost/development network" conclusion is finally liftable, but only when both `AuthConfig` *and* `TlsConfig` are configured together** — either alone still leaves the other half of the original gap open (`TlsConfig` alone still lets anyone who can connect do anything; `AuthConfig` alone still puts tokens and every record value in plaintext on the wire). Still not mTLS: the server authenticates itself to the client via a real certificate; client identity remains exactly `AuthConfig`'s existing shared-secret token scheme. **v0.12.0 (FR-022)** brings `SchemaDrivenClient` to the same posture: with `ConnectOptions::tls` it verifies the server's certificate under a caller-chosen `TrustPolicy` and sends its token only inside TLS; `TrustPolicy::DangerNoVerification` exists for a throwaway development certificate and is exactly as unsafe as its name — it encrypts but does not authenticate the server. **v0.13.0 (FR-023) closes the client-identity gap ADR-0014 left named**: with `TlsConfig::new_with_client_auth` a token alone no longer authenticates — the connection must first present a certificate chaining to the operator's own CA roots, or the handshake fails before any frame is read. The certificate decides admission only; class is still the token's, so every existing posture (`TlsConfig` alone, `AuthConfig` alone, both) is unchanged and "certificates only" is `AUTH-FR-007` behind the gate. The operator's client CA key is now the highest-value secret this server depends on. Still not: class from the certificate, revocation without a restart. **v0.15.0 (FR-025)** changes what "transaction" guarantees on a journaled adapter: atomicity with respect to a crash of the server process as well as to concurrent access, at one `fsync` per batch, provided the filesystem honors `fsync`/`msync`; on an unjournaled adapter (the default, `dog_server` without `SERVER_TXN_JOURNAL_PATH` included) v0.7.0's posture is unchanged and a partial batch after a crash remains possible. The journal holds record ids and field values in `codec` form, in the same directory and under the same permissions as the `.mmap` files — no token, no key. Opening the same files without a journal after a crash forgoes the replay; open the same way every time. **v0.21.0 (FR-031)** lets a client certificate carry authorization, not only admission: an operator who pins a leaf's exact DER bytes to a class gets a connection that starts there with no token exchanged at all — a certificates-only deployment becomes a real posture, at the cost of manual rotation (a re-issued certificate has new bytes and loses its class until the map is updated, failure closed). `AuthConfig::is_configured()` growing to include certificate classes means an admitted-but-unclassed connection on such a server goes from `ReadWrite` (v0.13.0's mTLS-alone posture) to unauthenticated — named as the one behavior change an existing certificates-only operator who adds a class would see, and the safe direction. **v0.22.0 (FR-032)** bounds online token guessing: a connection cannot fail `Authenticate` more than `MAX_AUTH_FAILURES` times before it is closed, and an operator who configures a per-peer budget bounds guessing from one address too, at the cost of a documented NAT false-positive mode (many clients behind one address share a budget). Neither mechanism bounds a distributed guess across many addresses — token strength (`AUTH-FR-005`'s advice) still matters — and neither changes what the server says: a throttled or locked-out attempt is `Unauthenticated`, the same as a wrong token, so an attacker learns nothing from the response about which limiter (if either) engaged. **v0.23.0 (FR-033)** answers the question the audit log deliberately left open — "who asked for what kind of request, how often, with what outcome shape" — on a second, opt-in sink an operator turns on independently of the audit log, so auditing admission/authentication decisions never implies also paying per-request volume, and vice versa; the same secrecy invariant holds (no id, field, value, token, or certificate in any line), extended from credentials to a request's content.
