# SERVER-001 — Network server/query layer: `Request`/`Response` protocol in front of `ProductionStore`/`GenericProductionStore`

- Version: 0.6.0 (authentication/authorization, `AuthConfig` — see "Change history")
- Status: Accepted
- Owners: baileyrd
- Depends on: `STORAGE-011` (`ProductionStore`), `STORAGE-012` (`GenericProductionStore`)
- Supersedes: none

## Purpose and scope

`docs/decisions/ADR-0010-server-query-layer-proposal.md` (Accepted) and `docs/design/SERVER-QUERY-LAYER-DESIGN.md` (Accepted) proposed a thin network server/query layer in front of this crate's existing `ProductionStore`/`GenericProductionStore` — a `Request`/`Response` wire protocol over length-prefixed `bincode` framing, thread-per-connection, reusing whichever `RwLock` the wrapped store already manages. This spec covers the real implementation: `src/server/**`, the `server` Cargo feature, three domain adapters (`Dog`, `Order`/`Customer`, `Employee`), a minimal server binary, and the tests that verify it end to end over a real socket.

## Non-goals

- Not transport encryption — named as an explicit, blocking gap by ADR-0010, still open even after v0.6.0's authentication/authorization work (ADR-0012, `docs/design/SERVER-AUTH-DESIGN.md`): this spec does not authorize deploying a server built from it beyond a trusted, localhost/development network unless paired with an external TLS-terminating proxy/tunnel. **Resolved (authentication/authorization half only), v0.6.0**: see FR-016 — `AuthConfig`/`Request::Authenticate` close the "anyone who can open a TCP connection can do anything" gap; the "anyone who can observe the network can read the token and every record in transit" gap remains open.
- Not session or transaction semantics across multiple requests — v0.6.0's per-connection authentication state is the one exception this spec has ever made to "no cross-request server-side state" (see `SERVER-AUTH-DESIGN.md`'s own "Non-goals"), and it is not a session in the query sense: it gates requests, it doesn't remember a cursor or a transaction.
- Not transaction semantics — every request is single-shot, same as every existing store method.
- Not a query language beyond fixed, server-assigned integer field tags — no parser, no planner, no schema-description sub-protocol.
- Not an async runtime (`tokio`) — thread-per-connection was the chosen concurrency model (ADR-0010's "Considered options"); this spec doesn't revisit that choice.
- Not a change to `ProductionStore`, `GenericProductionStore`, or any existing store/durability/concurrency code — this is a new, additive translation layer. **One exception, v0.3.0**: validating the `Employee` domain adapter surfaced a real, load-bearing gap directly in `crate::generic` (`Reversed` never forwarded `Neighbors`) — see FR-012. That fix completes already-accepted `STORAGE-012` capability, not a new storage-layer decision, and is the only `src/generic/**` change this spec's implementation has ever required.
- Not a benchmark suite for v0.1.0 through v0.3.0 — those rounds' acceptance criteria were correctness (a real client/server round trip, a concurrent-client stress test), not throughput measurement, named as a real, unscoped follow-up rather than silently assumed unnecessary. **Resolved, v0.4.0**: `benches/server.rs` closes this gap — see FR-014.
- Not `CreatedAt`/`DiscountCents` field access for `Order` — `OrderProductionStack` (the durable stack this spec wraps) only carries `Status`/`Amount`; those two fields are in-memory-only in `crate::generic` and were never part of the durable production stack to begin with (see `src/server/order.rs`'s own module docs).

## Context and terminology

- **`server` Cargo feature**: off by default, distinct from `research` — this is new, real, additive capability (a network-listening binary surface), not a benchmarked-alternative or historical-spike module. Validating it against `Order`/`Customer` or `Employee` additionally needs `research` (since `order_customer` and `employee_impl` are both research-gated reference material); the `Dog` side needs `server` alone.
- **`ConnectionStore`**: the one trait `dispatch`/`serve` are generic over (`src/server/mod.rs`) — a thin per-domain adapter, implemented by `server::dog::DogConnectionStore` (wraps `ProductionStore`), `server::order::OrderConnectionStore` (wraps `GenericProductionStore<OrderProductionStack>`, behind `research`), and `server::employee::EmployeeConnectionStore` (wraps `GenericProductionStore<EmployeeProductionStack>`, behind `research`).
- **`FieldRef`**: a `u16` field tag, fixed per domain adapter at compile time (not runtime-negotiated) — `Dog`'s `FIELD_BREED`/`FIELD_AGE`, `Order`'s `FIELD_AMOUNT`/`FIELD_STATUS`/`FIELD_CREATED_AT`/`FIELD_DISCOUNT`, `Employee`'s `FIELD_NAME`/`FIELD_DEPARTMENT`/`FIELD_SALARY`.
- **`ScanValue`**: the wire value type. Extends the accepted design's original `U32`/`I64`/`Bool` with `Str(String)` — a necessary completion for `Dog::breed`'s `GetById` response, not a reopened decision; see `src/server/protocol.rs`'s own doc comment for the full list of implementation-time completions beyond the design's proposed shape.
- **`ParentLookup`**: a three-way enum (`Parent(id)`/`NoParent`/`ChildNotFound`) preserving the not-found/no-parent distinction this project's own PR #21 (`docs/PROJECT-STATUS.md`'s `Parent::parent` fix) restored in-process — deliberately not collapsed into a two-way `Option` at the wire boundary.

## Requirements

- `SERVER-001-FR-001`: **`ConnectionStore` trait and `dispatch`** (`src/server/mod.rs`) — one trait covering `get`/`filter_eq`/`scan_field`/`update_field`/`parent`/`children`/`neighbors`; `dispatch(store, request) -> Response` translates one `Request` into one `Response` with no I/O of its own, independently testable.
- `SERVER-001-FR-002`: **Length-prefixed `bincode` framing** (`src/server/framing.rs`) — a 4-byte little-endian length prefix, then a `bincode`-encoded payload, over any `Read`/`Write`. A length prefix exceeding `MAX_FRAME_BYTES` (16 MiB) is rejected *before* any payload buffer is allocated.
- `SERVER-001-FR-003`: **Thread-per-connection serving** (`src/server::serve`) — accepts connections on a `TcpListener` and spawns one OS thread per connection, each holding only `&S: ConnectionStore`; all coordination is whatever locking the wrapped store already does internally (no new lock introduced at this layer). `TCP_NODELAY` is set on every accepted connection — see FR-006.
- `SERVER-001-FR-004`: **`Dog` domain adapter** (`src/server/dog.rs`) — wraps `S: DogStore + ConcurrentStore` (in practice `ProductionStore`). `get`/`scan_field`/`update_field`/`neighbors` map onto `DogStore`/`ConcurrentStore`'s existing methods; `filter_eq`/`parent`/`children` report `ErrorCode::Unsupported` (no equality-index or directed relation exists for `Dog` in-process either).
- `SERVER-001-FR-005`: **`Order`/`Customer` domain adapter** (`src/server/order.rs`, behind `research`) — wraps `GenericProductionStore<OrderProductionStack>`. `get`/`filter_eq`(`Status`)/`scan_field`+`update_field`(`Amount`)/`parent`/`children`(`BelongsToCustomer`) map onto its existing generic methods; `neighbors` reports `ErrorCode::Unsupported` (no symmetric relation exists for `Order`/`Customer`).
- `SERVER-001-FR-006`: **A real, measured Nagle/delayed-ACK fix** — a synchronous request/response protocol pays a real ~40ms-per-round-trip cost with Nagle's algorithm left at its default on either side of the connection; confirmed directly (a concurrent-client integration test went from ~36s to well under a second after disabling it). `TCP_NODELAY` is set server-side (`handle_connection`) and documented as required client-side too.
- `SERVER-001-FR-007`: **A minimal server binary** (`src/bin/dog_server.rs`, `required-features = ["server"]`) — a real, runnable `Dog`-domain server seeded from a small hand-written sample dataset (not `generator`, which is research-gated), so it builds under `server` alone.
- `SERVER-001-FR-008`: **Real end-to-end test coverage**, not just `dispatch`'s in-process logic — `tests/server_dog_integration.rs` and `tests/server_order_integration.rs` drive a real `TcpListener`/`TcpStream` pair (a background thread with a real socket, not a genuinely separate OS process — see those files' own module docs on what that does and doesn't prove) through `GetById`/`FilterEq`/`ScanField`/`UpdateField`/`Parent`/`Children`/`Neighbors`, including the domain-appropriate `Unsupported` cases.
- `SERVER-001-FR-009`: **A flagship concurrent-client stress test**, matching this crate's established rigor — `tests/server_dog_integration.rs`'s `concurrent_clients_over_the_wire_match_a_sequential_replay` runs 8 real client connections × 200 interleaved `GetById`/`UpdateField` requests each against a small contended id pool, verified via sequential-replay linearizability against a fresh in-memory reference (the same pattern `run_concurrency_stress_test`/`production_integration.rs` use), with the write-log append made atomic with the request's round trip — the same fix (and the same false-positive failure mode) `run_concurrency_stress_test`'s own doc comment already documents.
- `SERVER-001-FR-010` (v0.2.0, ADR-0011): **Schema discovery** — `Request::DescribeSchema`/`Response::Schema(DomainSchema)`; `ConnectionStore::describe(&self) -> DomainSchema` (infallible, no store access needed). Both domain adapters implement it, reporting every named field's `ValueKind` and per-operation `FieldCapabilities` (`filter_eq`/`scan`/`update`) honestly — including fields that exist but support none of the three (`Order`'s `created_at_unix_ms`/`discount_cents`) — plus `RelationCapabilities` (`parent_children`/`neighbors`). Field *tags* remain the wire addressing scheme; this adds runtime discovery of what a compile-time client already knows, not a new addressing scheme.
- `SERVER-001-FR-011` (v0.2.0, ADR-0011): **Schema discovery is genuinely usable, not just descriptive** — `tests/server_dog_integration.rs`'s `a_schema_driven_client_discovers_and_uses_the_age_field` and `tests/server_order_integration.rs`'s `a_schema_driven_client_discovers_and_uses_the_status_field` each drive a real client that starts with zero compile-time field-tag knowledge, calls `DescribeSchema`, finds a field by name, and completes a real `UpdateField`/`FilterEq` using only the discovered tag.
- `SERVER-001-FR-012` (v0.3.0): **`Employee` domain adapter** (`src/server/employee.rs`, behind `research`) — wraps `GenericProductionStore<EmployeeProductionStack>`. `get`/`filter_eq`(`Department`)/`scan_field`+`update_field`(`SalaryCents`)/`parent`/`children`(`ReportsTo`)/`neighbors`(`CollaboratesWith`) all map onto real generic methods — the first domain adapter where no relation-kind request is `Unsupported`, since `Employee` (`src/generic_spike/employee_impl.rs`) is self-referential on both a directed (`reports_to`) and a symmetric (`collaborates_with`) relation at once. Building this adapter required a real fix one layer down: `Reversed` (the `ChildOf`-forwarding wrapper) never forwarded `Neighbors`, and `GenericProductionStore` had no `neighbors` method — neither had been needed by any domain stacking only one relation kind. Both fixed directly in `src/generic/{store,production}.rs`; see `docs/decisions/ADR-0009-generic-schema-design-proposal.md`'s "Acceptance and implementation" addendum for the full account. `crate::generic`'s own trait/wrapper design is otherwise unchanged.
- `SERVER-001-FR-013` (v0.3.0): **Real end-to-end coverage of `Employee`, including the first all-relations-real case** — `tests/server_employee_integration.rs` drives a real `TcpListener`/`TcpStream` pair through `GetById`/`FilterEq`/`ScanField`/`UpdateField`/`Parent`/`Children`/`Neighbors`, all succeeding (no domain-shaped `Response::Err`), plus the empty-but-real cases (`Parent` on a record with no manager returns `Response::NoParent`, not an error; `Neighbors` on a record with no collaborators returns an empty `RecordList`, not an error) and a schema-driven test (matching FR-011's pattern) confirming `DescribeSchema` reports both `RelationCapabilities` as `true` for the first time.
- `SERVER-001-FR-014` (v0.4.0): **Throughput/latency benchmark** (`benches/server.rs`, `required-features = ["server", "research"]`) — a custom, non-Criterion harness (matching `benches/concurrency.rs`'s own shape, for the same reason: aggregate ops/sec across concurrently-running threads isn't what Criterion's `b.iter` model measures) that puts a real `TcpListener`/`TcpStream` pair in the timed path for the first time in this crate. Measures, per domain (`Dog`, `Order`/`Customer`, `Employee`): single-connection, zero-contention `GetById` round-trip latency (average of 5,000 sequential requests), and aggregate throughput under a thread-per-connection sweep (1/4/8/16 concurrent client connections, each a real socket, `Barrier`-synchronized, ops/sec from the slowest thread's elapsed time). Uses a small, fixed 20-id pool per domain (matching the flagship concurrent-client stress test's own contended-pool precedent), not this crate's usual 1K/100K/1M `SIZES` sweep — see the bench's own module docs for why. Results in `RESULTS.md`'s `## Server / query layer` section.
- `SERVER-001-FR-015` (v0.5.0): **A real, reusable schema-driven client** (`src/server/client.rs`'s `SchemaDrivenClient`, unconditional under `server` — no domain-specific code, so no `research` gate) — promotes the one-off schema-driven logic each of `tests/server_{dog,order,employee}_integration.rs`'s own schema-driven tests had reimplemented (FR-011/FR-013) into real library API. `connect` sends `Request::DescribeSchema` first and keeps the result; every subsequent method (`get`/`filter_eq`/`scan`/`update`/`parent`/`children`/`neighbors`) is addressed by field *name*, not a compile-time `FieldRef` constant — `get` returns `(String, ScanValue)` pairs, not `(FieldRef, ScanValue)`, for the same reason. `filter_eq`/`scan`/`update`/`parent`/`children`/`neighbors` each check the relevant `FieldCapabilities`/`RelationCapabilities` from the discovered schema *before* sending anything, returning `ClientError::Unsupported` locally rather than paying a round trip for something the schema already ruled out — an optimization, not a trust boundary: `dispatch` still enforces the identical rules independently on the server side. An unrecognized field name is `ClientError::UnknownField`, checked the same way, no round trip.
- `SERVER-001-FR-016` (v0.6.0, ADR-0012): **Authentication/authorization** (`AuthConfig`/`TokenClass` in `src/server/mod.rs`, `Request::Authenticate`/`ErrorCode::Unauthenticated`/`ErrorCode::Unauthorized` in `src/server/protocol.rs`) — implements `docs/design/SERVER-AUTH-DESIGN.md`'s `AUTH-FR-001` through `AUTH-FR-007` in full. `serve` takes an `AuthConfig` (two optional tokens, `read_only`/`read_write`, each mapping to a `TokenClass`); `handle_connection` gates its own request loop on per-connection state (`Option<TokenClass>`), never touching `dispatch` or the shared store. A connection with no successful `Authenticate` yet is rejected with `ErrorCode::Unauthenticated` for every other request kind, including `DescribeSchema` (the design's own "uniform rule" resolution of its one open question). `TokenClass::ReadOnly` is further rejected from `Request::UpdateField` with `ErrorCode::Unauthorized`; every other request kind succeeds for both classes once authenticated. `AuthConfig::check` compares the presented token against every configured token via `subtle::ConstantTimeEq`, never short-circuited on the first match (a new, narrow dependency — `Cargo.toml`'s own comment explains why this is the one place this spec departs from "avoid new dependencies"). `AuthConfig::default()` (no tokens configured) leaves every connection pre-authenticated at `TokenClass::ReadWrite` — `AUTH-FR-007`'s exact backward-compatibility bar; every pre-existing call site (`tests/server_{dog,order,employee}_integration.rs`, `tests/server_schema_driven_client.rs`, `benches/server.rs`) now passes `AuthConfig::default()` explicitly and required zero other change. `src/bin/dog_server.rs` uses `AuthConfig::from_env()` instead, reading `SERVER_AUTH_READ_ONLY_TOKEN`/`SERVER_AUTH_READ_WRITE_TOKEN` from the process environment at startup (`AUTH-FR-005`) — the exact env var names are this spec's own implementation-time decision, left open by the design. `tests/server_auth_integration.rs` (`required-features = ["server"]` — Dog domain alone is sufficient, no domain-specific behavior is under test) covers every functional acceptance criterion `SERVER-AUTH-DESIGN.md` names over a real socket; `src/server/mod.rs`'s own unit tests additionally include a timing measurement comparing `AuthConfig::check`'s latency for tokens that differ at the first byte vs. the last byte, the empirical evidence `AUTH-FR-006` calls for.

## Architecture and interfaces

`src/server/{mod,protocol,framing,dog,client}.rs` (unconditional under `server`); `src/server/order.rs`, `src/server/employee.rs` (additionally behind `research`). `src/bin/dog_server.rs` (`required-features = ["server"]`). `tests/server_dog_integration.rs` (`required-features = ["server"]`), `tests/server_order_integration.rs`, `tests/server_employee_integration.rs`, `tests/server_schema_driven_client.rs` (`required-features = ["server", "research"]` — the client test file exercises all three domains in one target, matching `benches/server.rs`'s own precedent), `tests/server_auth_integration.rs` (`required-features = ["server"]`). `benches/server.rs` (`required-features = ["server", "research"]`, `harness = false`). No changes to `src/production.rs`, `src/store/**`, `src/durability/**`, `src/concurrency/**`. `src/generic/{store,production}.rs` gained the `Neighbors`-forwarding fix described in FR-012 — the one exception to this spec's original "no `crate::generic` changes" scope, a completion of already-accepted `STORAGE-012` capability rather than a new decision (see `STORAGE-012`'s own change history). `Cargo.toml` gained one new dependency at v0.6.0, `subtle` (constant-time token comparison, FR-016) — every earlier version reused `bincode`/`serde`/`uuid`, all already present; `benches/server.rs` reuses `criterion`'s harness plumbing only nominally (`harness = false`, same as `benches/concurrency.rs` — a plain `fn main()`, no Criterion API calls); `server::client` reuses `framing`/`protocol` directly, no new dependency either.

## Data/state and invariants

- No new persistent state or on-disk format — the server process wraps an existing durable store; every byte on disk is written by `ProductionStore`/`GenericProductionStore` exactly as it already was.
- Per-connection state is limited to the TCP stream and its read/write buffers — no session, no per-client cursor, no cross-request server-side state, matching the "no transaction semantics" non-goal directly.
- Field tags are fixed at compile time per adapter (constants in `dog.rs`/`order.rs`), not negotiated at connection time.

## Errors, failure, recovery, and observability

- `dispatch` never panics on a well-formed but semantically invalid request (unknown field, unsupported operation, malformed value) — it returns `Response::Err { code, message }` with one of five `ErrorCode` variants (`UnknownField`/`Unsupported`/`Malformed`/`Unauthenticated`/`Unauthorized`, the last two added at v0.6.0, FR-016).
- `handle_connection` never panics on a malformed or oversized frame, or on a client disconnecting mid-request — the connection simply ends (`FrameError`, an ordinary `Result::Err`, not a panic). A rejected `UpdateField` (wrong `TokenClass`) or a failed `Authenticate` (wrong/no token) does not end the connection — only that one request is rejected; the connection stays open (v0.6.0).
- One bad `accept()` doesn't take down `serve`'s loop; one connection's error doesn't affect any other connection, since the only shared state is the wrapped store itself, already safe for concurrent access.
- Out of scope, named rather than silently assumed solved: structured logging/metrics, graceful shutdown/drain, a health-check RPC. Also out of scope, named by `SERVER-AUTH-DESIGN.md` rather than silently assumed solved: rate-limiting failed authentication attempts, lockout after N failures, an audit log of authentication attempts.

## Security, privacy, and compatibility

Through v0.5.0, identical posture to ADR-0010's own "Security, privacy, and compatibility": no authentication, no authorization, no transport encryption. **v0.6.0 (FR-016) closes the authentication/authorization half**: a server configured with tokens (`AuthConfig::new`/`AuthConfig::from_env`) rejects every request from a connection that hasn't presented a recognized token, and further restricts `ReadOnly`-authenticated connections from `UpdateField`. Token comparison is constant-time (`subtle::ConstantTimeEq`, checked against every configured token, never short-circuited). **Transport encryption remains open** — tokens and every record value are still plaintext on the wire; a server exposed beyond `127.0.0.1`/a trusted network still requires an external TLS-terminating proxy or tunnel, exactly as ADR-0012's own "Decision" section states. `AuthConfig::default()` (no tokens configured) is unchanged from v0.5.0's posture — this spec does not force authentication onto any existing deployment. `MAX_FRAME_BYTES` bounds one specific resource-exhaustion vector (a corrupt/hostile length prefix forcing an unbounded allocation) but is not a general defense against a hostile network peer — this spec's implementation does not change ADR-0010's "do not expose beyond a trusted, localhost/development network" conclusion, even with FR-016 configured.

- `cargo test --features server` passes (`Dog` domain: unit tests in `server::{dog,framing,protocol}` + `server::tests`, plus `tests/server_dog_integration.rs`'s four tests including the concurrent-client stress test and the schema-driven test, plus `tests/server_auth_integration.rs`'s five tests).
- `cargo test --features server,research` additionally passes `server::order::tests::*`, `server::employee::tests::*`, `tests/server_order_integration.rs`'s two tests, `tests/server_employee_integration.rs`'s three tests (the all-relations-real round trip, the schema-driven test, and the empty-but-real `Parent`/`Neighbors` cases), and `tests/server_schema_driven_client.rs`'s four tests (one per domain plus the unknown-field-name case).
- `cargo test --all-features`/`cargo test` (default) both still pass unchanged elsewhere — the `server` module adds no default-build surface.
- `cargo fmt --all -- --check` / `cargo clippy --all-targets --all-features -- -D warnings` / `cargo check --all-targets --all-features` all clean.
- No `src/production.rs`, `src/store/**`, `src/durability/**`, or `src/concurrency/**` changes — verified by diff. `src/generic/{store,production}.rs` changes are limited to the one `Neighbors`-forwarding completion FR-012 describes.
- `cargo bench --features server,research --bench server` completes without panics, prints its latency/throughput table for all three domains, numbers reported in `RESULTS.md`'s `## Server / query layer` section.
- Every `SERVER-AUTH-DESIGN.md` functional acceptance criterion holds over a real socket (`tests/server_auth_integration.rs`): unauthenticated rejection for every request kind including `DescribeSchema`; a wrong token indistinguishable from never authenticating; `ReadOnly` succeeding on reads and rejected on `UpdateField`; `ReadWrite` succeeding on everything; no configured tokens reproducing the original unauthenticated behavior with zero pre-existing test changes required.

## Verification plan

- Unit tests: wire-format round trip (`protocol.rs`, including `Request::Authenticate` and the two new `ErrorCode` variants, v0.6.0), framing round trip + oversized/truncated-frame handling (`framing.rs`), `dispatch`'s per-request-kind response mapping against a minimal fixture store (`mod.rs`), each domain adapter's own behavior against a real `ProductionStore`/`GenericProductionStore` (`dog.rs`/`order.rs`/`employee.rs`), `AuthConfig::check` against configured/unconfigured/single-class token setups (v0.6.0).
- Real end-to-end tests: a genuine `TcpListener`/`TcpStream` pair, all three domains, every request kind including the domain-appropriate `Unsupported` cases (`Dog`, `Order`/`Customer`) and the all-real case (`Employee`), a second independent connection observing the first's writes (proving the store, not connection-local state, is shared).
- Flagship stress test: 8 real client connections, 200 requests each, interleaved reads/writes against a 20-id contended pool, verified via sequential-replay linearizability.
- Benchmark run: `benches/server.rs`, all three domains, single-connection latency plus a thread-per-connection throughput sweep, run twice per environment to characterize run-to-run variance — originally 1/4/8/16 on this session's 4-core container, retuned to 1/4/24/48 for the `Beast` real-hardware follow-up, then to 1/4/32/64 for the `baileyai` real-hardware follow-up (see `RESULTS.md`).
- Schema-driven client: `tests/server_schema_driven_client.rs` connects to all three domains using only `SchemaDrivenClient`, importing no `FIELD_*` constant from any domain adapter — proves the client is genuinely usable end to end (discovers fields by name, drives every request kind through them), not just that its own unit-level logic is correct.
- Authentication/authorization (v0.6.0): `tests/server_auth_integration.rs` drives a real client through every `SERVER-AUTH-DESIGN.md` functional acceptance criterion; `src/server/mod.rs`'s own unit tests include a timing measurement (mean latency of `AuthConfig::check` over 20,000 iterations each, for a token differing at its first byte vs. one differing only at its last byte) as the empirical evidence `AUTH-FR-006` calls for — measured directly against the comparison function, not over a real TCP round trip, since network jitter (microseconds to milliseconds) would completely swamp the signal this specific claim is about.

## Open questions

- **Resolved, v0.6.0**: authentication/authorization now exists (FR-016, ADR-0012) — see this document's own "Security, privacy, and compatibility" section. Transport encryption remains a real, open gap; no revisit scheduled.
- **Resolved, v0.4.0**: a throughput/latency benchmark now exists (`benches/server.rs`, FR-014) — see `RESULTS.md`'s `## Server / query layer` section.
- **Resolved (real-hardware follow-up, `Beast`)**: the thread-per-connection model's real connection-count ceiling was re-measured on the owner's Windows dev machine (`Beast`, 24 real cores — real dedicated hardware, not a container), `THREAD_COUNTS` retuned to `[1, 4, 24, 48]` to match. The container's flat 4-through-16 plateau was confirmed to be that environment's own 4-core ceiling, not the model's: throughput genuinely keeps climbing from 4 to 24 threads on real hardware (roughly doubling again, every domain, both runs), then flattens or degrades at 48 (2× cores, deliberate oversubscription).
